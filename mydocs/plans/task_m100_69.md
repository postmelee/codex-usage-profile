# Task M100 #69 수행계획서

GitHub Issue: [#69](https://github.com/postmelee/codex-usage-profile/issues/69)
마일스톤: M100

## 목적

Codex Usage Profile의 product와 Sites 표면에 공통 semantic theme 계약을 도입하고
`system`, `light`, `dark` appearance를 제공한다. 첫 방문은 browser/OS 설정을 따르고,
사용자가 선택한 override는 device-local preference로 보존한다.

단순한 색상 반전이 아니라 Home, owner/public Profile, Settings, device 승인,
Marketing landing, Share Studio, skeleton·empty·error 상태와 Profile heatmap·tooltip까지
동일한 테마 체계에서 가독성과 접근성을 유지한다. Account Usage, 인증, API, D1/R2,
CLI, 카드 렌더러와 production 배포 계약은 변경하지 않는다.

## 배경

- 현재 `src/styles.css`의 `:root`는 `color-scheme: dark`와 dark palette만 정의한다.
- 루트 토큰 밖에도 흰색·검정·반투명 surface·상태색·카드 효과·heatmap 색상이
  컴포넌트별 값으로 남아 있어 light mode를 단순 override하면 대비와 상태 의미가 깨질 수 있다.
- product는 `index.html`과 `src/main.jsx`, Sites marketing 표면은 `sites.html`과
  `src/profile-marketing/sites-entry.jsx`를 사용하므로 두 진입점의 첫 paint 계약이 같아야 한다.
- Task #68에서 browser locale Provider와 en/ko catalog가 전역화되었으므로 appearance
  control의 문구·접근성 이름도 해당 계약을 재사용할 수 있다.
- 저장소는 `.openai/hosting.json`을 사용하는 기존 Sites 프로젝트다. 현재 Vite·lockfile·
  Cloudflare Worker 호환 구조를 유지하고, 이 task에서는 production hosting 변경을 하지 않는다.
- Codex 앱의 appearance 동작과 light/dark palette mapping은 읽기 전용 참고 자료로만
  분석한다. 저장소 라이선스와 호환되는 일반 패턴만 재현하며 제품 고유 자산이나 비공개
  구현을 복사하지 않는다.

## 설계 방향

- appearance preference의 canonical 값은 `system`, `light`, `dark` 세 가지로 제한한다.
  저장 값이 없거나 손상되면 `system`으로 fail-safe 한다.
- browser storage에는 device-local preference만 저장한다. 계정·backend 데이터와 결합하지
  않으며 storage 접근 실패에서도 system mode로 정상 렌더한다.
- document에는 선택 mode와 실제 resolved theme를 구분해 표현한다. CSS는 semantic token만
  소비하고 component가 mode를 직접 분기하지 않게 한다.
- 반대 테마 flash를 막기 위해 product와 Sites HTML의 React mount 이전에 작은 bootstrap을
  실행한다. bootstrap과 React runtime은 같은 storage key·mode resolver 계약을 사용하고
  테스트로 parity를 고정한다.
- light/dark palette는 Codex 앱의 현재 appearance를 읽기 전용으로 분석한 뒤 일반적인
  semantic 역할과 관찰 가능한 동작만 참고한다. 직접 재사용 가능 여부와 라이선스 판단은
  구현계획서에 기록한다.
- theme control은 Codex 앱과 유사하게 Settings의 독립 Appearance panel에 둔다. 기존
  account menu의 Settings 진입을 사용하고 header에 중복 quick toggle은 추가하지 않는 안을
  권고한다.
- control은 세 값이 명확한 radio group 또는 동등한 단일 선택 widget으로 구현하고 label,
  checked state, keyboard focus, en/ko message를 제공한다.
- dark palette의 제품 정체성은 유지하고 light palette는 대비를 우선한다. heatmap intensity와
  status 의미는 색상 하나에만 의존하지 않으며 focus ring은 두 theme에서 식별 가능해야 한다.
- card 이미지 자체는 renderer 산출물이므로 변경하지 않는다. preview container, border,
  shadow, beam, glare와 주변 surface만 현재 document theme에 맞춘다.
- 기존 Vite, package manager, lockfile, Sites Worker 구조를 유지한다. 이 task와 무관한
  이미지 생성, starter 교체, dependency 추가, hosting handoff는 수행하지 않는다.

## 리스크

- **초기 theme flash**: CSS와 React가 적용되기 전 반대 theme가 노출될 수 있다. 두 HTML
  entry에서 mount 전 bootstrap을 실행하고 Playwright 초기 paint 계약으로 고정한다.
- **bootstrap/runtime drift**: inline 초기화와 React resolver가 달라질 수 있다. mode·storage
  상수와 결과 parity 테스트를 두고 구현계획에서 공유 방법을 확정한다.
- **light mode 대비 손실**: dark 전용 alpha와 shadow가 밝은 surface에서 사라질 수 있다.
  semantic 역할별 token과 대표 component computed-style·시각 검증을 함께 사용한다.
- **system listener 누수**: React StrictMode에서 listener가 중복될 수 있다. 명시 cleanup과
  subscribe/unsubscribe 단위 테스트를 둔다.
- **storage 예외**: privacy mode나 손상 값에서 접근이 실패할 수 있다. 모든 read/write를
  예외 안전하게 만들고 system fallback을 검증한다.
- **카드 자체와 주변 theme 혼동**: renderer 산출물을 바꾸지 않고 preview chrome만 theme에
  맞추며 제한 경로 diff로 범위를 강제한다.
- **범위 팽창**: 색상 정리 중 #71~#73 또는 hosting 개선으로 번질 수 있다. 이번 task의
  semantic theme와 appearance control 외 변경은 후속 이슈로 유지한다.
