# Task M100 #59 수행계획서

GitHub Issue: [#59](https://github.com/postmelee/codex-usage-profile/issues/59)
마일스톤: M100

## 목적

device 승인 요청이 성공한 뒤 다시 클릭할 수 없는 terminal UI 상태를
제공하고, 승인 성공을 체크 아이콘·문구·접근성 상태로 명확히 전달한다.
CLI가 challenge를 시작할 때 optional `login | submit` intent를 전달해
브라우저가 현재 CLI 프로세스에 맞는 다음 행동을 안내한다.

동일한 authenticated owner가 이미 승인·교환된 challenge를 새로고침이나
요청 재시도로 다시 승인할 때는 성공 상태를 복구하되 토큰을 다시 발급하지
않는다. 다른 owner, 만료 challenge와 유효하지 않은 code는 기존처럼
fail-closed로 처리한다.

## 배경

현재 `DeviceApprovalPage`의 승인 가능 조건은 요청 중 상태만 제외하므로
성공 후 버튼이 다시 활성화된다. 재클릭하면 backend가 pending이 아닌
challenge를 `invalid_request`로 거부해, 실제로는 성공한 사용자가 실패로
오인할 수 있다.

또한 인증정보가 없는 `login`과 `submit`은 같은 device approval 화면을
사용하지만 승인 이후 동작은 다르다. `submit`은 기존 CLI 프로세스가 자동으로
usage 제출을 계속하고, `login`은 로그인만 완료하므로 이후 submit 명령이
필요하다. 즉시 Home으로 이동하면 CLI submit 완료 전에 `Submit usage
first`가 보일 수 있어, 브라우저 redirect보다 terminal 복귀 안내가 우선이다.

Issue #17의 device-code login API와 승인 UI, #34의 Home onboarding,
#45의 production 전체 흐름, #55의 랜딩 loading-card 전환을 기준으로 한다.
현재 canonical MVP는 `.openai/hosting.json`의 기존 Sites project와 D1/R2
linkage를 사용하므로 challenge의 optional metadata는 기존 D1 migration
runner와 store contract에 맞춰 추가한다.

## 설계 방향

- **표시 전용 intent**: `login`, `submit`, `null`만 허용한다. CLI
  `login`은 `login`, 인증정보가 없어 device flow를 시작하는 `submit`은
  `submit`을 전송한다. 기존 credential이 있는 `submit`은 device flow를
  시작하지 않는다. intent는 표시 문구 선택에만 사용하고 owner 검증,
  challenge 상태 전이, token scope와 redirect에는 사용하지 않는다.
- **구버전 호환**: start body에서 intent가 없으면 `null`로 저장하고
  일반적인 “터미널로 돌아가세요” 안내를 반환한다. unknown/non-string
  intent는 묵인하지 않고 validation error로 거부한다.
- **durable schema**: D1과 Postgres `cli_login_challenges`에 nullable
  `intent` column과 `login | submit | NULL` 제약을 별도 forward migration으로
  추가한다. 기존 rows는 `NULL`로 유지한다. memory/file store는 기존 generic
  record 보존 경계를 따르고 D1/Postgres column mapping만 확장한다.
- **승인 응답 최소화**: device authorize 응답은 UI가 필요한 status,
  normalized intent와 완료 시각만 포함하는 전용 serializer를 사용한다.
  raw device code/digest, owner id, CLI token id·token은 반환하지 않는다.
  start/poll의 기존 단일 token 전달 계약은 바꾸지 않는다.
- **동일 owner 복구**: expiry를 먼저 검사한 뒤 challenge가
  `approved`/`exchanged`이고 저장된 owner와 현재 authenticated owner가
  같으면 현재 상태를 그대로 반환한다. owner가 다르거나
  pending 이외의 허용되지 않은 상태는 거부한다. pending 승인 경합에서
  atomic operation의 loser는 challenge를 한 번 다시 읽고 동일 owner의
  완료 상태일 때만 성공으로 복구한다.
- **단일 발급 불변식**: 승인 복구 경로는 token service와
  `atomic.exchangeCliLogin`을 호출하지 않는다. token은 기존 poll 교환에서
  한 번만 발급되며 승인 재시도 응답에 포함되지 않는다.
- **오류 상태**: network, `429`, `5xx`는 같은 code로 수동 재시도 가능한
  retryable error로 돌린다. expired/not-found/validation/ownership 등
  terminal error는 해당 code의 승인 버튼을 잠그되 input 편집은 허용하고,
  code 변경 시 idle로 초기화한다. 성공 상태만 input까지 영구 잠근다.
- **intent별 onboarding**: `submit`은 현재 terminal 프로세스가 usage
  submit을 계속하므로 명령 재실행을 안내하지 않는다. `login`은
  `npx codex-usage-profile@latest submit`을 명시적 copy button으로 제공한다.
  현재 origin이 CLI 기본 production origin과 다르면
  `--server <current-origin>`을 추가하며, arbitrary response URL이나 query를
  command에 사용하지 않는다.
- **선택적 이동**: success 영역에 same-origin Home/profile link를 제공할
  수 있지만 자동 navigation은 하지 않는다. 브라우저 storage와 자동
  clipboard write도 사용하지 않는다.
- **motion personality**: 기존 clean dashboard에 맞춘 Corporate motion을
  사용한다. 성공 전환은 약 240ms `cubic-bezier(0.2, 0, 0, 1)`의 작은
  content 전환으로 제한하고 bounce나 layout 이동을 넣지 않는다. check
  icon과 `Approved` 문구로 색상 외 의미를 제공하며 reduced-motion에서는
  animation/transition 없이 즉시 같은 완료 상태를 표시한다.
- **Sites 경계**: 기존 Sites project/D1/R2 binding을 보존한다. task에서는
  D1 migration과 production artifact를 검증하지만 production database
  migration이나 deploy는 수행하지 않는다.

## 리스크

- **중복 승인과 token 재발급**: idempotent approval을 잘못 구현하면
  exchange까지 재실행할 수 있다. 복구 경로는 저장된 상태만 반환하고 기존
  atomic exchange 및 poll의 one-token invariant를 유지한다.
- **승인 race**: 두 요청이 모두 pending을 읽은 뒤 하나가 transaction에서
  실패할 수 있다. 실패 후 한 번만 re-read하고 same-owner approved/exchanged
  상태에서만 성공으로 복구한다.
- **owner 경계 약화**: 완료 상태라는 이유로 다른 owner에게 성공을 반환할
  수 있다. authenticated owner와 challenge owner를 server에서 비교하고
  mismatch는 기존 오류로 fail closed한다.
- **expired 완료 상태 오인**: 오래된 exchanged challenge를 무기한 성공으로
  보일 수 있다. 모든 승인 복구 전에 expiry를 검사해 expired challenge는
  성공으로 바꾸지 않는다.
- **schema 호환성**: 새 code가 migration 전 D1/Postgres에서 column을
  요구하면 runtime이 실패한다. 별도 forward migration, 기존 row의 nullable
  fallback과 migration/artifact 검증을 같은 task에 포함한다.
- **명령 injection/잘못된 origin**: response나 query의 임의 문자열을
  command에 넣으면 위험하다. browser의 normalized `location.origin`과
  고정 command token만 조합하고 자동 실행하지 않는다.
- **오류 재시도 dead end**: 모든 error를 terminal로 잠그면 일시 장애를
  복구할 수 없다. network/429/5xx와 terminal code를 분리하고 code 편집 시
  terminal 상태를 초기화한다.
- **접근성·과도한 motion**: 초록색이나 animation만으로 성공을 전달할 수
  있다. check icon, text, live/busy semantics를 함께 사용하고 Corporate
  timing을 240ms로 제한하며 reduced-motion에서 제거한다.
- **배포 범위 오인**: migration과 Sites artifact가 성공해도 이번 task는
  production DB migration/deploy/access를 승인하지 않는다. 배포는 별도
  지시와 gate에서만 수행한다.

## 승인 요청 사항

- optional `login | submit | null` intent를 표시 전용 metadata로 저장하고
  invalid enum을 거부하는 계약
- D1/Postgres challenge table에 nullable intent column을 추가하되 기존
  Sites project/D1/R2 linkage는 유지하는 migration 방향
- device approval 응답을 status/intent/완료 시각으로 최소화하고
  owner/token/digest를 제외하는 방향
- same-owner approved/exchanged 및 pending race를 상태 re-read로 복구하되
  token exchange를 재실행하지 않는 idempotency 경계
- retryable error는 수동 재시도, terminal error는 code 변경으로만 idle
  복귀하며 approved에서는 button/input을 모두 잠그는 UI 상태 모델
- login/submit/no-intent별 안내, local origin 보존 copy UI, 보조 link와
  자동 redirect/storage/clipboard 금지
- 약 240ms Corporate 성공 전환과 reduced-motion 정적 대체
- 공식 사용자 문서는 기존 `docs/cli-submit.md`와 package README만
  갱신하고 production deploy를 제외하는 4개 Stage

승인되면 `task_m100_59_impl.md`에서 단계별 산출물, 검증 명령, 커밋
메시지를 구체화한다.
