# Task M100 #44 수행계획서

GitHub Issue: [#44](https://github.com/postmelee/codex-usage-profile/issues/44)
마일스톤: M100

## 목적

`codex-usage-profile` CLI의 첫 public npm version을 검증된 하나의
artifact로 게시하고, 완전히 분리된 사용자 환경에서 production Sites origin을
기본값으로 사용하는 login, status, Account Usage Contract v1 submit과 logout
흐름을 확인한다.

첫 publish는 되돌리거나 같은 version으로 덮어쓸 수 없는 외부 변경이다.
package/repository 공개 상태와 publish 인증 경로를 먼저 결정하고, exact
version·tarball digest·파일 목록·검증 결과에 대한 별도 승인 뒤에만 registry
write를 수행한다. 공개 문서는 실제 registry 상태를 확인한 뒤에만
`npx codex-usage-profile@latest`를 현재 사용 가능한 명령으로 확정한다.

## 배경

- Task #51과 PR #52에서 ChatGPT Sites + D1 + native R2를 M100 canonical
  production으로 공개 전환했다.
- canonical origin은
  `https://codex-usage-profile-stage5.meleeisdeveloping.chatgpt.site`이며,
  현재 landing과 `/healthz`는 public `200`이다.
- CLI package의 현재 이름과 version은 `codex-usage-profile@0.1.0`이고
  `publishConfig.access`는 `public`이다.
- 2026-07-28 registry 조회는 package `404 Not Found`였다. package 이름은
  publish 직전 다시 확인하며, 충돌 시 임의 rename이나 다른 scope로 우회하지
  않는다.
- package README와 제품 landing은
  `npx codex-usage-profile@latest submit`을 안내하지만 아직 registry artifact가
  없어 외부 사용자가 핵심 흐름을 완료할 수 없다.
- GitHub repository는 현재 private이고 package의 `homepage`, `repository`,
  `bugs`는 이 private repository를 가리킨다. private 상태로 공개 package를
  게시하면 외부 사용자가 해당 링크를 열 수 없고 provenance도 생성되지 않는다.
- repository에는 npm publish workflow가 없다. 현행 npm trusted publishing은
  npm CLI 11.5.1+/Node 22.14.0+와 OIDC를 요구하며, provenance는 public
  repository와 public package 조합에서만 자동 생성된다.
- 현행 npm staged publishing은 이미 registry에 존재하는 package에만 사용할 수
  있어 brand-new `0.1.0`의 최초 publish에는 사용할 수 없다. 최초 version은
  2FA interactive publish 또는 승인된 CI credential을 사용하는 direct
  publish가 필요하다.
- #43 Cloud Run fallback은 실제 비용·quota·정책·장애 trigger가 없으므로 이
  release의 선행조건이 아니다. #45가 npm publish 뒤 production whole-flow와
  security의 최종 release QA를 담당한다.

## 설계 방향

- **첫 version 고정**: registry가 비어 있는 동안 package의 현재 version
  `0.1.0`을 첫 후보로 유지한다. package-name 충돌, 이미 존재하는 version 또는
  account ownership 불일치가 보이면 자동 rename/version bump를 하지 않고
  중단한다.
- **artifact-first**: 하나의 clean commit에서 `npm pack`한 tarball의 SHA-512,
  파일 목록, unpacked size와 bin 동작을 고정한다. publish와 fresh install은
  같은 artifact/version을 검증해야 한다.
- **공개 문서 truthfulness**: registry `200`, public access, exact dist-tag와
  install smoke를 확인하기 전에는 “published” 표현으로 문서를 바꾸지 않는다.
- **최초 publish channel Gate A**:
  - 권고안 A — repository 공개 + GitHub Actions publish:
    전체 Git history의 credential/private-data/license scan을 통과하고
    repository public 전환을 별도 승인받는다. GitHub-hosted runner에서
    Node 24와 현재 npm을 사용하고, 최초 publish에만 최소 범위의 임시 npm
    credential을 사용해 provenance가 있는 public `0.1.0`을 게시한다. 성공
    뒤 package trusted publisher를 설정하고 임시 credential을 폐기한다.
  - 대안 B — repository private 유지 + interactive 2FA publish:
    local interactive `npm publish --access public`로 최초 version을 게시한다.
    public repository가 아니므로 provenance가 없음을 registry와 문서에
    정확히 기록한다. 외부에서 열 수 없는 `homepage`, `repository`, `bugs`
    metadata는 public Site 또는 생략으로 정리한다. package 생성 뒤 future
    publish에는 private-repository OIDC trusted publisher를 검토하되 provenance
    미지원은 유지된다.
- **공개 전환 보수성**: 권고안 A의 repository public 전환은 수행계획 승인만으로
  실행하지 않는다. full-history scan 결과, 공개될 branch/tag, package metadata,
  workflow와 rollback 한계를 제시한 Gate A에서 다시 승인받는다.
- **2FA와 token 최소화**: raw npm token, OTP, recovery code와 browser session을
  source, shell argument, log, URL, report 또는 GitHub output에 기록하지 않는다.
  CI token을 선택하면 최초 publish에 필요한 최소 권한·기간으로 제한하고 성공
  직후 secret과 token을 폐기한다. package 생성 뒤에는 “2FA required and
  disallow tokens”와 trusted publisher를 우선한다.
- **irreversible publish Gate B**: package name/version, public access,
  dist-tag, tarball SHA-512, 파일 목록, dependency tree, test 결과, publish
  account와 선택 channel을 제시하고 명시 승인 전에는 `npm publish`, tag,
  release를 실행하지 않는다.
- **production smoke Gate C**: 실제 Account Usage Contract v1 submit에는
  작업지시자의 별도 data 전송 승인을 받는다. 승인 범위는 집계 contract
  field뿐이며 prompt, response, Codex/OpenAI credential과 local session file은
  포함하지 않는다.
- **fresh 환경**: repository checkout, 기존 npm cache, 기존 product credential,
  browser session에 의존하지 않는 임시 HOME/XDG/npm cache에서 exact version을
  설치한다. 검증 종료 시 CLI token·credential과 test publication을 revoke,
  logout, unpublish하며 owner data의 보존/삭제는 exact plan을 제시해 별도
  승인받는다.
- **version 불변성**: publish 후 오류가 발견돼도 `0.1.0`을 덮어쓰거나 즉시
  unpublish하지 않는다. 영향 범위를 기록하고 수정된 `0.1.1` 후보를 별도
  승인한다. 사용 중단 안내가 필요하면 `npm deprecate`도 exact message 승인
  뒤에만 수행한다.
- **#43 보류**: 기존 `local/task43` Stage 1/2 작업과 main worktree를 변경하지
  않는다. #44는 분리 worktree `local/task44`에서 진행하고 Cloud Run fallback
  코드를 merge하지 않는다.

## 잠정 단계

- **Stage 1 — package release contract와 local preflight**
  - metadata/bin/files/license/dependency, tarball manifest·integrity와 secret/path
    scan을 반복 가능한 verifier와 test로 고정한다.
  - `0.1.0` clean install, Node 지원 범위, default/override/origin binding을
    local fixture에서 검증한다.
- **Stage 2 — Gate A: repository visibility와 최초 publish channel**
  - npm account/name/2FA, repository visibility, history scan, provenance 조건과
    exact channel A/B를 제시한다.
  - 승인된 channel의 workflow 또는 interactive runbook을 구현하되 registry
    publish와 public transition은 해당 Gate의 exact 승인 범위만 수행한다.
- **Stage 3 — immutable release candidate와 Gate B**
  - 전체 test, pack, install, artifact scan과 dependency audit를 clean commit에서
    실행한다.
  - exact `0.1.0`, tarball digest/files, account, access, tag/dist-tag와 rollback
    한계를 제시하고 최초 publish 승인을 받는다.
- **Stage 4 — first npm publish와 registry 검증**
  - 승인된 한 channel로 `0.1.0`을 한 번 게시한다.
  - registry metadata, public tarball/integrity, `latest`, provenance 상태와
    temporary credential cleanup을 검증한다.
- **Stage 5 — Gate C: published CLI production smoke와 사용자 문서**
  - 별도 전송 승인 뒤 isolated fresh install로 production OAuth device flow,
    Contract v1 submit, status, publish/unpublish와 logout/revoke를 검증한다.
  - test data를 승인된 종료 상태로 정리하고 실제 package 상태를 README와
    CLI/card 문서에 반영한다.
- **Stage 6 — release 판정과 #45 handoff**
  - 전체 회귀, install/registry/security scan을 재실행한다.
  - exact version/origin, provenance와 잔여 위험을 최종 보고하고 #45의
    production whole-flow/security QA 입력을 고정한다.

## 리스크

- **첫 publish 비가역성**: 같은 name/version은 덮어쓸 수 없다. exact artifact와
  승인 전 publish를 차단하고 오류는 patch version으로 복구한다.
- **package name 선점**: 현재 404라도 publish 전 바뀔 수 있다. Gate B 직전에
  다시 확인하며 충돌 시 자동 rename하지 않는다.
- **private repository와 provenance 충돌**: private repository에서는 public
  package도 provenance가 생성되지 않는다. public 전환은 full-history scan과
  별도 승인 후에만 수행하고, 미승인 시 provenance 없음과 metadata 대안을
  명시한다.
- **최초 package와 staged/trusted bootstrap**: brand-new package는 staged
  publish를 사용할 수 없고 package settings의 trusted publisher도 아직
  구성할 수 없다. 최초 1회는 승인된 direct channel로 만들고 즉시 future
  trusted publisher/2FA policy로 전환한다.
- **credential 노출**: CI/local token, OTP 또는 recovery code가 shell history,
  Actions log와 report에 남을 수 있다. secret store/stdin·browser prompt만
  사용하고 값 출력 없이 폐기 여부만 확인한다.
- **package metadata의 private link**: repository를 private로 유지하면 npm
  사용자의 support/source 링크가 막힌다. public Site로 정렬하거나 필드를
  생략하고 실제보다 공개된 것처럼 주장하지 않는다.
- **published CLI의 실제 usage 전송**: fresh production smoke가 개인 집계
  데이터를 전송한다. Contract v1 field 범위와 cleanup을 별도 승인받고
  prompt/response/credential/session은 전송하지 않는다.
- **registry/CDN 전파 지연**: publish 직후 `npx`가 stale 404 또는 이전
  dist-tag를 볼 수 있다. bounded polling과 exact version 조회를 먼저 사용하며
  반복 publish하지 않는다.
- **dependency supply chain**: public package는
  `codex-usage-analyzer@^0.2.0`을 설치한다. exact resolved version/integrity와
  install tree를 검사하고 unattended 안내는 exact CLI version을 유지한다.
- **#43 작업 충돌**: main worktree의 과거 Cloud Run canonical 계획은 현
  architecture와 맞지 않는다. 해당 branch를 변경·merge하지 않고 #44
  분리 worktree만 사용한다.

## 승인 요청 사항

- Task #44의 범위, 6개 Stage, 문서 위치와 `0.1.0` 최초 publish 후보를
  승인해 달라.
- **권고안 A**를 기본 조사안으로 승인해 달라: full-history scan 통과 후
  repository public 전환 + GitHub Actions 최초 publish + provenance +
  성공 뒤 trusted publisher/token 폐기. repository public 전환 자체는 Gate A
  exact 결과를 다시 제시하기 전에는 실행하지 않는다.
- repository를 private로 유지하려면 **대안 B**로 명시해 달라. 이 경우
  interactive 2FA 최초 publish, provenance 없음과 public metadata 대안을
  구현계획서에 고정한다.
- 수행계획 승인에는 npm publish, repository visibility 변경, Git tag/release,
  npm access policy 변경, 실제 usage 전송과 remote data 삭제 승인이 포함되지
  않는다. 각 Gate에서 exact 값과 비가역성을 다시 승인받는다.

승인되면 `task_m100_44_impl.md`에서 단계별 파일, 검증 명령, Gate 입력과
커밋 메시지를 구체화한다.
