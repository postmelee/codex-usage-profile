# Task #137 수행계획서 — CLI 재인증·온보딩 개선의 npm 0.1.4 및 production 릴리스

GitHub Issue: [#137](https://github.com/postmelee/codex-usage-profile/issues/137)
마일스톤: M100

## 목적

Task #134에서 `devel`에 반영한 file credential 자동 재인증·재제출, 전역·명령별 help,
Profile 온보딩과 device approval 완료 링크 위계 개선을 immutable npm patch
`codex-usage-profile@0.1.4`와 canonical production Site에 같은 exact release source로
승격한다.

Local certification 뒤 checkpoint와 `devel → main` release PR로 exact `main` source를 먼저
고정하고, 그 commit을 stage5 owner-only 환경에서 검증한 뒤 npm tag와 production Sites saved
version의 provenance로 사용한다. production의 기존 public access와 durable data를 보존하면서 temporary application
maintenance, migration readiness와 비파괴 smoke를 분리된 승인 Gate로 수행한다.

## 배경

- PR #136은 Task #134 source와 최종 보고를 `devel`에 merge했으나 현재 `main`, public npm
  `0.1.3`과 production deployment에는 해당 변경이 없다.
- npm registry version은 immutable이므로 같은 `0.1.3`을 덮어쓰지 않고 `0.1.4` patch와 exact tag,
  trusted publisher의 staged publishing·maintainer 2FA가 필요하다.
- Task #108은 production과 stage5를 서로 다른 Site project·D1·R2·OAuth/secret·identity state로
  분리하고 Local → stage5 → production runbook을 `docs/sites-operations.md`에 고정했다.
- production은 public 운영 중이므로 candidate save, deployment, migration, environment와 smoke를
  하나의 원격 변경으로 간주하지 않는다. source·artifact 오류는 stage5에서 먼저 차단하고 production
  mutation은 별도 Gate에서만 실행한다.
- 현재 repository manifest는 production project와 logical `DB`, `PROFILE_MEDIA` binding을 가리키며,
  target registry는 production과 stage5의 project/origin을 분리한다. 이번 task는 이 topology를
  변경하지 않는다.
- migration source는 기존 1~6이며 Task #134는 backend/schema를 변경하지 않았다. 따라서 신규
  migration은 만들지 않고 두 Site에서 expected/applied `[1,2,3,4,5,6]` exact match를 확인한다.

## 설계 방향

### Exact release source와 version

- `0.1.4`는 Task #134 변경을 포함하는 최소 patch다. 기능 source는 다시 수정하지 않고 package manifest,
  lockfile, exact-version 사용자 예와 release 문서만 릴리스 경계에 맞춘다.
- package candidate, stage5 artifact, `main` release tree, npm tag와 production archive는 동일한 product
  tree를 사용해야 한다. 원격 결과 기록 때문에 후속 문서 commit이 생겨도 배포 product tree가 달라지지
  않았음을 path diff로 증명한다.
- npm tag는 exact `main` release commit에 한 번만 생성한다. workflow가 stage를 만든 뒤 사용자가 npm
  웹에서 version·provenance를 확인하고 2FA 승인하기 전에는 registry 게시 완료로 기록하지 않는다.

### Remote Gate와 승인 경계

- **Gate A — local candidate**: version·문서 source와 전체 local certification을 승인한다.
- **Gate B — source integration/main release**: local candidate PASS 뒤 checkpoint PR을 `devel`에
  merge하고, 별도 release PR로 exact tree를 `main`에 반영한다. 두 PR merge는 작업지시자가
  수행·승인하며 이 단계 자체는 npm·Sites 배포를 만들지 않는다.
- **Gate C — stage5 save/deploy**: exact main source의 target preflight 뒤 owner-only access를 유지하며
  저장·배포한다. environment maintenance와 protected migration은 별도 하위 승인으로 실행하고 즉시
  disabled·secret-absent baseline으로 복원한다.
- **Gate D — npm staged publish**: exact main tag push로 Node 20/22/24 검증과 stage를 만든다. npm 웹
  2FA는 작업지시자만 수행하며 승인 뒤 registry를 read-only 검증한다.
- **Gate E — production save/deploy**: public access는 바꾸지 않고 temporary application maintenance,
  deployment, protected readiness, maintenance 종료를 순서대로 수행한다. 각 상태를 확인하기 전 다음
  mutation을 하지 않는다.
- **Gate F — production smoke/handoff**: 공개 서비스의 비파괴 사용자 흐름, 로그·error contract,
  npm/production provenance와 rollback 후보를 기록한다.

### Sites와 데이터 보존

- `.openai/hosting.json`과 `.openai/hosting-targets.json`은 수정하지 않는다. target materializer와
  production artifact verifier가 project/origin/source mismatch를 거부해야 한다.
- stage5와 production 모두 신규 schema 변경은 없다. physical migration과 application
  `schema_migrations`가 exact `[1,2,3,4,5,6]`일 때만 readiness를 통과시킨다.
- production의 public access policy와 기존 owner/publication data는 보존한다. 배포 중 write는
  application maintenance로만 닫고, failure 시 maintenance를 유지한 채 이전 saved version과 exact
  environment baseline으로 원복한다.
- stage5 smoke는 synthetic 계정만 사용하고 production credential/data를 복제하지 않는다. disposal은
  이번 task에서 하지 않는다.

### npm과 production 적용 순서

- exact main 고정과 stage5 검증 전에는 tag·npm stage·production deploy를 하지 않는다.
- npm `0.1.4`와 production Site는 같은 main source를 사용한다. 공개 전환 충돌을 최소화하기 위해
  production saved version·rollback 준비를 확인한 뒤 npm stage를 만들고, npm 승인과 production
  deployment의 실제 순서는 구현계획서에서 유지보수 창·rollback 준비를 기준으로 고정한다.
- `latest`가 `0.1.4`를 가리키기 전후 모두 production default origin이 유효해야 한다. API contract
  변경이 없으므로 `0.1.3` client와 새 Site, `0.1.4` client와 직전 Site의 호환성을 local/stage5에서
  확인한다.

## 리스크

- **npm immutable version**: tag·stage·registry 중 하나가 생성된 뒤 같은 version을 재사용하지 않는다.
  upload 전 실패는 새 승인 계획, registry 게시 뒤 결함은 새 patch와 필요 시 deprecate로 처리한다.
- **npm 승인과 Site 배포 시차**: `latest`와 production source가 어긋나는 시간을 줄이되, API 호환성을
  먼저 검증하고 각 provider의 rollback 준비 없이 순서를 바꾸지 않는다.
- **cross-target 배포**: target role, project, origin, binding, exact source 중 하나라도 mismatch면
  archive save 전 중단한다.
- **public production write 경쟁**: access를 닫는 대신 temporary application maintenance를 사용하고,
  migration/readiness·maintenance 종료를 확인하기 전 공개 smoke를 하지 않는다.
- **durable data 손상**: data disposal·account deletion을 제외하고 migration은 기존 manifest의 pending
  version만 허용한다. drift는 임의 SQL로 보정하지 않고 maintenance 상태에서 보고한다.
- **Node 24 D1 test hang**: #135 범위와 분리하고 Task #134에서 검증한 Node 24 비-D1 + Node 22 D1
  분할로 전체 계약을 판정한다. release runner의 Node 20/22/24 package matrix는 별도로 통과해야 한다.
- **사람 2FA 의존성**: npm stage 생성 뒤 작업지시자의 npm 웹 승인이 필요하다. 승인 전에는 게시 완료나
  production handoff를 주장하지 않는다.
- **Sites public access 승인**: production은 이미 public이므로 access policy를 변경하지 않는다. Sites
  도구가 shared/public deployment에 별도 승인을 요구하면 resolved access를 제시하고 사용자 승인을
  받은 뒤에만 deploy한다.

## 승인 요청 사항

- npm package를 immutable `0.1.4` patch로 게시하고 `0.1.3`을 변경하지 않는 방향
- Local → checkpoint/main source 고정 → exact-main stage5 owner-only → npm stage → production patch release의 6 Stage
  순서와 각 remote mutation 전 별도 승인 Gate
- production public access와 durable data를 보존하고 temporary application maintenance만 사용하는 방향
- 신규 migration·data disposal·SNS 게시·Node 24 D1 수정·Cloud Run fallback을 제외하는 범위
- `docs/npm-release.md`를 공식 npm provenance 기록으로 사용하고 Sites 문서는 실제 contract가 달라지는
  행만 최소 보정하는 문서 위치 판단
- checkpoint PR과 `devel → main` release PR을 Task #137 한정 exact-main 승격 절차로 사용하는 방향

승인되면 `task_m100_137_impl.md`에서 Stage별 산출물, 검증 명령, commit과 remote Gate의 중단·원복
조건을 구체화한다.
