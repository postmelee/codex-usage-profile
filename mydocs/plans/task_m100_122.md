# Task #122 수행계획서 — Sites live D1 structured 계정 삭제 충돌 보정

GitHub Issue: [#122](https://github.com/postmelee/codex-usage-profile/issues/122)
마일스톤: M100

## 목적

Task #119에서 추가한 owner 삭제 operation·lease·bounded media 재개 계약이 실제
Stage5 D1의 `structured` 단계에서 반복 `maintenance_conflict`로 멈추는 원인을
provider-faithful 환경에서 재현하고 보정한다. 수정은 exact `main`으로 Stage5에 배포해
provider 차이와 안전 기준선을 확인한다. 기존 active operation의 live resume는 자격 증명을
transcript·명령행·process argument에 노출하지 않는 실행 경로가 먼저 필요하므로 #125로
이관하고, Task #108의 production 배포·migration·사용자 흐름 smoke를 차단하지 않는다.

raw D1/R2 직접 삭제나 guard 완화는 사용하지 않는다. 실패 단계는 운영자가 비밀 정보나
row payload 없이 구분할 수 있어야 하며, production project·data·access·environment는
끝까지 read-only baseline으로 유지한다.

## 배경

- Task #108 Stage 5 Gate E에서 exact `main`
  `6fec1182f9f0f6ae47cb168ab11b0965235050a0`의 Stage5 version 35와 D1 migration
  `1..6`을 검증한 뒤, 승인된 두 테스트 owner 삭제를 실행했다.
- `thechoicesinmylife`는 정상 완료됐지만 `postmelee`는 R2 revision 0, stable
  tombstone, private structured state까지 진행한 뒤 `structured` phase에서 충돌을
  반복했다. 전체 128회와 별도 8회 재개 모두 `delete_account_iteration_limit`으로
  끝나 단순 15초 client timeout이나 edge propagation만으로 설명되지 않는다.
- 현재 active operation은
  `maintenance_delete_20d40b9d433449a6a33ae02c56ca17e1`, phase `structured`,
  lease 없음, 최초 승인 object count 77을 유지한다. owner 관련 D1 row는 owner 1,
  OAuth state 22, session 22, login challenge 11, CLI token 8, latest usage 1,
  submitted device 7, rate limit 2, deletion operation 1이다.
- 최초 진단의 OAuth state 19는 Sites table viewer 첫 25행에서 target owner row만 센 값이었다.
  Gate 5A에서 다음 page의 기존 3행을 추가로 확인했으며 22행 모두 operation 생성 전부터
  존재한다. 따라서 live drift가 아니라 pagination 누락 보정이고, 최초 승인 object count 77과
  operation authority는 변경하지 않는다.
- 삭제 전 backup은 저장소 밖 mode `0600` 파일로 유지된다. `postmelee` backup의
  SHA-256은 `fc617cc42dbfa451c30288c74f10964a9eff49f7e2afd74547f176da215cf667`이며,
  삭제가 완료된 `thechoicesinmylife` backup도 그대로 보존한다.
- 실패 뒤 Stage5 maintenance는 비활성화됐고 owner-only access와 service normal을
  복구했다. production project
  `appgprj_6a83ecc3c4c08191bda7f14d7c26c974`는 version 2, environment revision 2의
  기존 baseline에서 변경되지 않았다.
- PR #120은 unit·Miniflare·real-workerd에서 timeout 이후 재개 계약을 검증했지만 live
  Stage5 D1 structured delete는 범위에서 제외했다. 현재 D1 adapter는 guard claim,
  dependent-row deletion, operation deletion, owner deletion과 claim cleanup을 하나의
  `batch()`에 넣고 provider 오류를 공통 conflict로 정규화하므로, 먼저 실제 실패 종류와
  transaction 경계를 재현 가능한 테스트로 고정해야 한다.

## 범위

### 포함

- live 실패와 동등한 다수 session·token·challenge·device·rate-limit 및 active
  `structured` operation fixture
- D1 `deleteOwner` guard, batch/transaction, foreign-key·cascade와 operation/lease
  상호작용의 원인 재현
- structured delete의 provider-compatible 원자성 보정과 최초 승인값·owner scope 보호
- Sites maintenance의 안전한 내부 오류 분류와 외부 응답 정보 경계
- operator CLI의 structured conflict 재조정, 반복 상한과 완료 reconciliation 보정
- unit, Miniflare, real-workerd 및 production artifact 검증
- source integration checkpoint, exact-`main` release provenance와 owner-only Stage5 배포
- 기존 Stage5 active operation의 불변 확인, maintenance 안전 종료와 #125 handoff
- Sites 운영 문서, production rollback 문서와 Task #108 handoff 기록 보정

### 제외

- raw D1/R2 직접 삭제, SQL console 수동 삭제 또는 guard를 우회하는 강제 삭제
- production data, access, environment, OAuth/secret 또는 application version 변경
- 최초 승인 digest/count, immutable ETag, R2-first, lease·atomicity 안전장치 완화
- 새 operation 생성이나 기존 active operation의 승인값 재작성
- Stage5 public 전환 또는 외부 SNS crawler 검증
- 공개 사용자 UX, 일반 submit/profile 기능과 npm package 변경
- backup에 포함되지 않는 session/token/OAuth transient state 복원
- owner-only 우회·maintenance 자격 증명의 안전한 전달 경로와 기존 operation live resume
  (#125 범위)

## 설계 방향

- **재현 우선**: 수정 전에 live row 분포와 phase를 반영한 fixture에서 같은 structured
  실패를 재현한다. Node mock에서만 통과하는 조건을 수용하지 않고 Miniflare 또는
  real-workerd D1 실행 경로까지 실패 전·후를 비교한다.
- **원인별 최소 보정**: batch statement, assertion claim, foreign-key/cascade,
  operation row 또는 provider 제한 중 실제 원인을 확인한 뒤 가장 작은 경계만 바꾼다.
  원인을 확인하기 전에 transaction을 분할하거나 안전 guard를 제거하지 않는다.
- **원자성과 순서 불변**: R2 revision 0과 non-public stable state를 다시 확인한 뒤에만
  structured delete를 시작한다. dependent rows, deletion operation과 owner의 최종 상태는
  하나의 원자적 성공/rollback 경계로 관찰돼야 하고 부분 structured 삭제를 남기지 않는다.
- **승인 authority 유지**: 기존 operation ID와 최초 승인 digest/count가 authority다.
  재개 중 plan 또는 scope가 달라지면 fail closed하며 새 operation으로 자동 대체하지 않는다.
- **안전한 관측 가능성**: service 내부에는 `phase`와 정규화된 failure class를 남기되,
  API·CLI에는 credential, SQL, row payload, nonce, provider 원문을 노출하지 않는다.
  retryable conflict와 terminal invariant violation을 구분해 무의미한 128회 반복을 막는다.
- **Task #108과 브랜치 분리**: 현재 열린 Task #108 worktree 파일을 Task #122 브랜치에서
  직접 덮어쓰지 않는다. Task #122 단계·최종 보고서에 exact handoff를 남기고, merge 뒤
  Task #108이 이를 기준으로 Gate E와 최종 보고를 이어가도록 한다.
- **exact-main 원격 Gate**: code fix가 `devel`에 integration checkpoint로 병합되고 별도
  `devel → main` release PR로 승격된 exact commit만 Stage5에 배포한다. Task #122 이슈는
  live 검증 전까지 닫지 않으며 checkpoint PR도 이슈를 close하지 않는다.
- **Stage5 mutation Gate**: source provenance, migration `1..6`, owner-only access,
  maintenance disabled baseline, backup checksum, operation ID·digest/count·phase와 production
  read-only baseline이 모두 일치할 때만 remote Gate를 연다. credential handoff가 secret을
  transcript·명령행·process argument에 남길 수 있으면 operation 요청 전에 중단하고
  maintenance를 닫는다. 안전한 live resume는 #125에서 별도 계획·승인으로 수행한다.
- **공개 비차단 경계**: #125는 폐기 가능한 Stage5 테스트 operation의 maintenance recovery
  후속 증적이다. #108의 exact-main production 배포, migration 6, 사용자 흐름 smoke와
  공개·마케팅 release gate는 #125와 독립적으로 진행한다.

## 잠정 단계

- **Stage 1 — live-equivalent 재현과 원인 고정**
  - high-cardinality structured operation fixture와 수정 전 실패 회귀를 추가한다.
  - D1 provider 경로에서 정확한 실패 statement·constraint class와 transaction 결과를
    민감 정보 없이 식별하고 장애 분석 문서에 고정한다.
- **Stage 2 — D1 원자 삭제와 Sites 오류 경계 보정**
  - 확인된 원인에 대한 최소 D1 delete contract를 구현한다.
  - R2-first, 승인 authority, atomic rollback과 safe service error taxonomy를 검증한다.
- **Stage 3 — CLI reconciliation과 통합 회귀·운영 문서**
  - retryable/terminal structured failure의 반복·중단·완료 reconciliation을 보정한다.
  - unit·Miniflare·real-workerd·artifact 전체 회귀와 공식 운영 문서를 완성한다.
- **Stage 4 — source integration checkpoint와 exact-main release**
  - Task #122 source PR을 이슈 미종료 상태로 `devel`에 병합하고 exact tree를 검증한다.
  - 별도 release PR로 `main`에 승격한 뒤 Stage5 candidate artifact와 provenance를 고정한다.
- **Stage 5 — exact-main Stage5 배포·안전 종료와 Task #108/#125 handoff**
  - 명시적 원격 Gate 승인 뒤 exact-main을 owner-only Stage5에 배포하고 기존 operation의
    authority·phase·lease·R2 0 상태를 다시 확인한다.

## 리스크

- **provider 차이 재현 실패**: SQLite mock 통과만으로 live 원인을 확정할 수 없다.
  Miniflare·real-workerd D1 경로와 실제 statement class까지 확인하지 못하면 Stage 2로
  넘어가지 않는다.
- **transaction 분할 유혹**: live batch 오류를 피하려고 delete를 여러 요청으로 나누면
  structured partial state가 생길 수 있다. 원자 성공/rollback을 수용 기준으로 유지한다.
- **기존 operation 손상**: operation row를 먼저 지우거나 승인값을 갱신하면 audit와 재개
  authority를 잃는다. 동일 operation 불변 확인을 모든 live mutation 전후에 수행한다.
- **Task #108 병렬 worktree 충돌**: 같은 내부 문서를 양쪽 branch에서 수정하면 merge
  충돌과 증적 불일치가 생긴다. Task #122는 자체 보고서에 handoff를 남기고 Task #108
  파일은 merge 뒤 별도로 동기화한다.
- **exact-main 필요성**: task source가 merge되기 전에는 live fix를 exact `main`으로
  검증할 수 없다. issue를 닫지 않는 integration checkpoint와 release PR을 승인 Gate로
  분리한다.
- **원격 destructive mutation**: 기존 승인 대상이라도 live state가 달라질 수 있다.
  exact target·backup·operation·baseline이 하나라도 다르면 실행하지 않고 재승인을 받는다.
- **credential 전달 노출**: owner-only 우회와 maintenance token을 transcript·명령행·process
  argument로 전달하지 않는다. 안전한 handoff가 없으면 Stage5를 닫고 #125로 이관한다.

## 승인 요청 사항

- 5개 Stage와 `재현 → D1/Sites 보정 → CLI·문서 → integration/release → Stage5 재개`
  순서를 승인한다.
- 원자성, R2-first, 동일 operation·최초 승인값 불변과 safe error boundary를 필수
  설계 기준으로 승인한다.
- 공식 문서는 기존 `docs/sites-operations.md`, `docs/production-hosting.md`만 수정하고,
  특정 incident 증적은 `mydocs/troubleshootings/`에 새 문서로 분리한다.
- Task #108 active worktree 문서는 직접 수정하지 않고 Task #122 merge 뒤 handoff를
  반영하는 충돌 회피 방식을 승인한다.
- Stage 4의 issue 미종료 integration checkpoint와 exact-main release 흐름을 승인한다.
- Stage5 실제 mutation은 Stage 5 진입 승인과 exact preflight 일치 뒤에만 수행하며,
  production은 전체 task 동안 read-only로 둔다.

승인되면 `task_m100_122_impl.md`에서 재현 fixture, atomic boundary, safe error taxonomy,
checkpoint/release와 Stage5 Gate별 산출물·검증·커밋 메시지를 구체화한다.
