# Task #119 수행계획서

GitHub Issue: [#119](https://github.com/postmelee/codex-usage-profile/issues/119)
마일스톤: M100

## 목적

Sites maintenance 계정 삭제가 많은 R2 revision을 순차 처리하다 요청 제한을 넘더라도 안전하게 재개되어 최종 완료되도록 보강한다. 삭제 진행 중 publication은 tombstone, 구조화 데이터는 private 상태를 유지하고, 동일 owner에 대한 중복 실행은 지속 상태를 기준으로 차단하거나 같은 작업으로 직렬 재개한다.

기존 exact owner 확인, content digest·object count 확인, stable publication 및 immutable ETag 보호는 완화하지 않는다. 운영자는 부분 진행 상태와 다음 재개 동작을 비밀 데이터 없이 확인할 수 있어야 한다.

## 배경

Task #108 Stage5 Gate E에서 95개 객체를 가진 테스트 계정 삭제를 실행했다. 첫 요청은 publication tombstone과 owner quiesce 후 R2 revision 18개를 삭제했지만 클라이언트 요청 제한을 넘겼다. 잔여 77개 계획은 유지됐고 후속 실행은 `maintenance_conflict`로 중단돼, 현재 단일 요청 기반 삭제가 timeout 이후 완결 가능한 운영 계약을 제공하지 못함을 확인했다.

현재 서비스는 `tombstone → quiesce → 모든 R2 revision 순차 삭제 → D1 owner 삭제`를 한 요청에서 수행한다. R2 삭제는 revision마다 stable state, storage ETag, 삭제 결과를 재검사하므로 안전하지만 객체 수에 비례해 요청 시간이 증가한다. CLI 또한 완료 응답을 받기 전에 연결이 끊기면 서버의 실제 진행 상태를 복원할 수 없다.

## 설계 방향

- **지속 operation authority**: D1 migration으로 owner별 삭제 operation과 phase, 원래 승인 digest/count, lease 만료 및 갱신 시각을 보존한다. 요청 timeout이나 worker 교체 뒤에도 다음 호출이 같은 작업을 식별한다.
- **bounded media batch**: R2 revision 삭제는 한 요청에서 제한된 수만 처리한다. 각 batch 시작 전 실제 manifest와 stable tombstone을 다시 읽고 기존 storage ETag 검사를 유지한다.
- **실제 상태 기반 멱등성**: checkpoint 전에 연결이 끊겨도 이미 사라진 revision은 다음 manifest에서 제외한다. R2가 완전히 비어야 D1 owner 삭제 단계로 전이한다.
- **중복 실행 통제**: owner별 lease를 원자적으로 획득·갱신하고 다른 operation은 retryable conflict로 거부한다. 만료된 lease는 같은 operation이 회수할 수 있어야 한다.
- **운영자 가시성**: maintenance 결과에는 `in_progress` 또는 `completed`, phase, 이번 요청 처리량, 잔여 객체 수, 재개 식별자처럼 민감하지 않은 진행 정보만 노출한다.
- **CLI 직렬 재개**: CLI는 한 번에 한 요청만 보내고 `in_progress` 결과를 받아 같은 operation을 반복 호출한다. 네트워크 결과가 불확정하면 plan/status를 먼저 확인하고 새 삭제를 겹쳐 보내지 않는다.
- **호환성**: 기존 plan/export/restore/retention 계약과 backup schema는 유지한다. 기존 단건 fixture는 한 호출에서 `completed`가 되어 현재 운영 흐름과 호환한다.

### 통합 검증

- 대량 R2 fixture의 중간 timeout 후 같은 operation 재개가 모든 media와 D1 owner를 정확히 한 번 제거한다.
- 중복 요청은 owner lease로 차단되거나 동일 operation으로 직렬화되며 데이터 손상을 만들지 않는다.
- stable publication이 다시 생기거나 immutable revision ETag가 달라지면 삭제하지 않고 conflict로 닫힌다.
- R2 revision이 남아 있는 동안 D1 owner 삭제가 실행되지 않는다.
- CLI는 `in_progress`를 직렬 반복하고 불확정 네트워크 결과 후 상태 확인 없이 중복 삭제를 시작하지 않는다.
- 기존 plan/export/restore/retention, backup schema, 단건 삭제 테스트가 회귀 없이 통과한다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **D1 schema 확장**: 새 migration이 기존 1~5 순서와 production readiness 계약을 변경한다. manifest·migration contract·Sites packaging 검증을 함께 갱신한다.
- **lease 고착**: worker 중단 시 작업이 영구 잠길 수 있다. 명시적 TTL과 동일 operation 회수 규칙을 둔다.
- **R2/D1 비원자성**: 두 저장소를 하나의 transaction으로 묶을 수 없다. 실제 R2 manifest를 매 batch 재계획하고 D1 삭제를 마지막 단계로 제한한다.
- **호환성**: 응답 필드 확장이 기존 CLI/운영 스크립트를 깨뜨릴 수 있다. 기존 summary 필드를 유지하고 새 진행 필드는 추가 계약으로 정규화한다.
- **Stage5 재현과 코드 수정 분리**: 이 task에서는 live 데이터에 손대지 않는다. merge·배포 후 Task #108 Gate E에서 별도로 재검증한다.

## 승인 요청 사항

- D1 지속 operation/lease와 bounded R2 batch를 기본 복구 구조로 채택한다.
- 공식 운영 문서는 기존 `docs/sites-operations.md`, `docs/production-hosting.md`만 필요한 범위에서 수정한다.
- Stage5 실제 잔여 삭제·배포는 제외하고 Task #108 후속 검증으로 남긴다.
- 승인되면 `task_m100_119_impl.md`에서 schema, phase, 응답 필드, batch 크기, TTL, 단계별 커밋과 검증 명령을 구체화한다.
