# Task M100 #57 수행계획서

GitHub Issue: [#57](https://github.com/postmelee/codex-usage-profile/issues/57)
마일스톤: M100

## 목적

`codex-usage-profile@0.1.0` 사용자가 PATH에 별도 `codex` 명령을 설치하지
않았더라도 macOS의 표준 ChatGPT/Codex 앱 번들에 포함된 호환 실행 파일을
자동으로 찾아 Account Usage Contract v1을 제출할 수 있게 한다.

이미 이 탐색 경계를 구현해 공개한 `codex-usage-analyzer@0.4.1`을 exact
dependency로 채택하고, 기존 CLI·전송·credential 계약이 넓어지지 않았음을
검증한 뒤 `codex-usage-profile@0.1.1` provenance patch release를 게시한다.

## 배경

현재 profile CLI는 `codex-usage-analyzer@0.2.0`을 exact dependency로
사용한다. 이 버전은 `codex app-server`를 PATH에서만 실행하므로 ChatGPT
desktop 앱에 호환 Codex 실행 파일이 있어도 일반 shell PATH에 노출되지
않으면 `CODEX_NOT_FOUND`로 실패한다. 실제 production 사용자 검증에서는
다음 PATH prefix를 임시로 붙였을 때 submit이 성공했다.

```bash
PATH="/Applications/ChatGPT.app/Contents/Resources:$PATH" \
npx codex-usage-profile@latest submit
```

공개된 `codex-usage-analyzer@0.4.1`은 PATH의 `codex`를 우선하고, macOS의
system/user Applications 아래 ChatGPT/Codex 앱 번들을 정해진 후보로만
탐색한다. npm registry의 exact version과 integrity도 확인됐다. 따라서
profile 저장소가 동일 탐색을 다시 구현하지 않고 upstream analyzer의
검증된 책임을 채택하는 것이 package 경계와 최소 변경 원칙에 맞다.

관련 기준은 Issue #42의 CLI submit 계약, #44의 npm provenance 운영,
#45의 production 전체 흐름 검증과 `docs/npm-release.md`의 immutable
version·trusted publisher 절차다.

## 범위

### 포함

- `codex-usage-analyzer` exact dependency를 `0.2.0`에서 `0.4.1`로 갱신
- profile CLI package/SDK version을 `0.1.1`로 올리고 lockfile을 registry
  tarball URL·integrity까지 exact 고정
- Account Usage Contract v1, `readAccountUsage()`, error mapping과
  profile CLI public exports의 하위 호환성 검증
- PATH 우선, 표준 macOS ChatGPT/Codex 앱 번들 fallback, 후보 부재
  fail-close를 downstream 관점에서 검증
- release verifier, local tarball smoke와 관련 테스트의 expected
  package/analyzer contract 갱신
- root/package README와 CLI/analyzer/npm release 공식 문서의 version,
  requirement, troubleshooting과 후속 patch 운영 기록 갱신
- public release scanner, package candidate, Node 20/22/24 CI와 local
  preflight 통과
- exact final commit과 `codex-usage-profile-v0.1.1` tag를 별도 Gate에서
  승인받아 trusted publisher staged publish 실행
- npm 2FA 승인 후 public version, `latest`, integrity, provenance,
  dependency tree와 실제 PATH-prefix 없는 production submit 검증

### 제외

- `codex-usage-analyzer` 저장소 소스 수정 또는 새 analyzer version 게시
- 비표준 앱 설치 위치를 찾기 위한 전체 disk scan, shell profile 수정,
  symlink 생성 또는 사용자의 PATH 영구 변경
- Account Usage Contract v1 field, submit payload, credential 저장소,
  service origin, backend/Sites API 변경
- #55 랜딩 카드 skeleton과 #38 Share Studio UI 변경
- 기존 immutable `codex-usage-profile@0.1.0` 또는 canonical/recovery tag
  이동·덮어쓰기·unpublish
- npm direct publish 또는 장기 npm token 재도입

## 설계 방향

- 실행 파일 탐색은 local usage source를 소유하는 analyzer 책임으로
  유지한다. profile CLI에는 macOS 앱 경로를 중복 구현하지 않는다.
- analyzer dependency는 `0.4.1` exact version으로 고정한다. range를
  사용하지 않고 package-lock의 registry URL과 SHA-512 integrity까지
  verifier가 검사하게 해 공급망 범위를 유지한다.
- upstream resolver의 우선순위인 PATH → system Applications →
  user Applications를 그대로 채택한다. 정해진 후보가 없으면
  `CODEX_NOT_FOUND`로 종료하며 임의 실행 파일을 찾거나 실행하지 않는다.
- submit 전송 document와 device header, service token 경계는 변경하지
  않는다. 신규 검증은 실행 파일 선택과 package dependency 호환성에
  한정한다.
- patch version은 `0.1.1`로 고정하고 기존 trusted publisher,
  `npm-publish` environment와 `npm stage publish --access public` 경로를
  재사용한다. publish workflow 자체의 권한이나 인증 경계는 넓히지 않는다.
- tag는 package version과 정확히 일치하는 annotated tag 한 개만 만들고
  이동하지 않는다. stage 생성 전 exact commit·tag·candidate 결과를
  Gate B로 다시 승인받는다.
- npm stage가 생성되면 작업지시자가 npm 웹에서 package/provenance를
  확인하고 2FA 승인한다. 승인 전에는 public version이 생성됐다고
  간주하지 않는다.

## 리스크

- **upstream minor-version 호환성**: analyzer `0.2.0`에서 `0.4.1` 사이의
  experimental surface가 늘었더라도 profile이 사용하는
  `readAccountUsage()`와 Account Usage Contract v1만 대상으로 exact
  compatibility test를 수행한다.
- **앱 번들 내부 경로 안정성**: 표준 후보는 analyzer가 명시적으로
  지원하는 경로만 사용한다. 비표준 경로 탐색이나 shell profile 수정으로
  범위를 넓히지 않고 실패 시 공식 CLI 설치 안내를 유지한다.
- **잘못된 실행 파일 선택**: PATH를 최우선으로 유지하고 후보 파일의
  executable 여부를 확인하는 upstream 경계를 검증한다. 전체 disk scan과
  임의 이름 실행은 금지한다.
- **공급망 변경**: exact version, registry URL, integrity, MIT license와
  Node engine을 release verifier에서 검사하고 lifecycle script를 계속
  거부한다.
- **immutable release 실패**: tag와 version은 재사용하거나 이동하지
  않는다. upload 전 실패는 원인을 수정한 새 승인 경로로, registry 생성
  후 결함은 새 patch version으로 복구한다.
- **공개 stage 오승인**: tag push와 npm 2FA는 분리하고, staged package의
  exact commit·provenance·dependency를 확인하기 전 2FA 승인하지 않는다.
- **production usage 중복**: 동일 usage 제출은 backend idempotency를
  사용하며 smoke 전후 status를 비교한다. prompt/response나 credential은
  출력·보고에 기록하지 않는다.
- **#55 순서 충돌**: #57은 CLI/package/docs만 변경하고 UI를 건드리지
  않는다. #57 release와 merge cleanup 후 #55 worktree를 시작한다.

## 승인 요청 사항

- analyzer executable lookup을 profile에 중복 구현하지 않고 공개
  `codex-usage-analyzer@0.4.1` exact dependency로 채택하는 방향
- patch version을 `codex-usage-profile@0.1.1`로 고정하고 기존
  trusted publisher staged publishing 경로를 재사용하는 방향
- 공식 사용자·통합·release 문서를 기존 root/package README와 `docs/`
  위치에서 갱신하는 문서 위치 판단
- 4개 Stage와 Stage별 승인 게이트, Stage 3 종료 후 exact candidate
  commit/tag/publish를 Gate B에서 다시 승인받는 절차
- Sites/backend/UI와 #55를 이번 task에서 제외하는 범위

승인되면 `task_m100_57_impl.md`에서 단계별 산출물, 검증 명령, 커밋
메시지와 Gate B exact 값을 구체화한다.
