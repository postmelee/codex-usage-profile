# Task #113 수행계획서

GitHub Issue: [#113](https://github.com/postmelee/codex-usage-profile/issues/113)
마일스톤: M100

## 목적

GitHub Community Standards에서 누락된 Code of conduct, Contributing, Issue templates를 보완해 기본 브랜치 반영 후 Community Profile 100%를 달성한다. 코드, 문서, 디자인 피드백과 아이디어를 기여로 인정하고 Discussion → Issue → Pull Request로 이어지는 공개 참여 경로를 영문으로 제공한다.

보안 취약점은 공개 Issue 대신 GitHub Private Vulnerability Reporting으로 접수하도록 `SECURITY.md`와 저장소 설정을 함께 구성한다. 행동강령 위반 신고는 취약점 신고와 분리하고, 작업지시자가 승인한 비공개 연락 수단만 공개한다.

## 배경

2026-08-22 live 조회 기준 Community Profile health는 57%이며 Description, README, License, Pull request template만 인식된다. `.github/ISSUE_TEMPLATE/task.yml`은 기본 브랜치에 있고 공식 issue form 필수 key인 `name`과 `description`도 가지지만 Community Profile 지표의 Issue templates에는 반영되지 않는다. 이 form은 내부 Hyper-Waterfall 타스크용이므로 외부 사용자를 위한 bug report와 feature request form을 별도로 제공하는 것이 지표 복구와 기여 경험 양쪽에 적합하다.

Discussions는 활성화되어 있지만 게시글이 없고 Announcements, General, Ideas, Polls, Q&A, Show and tell 기본 카테고리만 존재한다. GitHub Private Vulnerability Reporting은 비활성화되어 있다. 루트 README는 영문 사용자 문서이지만 기여 진입점이 없고, 현재 `.github/pull_request_template.md`는 한국어 maintainer 절차를 위한 내부 task 템플릿이다.

관련 기존 작업 중 [#90](https://github.com/postmelee/codex-usage-profile/issues/90)은 Gate C 이후 release 문서와 repository metadata 정합화를 담당한다. 이번 task는 README의 독립된 Contributing 섹션과 GitHub 커뮤니티 파일·설정만 다루며 #90의 배포 상태, badge, canonical URL과 metadata 범위는 변경하지 않는다.

공식 기준은 다음 문서를 따른다.

- [About community profiles for public repositories](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)
- [Adding a code of conduct to your project](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-a-code-of-conduct-to-your-project)
- [Setting guidelines for repository contributors](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)
- [Configuring issue templates for your repository](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository)
- [Configuring private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository)

## 범위

### 포함

- GitHub가 지원하는 Contributor Covenant template을 기반으로 루트 `CODE_OF_CONDUCT.md`를 추가한다.
- 기여 유형별 Discussion, Issue, Pull Request 경로와 로컬 개발·검증 방법을 설명하는 영문 `CONTRIBUTING.md`를 추가한다.
- 최신 공개 release만 지원하는 원칙과 GitHub private security advisory 신고 절차를 설명하는 영문 `SECURITY.md`를 추가한다.
- GitHub Private Vulnerability Reporting을 활성화하고 live API로 상태를 검증한다.
- README의 `Development` 앞에 짧은 영문 `Contributing` 섹션을 추가한다.
- 외부 사용자용 `bug_report.yml`, `feature_request.yml`, `config.yml`을 `.github/ISSUE_TEMPLATE/`에 추가한다.
- 기존 `.github/ISSUE_TEMPLATE/task.yml`의 구조와 task-register 입력 계약은 유지하면서 maintainer 전용임을 이름과 설명에서 명확히 한다.
- 내부 Hyper-Waterfall 기본 PR 템플릿은 유지하고 `.github/PULL_REQUEST_TEMPLATE/external-contribution.md`를 별도로 추가한다.
- CONTRIBUTING에서 외부 기여 템플릿 사용 경로와 `devel` 대상 PR 원칙을 안내한다.
- 다음 Discussion을 승인된 영문 본문으로 게시한다.
  - Announcements: `Welcome to Codex Usage Profile Discussions`
  - Ideas: `Share Your Profile Card Customization Ideas`
  - Show and tell: `Show Us Your Codex Usage Profile`
- Welcome과 customization 글을 고정하고, 생성된 Discussion URL을 README와 CONTRIBUTING의 진실 원천 링크로 사용한다.
- 기본 브랜치 merge 전에는 로컬 파일 구조·YAML·링크와 remote 설정을 검증하고, merge 후 Community Profile 100%와 GitHub 렌더링을 live 검증한다.

### 제외

- profile card customization 기능, preset, theme 또는 UI 구현
- 제품 API, runtime, 배포, storage, CLI와 npm package 변경
- #90의 release 문구, badge, canonical production URL, repository description/homepage 변경
- Dependabot, secret scanning, push protection 등 Private Vulnerability Reporting 외 GitHub security 설정 변경
- Discussion category 추가·삭제·이름 변경과 Poll 게시
- 외부 SNS 게시와 마케팅 캠페인
- npm release, GitHub Release/tag, default branch와 branch protection 변경
- 이번 task에서 실제 취약점 또는 행동강령 사건을 처리하는 운영

## 설계 방향

- 공개 기여 흐름은 `초기 아이디어·질문 → Discussions`, `재현 가능한 bug·합의된 feature → Issues`, `구현·문서 변경 → devel 대상 Pull Request`로 구분한다.
- Discussions의 Ideas는 자유로운 customization 제안을 받고, feature request form은 구현 범위와 수용 조건이 구체적인 제안을 받도록 문구를 분리한다.
- Issue template chooser는 blank issue를 비활성화하고 Q&A, customization ideas, private security reporting의 contact link를 제공한다.
- 기존 `task.yml`의 body field와 내부 task workflow는 변경하지 않고 top-level name/description만 maintainer 전용으로 명확히 한다.
- 기존 `.github/pull_request_template.md`는 task-final-report와 내부 매뉴얼이 의존하므로 수정하지 않는다. 외부 기여자는 별도 영문 템플릿을 사용하게 해 내부·외부 workflow를 분리한다.
- `CODE_OF_CONDUCT.md`는 GitHub `codes_of_conduct/contributor_covenant`가 제공하는 지원 template 본문을 기준으로 하며, placeholder를 승인된 비공개 행동강령 신고 수단으로 교체한다. Private Vulnerability Reporting은 행동강령 신고 채널로 재사용하지 않는다.
- `SECURITY.md`는 공개 Issue 금지, private advisory 제출 URL, 필요한 재현·영향 정보, 공개 시점 조율 원칙을 설명하되 응답 시간이나 수정 기한을 보장하지 않는다.
- Discussion 생성과 pinning, PVR 활성화는 재실행 전에 현재 상태·제목·URL을 조회해 중복 mutation을 막는다.
- GitHub Community Profile은 default branch만 평가하므로 PR 전에는 100%를 주장하지 않는다. merge 이후 live API와 Community Standards 화면 확인을 최종 수용 gate로 둔다.
- 모든 공개 문서는 영문으로 작성하고, 내부 계획·보고 문서는 저장소 Hyper-Waterfall locale인 한국어를 유지한다.

## 잠정 단계

- **Stage 1 — Discussion과 private security entrypoint 구축**
  - 기존 Discussion·PVR 상태를 재확인하고 세 게시글을 생성·검증한다.
  - Welcome과 customization discussion을 고정하고 영구 URL을 확보한다.
  - Private Vulnerability Reporting을 활성화하고 API로 검증한다.
- **Stage 2 — 공개 커뮤니티 정책과 README 기여 경로 작성**
  - `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`를 추가한다.
  - README에 exact Discussion URL과 기여 경로를 연결한다.
  - GitHub 지원 template 일치, 영문 품질, 비공개 연락처와 보안 신고 경계를 검증한다.
- **Stage 3 — 외부 Issue·Pull Request intake 정비**
  - bug/feature issue form과 chooser config를 추가한다.
  - maintainer task form을 명확히 하고 별도 영문 external contribution PR template을 추가한다.
  - YAML schema, 링크, 내부 Hyper-Waterfall workflow 비회귀를 검증한다.
- **Stage 4 — 통합 검증과 merge 후 live gate 준비**
  - 전체 Markdown·YAML·링크·개인정보 노출과 GitHub remote 상태를 통합 검증한다.
  - PR 전에는 default branch 미반영 한계를 명시하고, merge 후 Community Profile 100%와 GitHub UI 렌더링을 확인할 exact checklist를 최종 보고에 남긴다.

## 검증 계획

### 단계별 검증

- Stage 1
  - GraphQL로 Discussion 제목, 카테고리, URL, 고정 상태를 조회한다.
  - `gh api repos/postmelee/codex-usage-profile/private-vulnerability-reporting`이 `enabled: true`를 반환하는지 확인한다.
  - 같은 제목의 Discussion이 중복 생성되지 않았는지 확인한다.
- Stage 2
  - GitHub 지원 Contributor Covenant template과 `CODE_OF_CONDUCT.md` 구조를 비교한다.
  - `rg`로 placeholder, 공개 취약점 신고 유도, 승인되지 않은 연락처가 없는지 확인한다.
  - README, CONTRIBUTING, SECURITY의 상대·절대 링크 대상을 검사한다.
  - `git diff --check`를 실행한다.
- Stage 3
  - issue form YAML을 parser로 읽고 top-level `name`, `description`, `body`와 필수 validation을 검사한다.
  - `config.yml` contact link가 Q&A, Ideas, private advisory 경로를 가리키는지 확인한다.
  - 기존 `task.yml` body field id와 내부 PR template이 유지되는지 diff로 확인한다.
  - `git diff --check`를 실행한다.
- Stage 4
  - `rg --files -uu`와 링크 검사로 모든 community 파일 위치를 감사한다.
  - 공개 문서의 영문 표현, 개인정보와 secret 노출, 지원 범위 표현을 수동 검토한다.
  - `gh api`와 GraphQL로 PVR·Discussion remote 상태를 재검증한다.
  - `npm run scan:public-release`가 공개 파일 정책을 통과하는지 확인한다.
  - `git diff --check`를 실행한다.

- 보안 취약점 신고와 행동강령 신고의 private channel이 분리되어 있다.
- 기존 maintainer task issue form과 Hyper-Waterfall PR workflow가 유지된다.
- PVR은 live GitHub 설정에서 활성화되어 있고 Discussion 3건과 pin 2건이 존재한다.
- PR merge 후 `gh api repos/postmelee/codex-usage-profile/community/profile`의 `health_percentage`가 100이고 code of conduct, contributing, issue template이 non-null이다.
- PR merge 후 Community Standards, Issue chooser, Security policy와 README rendering을 GitHub UI에서 확인한다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **행동강령 신고 연락처 미확정**: Contributor Covenant는 private enforcement contact가 필요하다. 작업지시자가 공개를 승인한 전용 이메일 또는 동등한 비공개 채널이 확정되기 전에는 Stage 2를 완료하지 않는다.
- **default branch 반영 시차**: Community Profile은 task branch를 평가하지 않으므로 100% live 검증은 merge 후에만 가능하다. PR 전에는 공식 파일 조건과 구조를 검증하고 merge 후 exact API/UI gate를 수행한다.
- **GitHub 지표 cache 또는 인식 지연**: 유효한 issue form을 추가한 뒤에도 score 갱신이 지연될 수 있다. 파일 경로·schema와 default branch 반영을 확인한 뒤 재조회하고, 지연 자체를 성공으로 오인하지 않는다.
- **원격 mutation 중복**: Discussion 생성과 pinning은 Git commit으로 되돌릴 수 없다. mutation 전 제목·카테고리·현재 pin을 조회하고 생성된 node ID와 URL을 단계 보고서에 남긴다.
- **보안 신고 경로 혼동**: PVR은 취약점 전용이며 행동강령 신고에 사용하지 않는다. README, CONTRIBUTING, SECURITY와 CODE_OF_CONDUCT에서 역할을 교차 검토한다.
- **내부 workflow 회귀**: default PR template과 `task.yml` body를 변경하면 Hyper-Waterfall 절차가 깨질 수 있다. 별도 external PR template을 사용하고 `task.yml`은 top-level 안내만 최소 수정한다.
- **#90과 README 충돌**: `devel` 최신화와 #90 상태를 단계 시작 전에 재확인하고 이번 diff는 독립된 Contributing 섹션으로 제한한다.
- **개인정보 공개**: 로컬 Git 설정이나 계정 이메일을 자동 채택하지 않는다. 작업지시자가 명시적으로 승인한 연락처만 CODE_OF_CONDUCT에 기록한다.

## 승인 요청 사항

- 4개 Stage 분할과 Discussion → Issue → PR routing을 승인한다.
- 루트에 `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`를 두고 GitHub template은 `.github/`에 두는 문서 위치 판단을 승인한다.
- 기존 내부 PR template은 유지하고 별도 영문 external contribution template을 추가하는 호환성 방향을 승인한다.
- blank issue를 비활성화하고 Questions·Ideas·Security를 각각 Q&A Discussion, customization Discussion, Private Vulnerability Reporting으로 안내하는 chooser 정책을 승인한다.
