# Task M100 #15 수행계획서

GitHub Issue: [#15](https://github.com/postmelee/codex-usage-profile/issues/15)
마일스톤: M100

## 목적

로그인 사용자가 Settings 화면에서 CLI submit용 API token과 submit device를 관리할 수 있게 한다. token은 settings에서 직접 생성하거나 device-code login으로 발급된 것을 같은 목록에서 확인하고 revoke할 수 있어야 한다. device는 submit한 로컬 머신을 구분하는 계정 관리 데이터로 다루며, 사용자는 표시 이름을 변경할 수 있어야 한다.

이 작업은 analyzer의 사용량 추출 정확도와 분리한다. analyzer snapshot은 사용량 값의 원천이고, token/device는 웹 서비스의 GitHub 계정, session, submit 인증, submit 출처 관리 계층이다.

## 배경

#14로 `/settings` shell과 계정 overview가 들어왔고, #17로 device-code login API와 raw CLI token 1회 반환 흐름이 들어왔다. #15는 이 두 선행 작업 위에 settings 관리 화면을 확장한다.

비교 대상으로 검토한 toxscale 방식은 API token을 settings와 CLI login 양쪽에서 발급하고, raw token은 생성 직후 한 번만 보여주며, 서버에는 digest와 metadata만 남긴다. device는 분석 결과 자체가 아니라 submit payload의 device id/name을 기준으로 등록되는 submit 출처이며, settings에서는 목록 표시와 rename을 담당한다. 이 구조는 현재 프로젝트에도 동일한 UX로 적용할 수 있지만, Next.js/Drizzle/Postgres 구조를 그대로 복사하지 않고 기존 Node HTTP handler, memory/durable store, React UI 패턴에 맞춰 구현한다.

## 설계 방향

- token 관리는 기존 `createCliTokenService`와 store의 digest 저장 정책을 유지한다.
- settings token API는 browser session cookie 기반으로만 동작한다. CLI bearer token만으로 token 생성/폐기 같은 계정 관리 권한을 얻지 못하게 한다.
- token 생성 응답에서만 raw token을 반환하고, list 응답은 `id`, `label`, `scopes`, `createdAt`, `expiresAt`, `revokedAt`, `lastUsedAt`, `source` 계열 metadata만 반환한다.
- revoke는 hard delete가 아니라 기존 `revokedAt` soft revoke 정책을 유지한다.
- token list는 active token을 기본 표시하되, 이번 task에서 revoked token 표시가 필요하면 UI에서 revoked 상태를 비활성으로 표현한다.
- device model은 analyzer snapshot 내부 field가 아니라 submit wrapper/service metadata로 둔다. 최소 필드는 `id`, `ownerId`, `deviceKey`, `displayName`, `createdAt`, `updatedAt`, `lastSubmittedAt`이다.
- submit payload는 optional `device: { id, name }` 형태를 허용한다. 없는 경우 legacy/default device로 처리해 기존 submit contract를 깨지 않는다.
- device rename은 session owner와 device owner가 일치할 때만 허용한다. cross-user 접근은 존재 여부를 누설하지 않도록 not found 계열로 처리한다.
- Settings UI는 #14의 `ProfileShell`, `SettingsPage`, account state contract를 재사용한다. 별도 디자인 시스템을 만들지 않는다.
- toxscale과 같은 섹션 구조를 따르되, 현재 제품의 어두운 Codex profile UI 톤과 기존 CSS token에 맞춘다.

- **Stage 1 — token settings API**
  - token list/create/revoke route와 store/service method를 추가한다.
  - raw token 1회 반환, digest 미노출, session-only 관리 권한을 테스트한다.

  - submitted device store/service, submit metadata 저장, list/rename route를 추가한다.
  - device name validation과 owner authorization을 테스트한다.
- **Stage 3 — Settings API Tokens UI**
  - settings token create/list/revoke UI를 구현한다.
  - one-time token reveal/copy UX와 error/loading 상태를 확인한다.
- **Stage 4 — Settings Devices UI**
  - device empty/list/rename UI를 구현한다.
  - responsive layout과 keyboard save/cancel 동작을 확인한다.
- **Stage 5 — integration hardening**
  - 전체 테스트, build, security regression, browser QA를 수행하고 최종 보고서를 작성한다.

## 리스크

- **범위 확장**: CLI submit 전체 구현은 #5 범위로 남긴다. 이번 task는 backend가 optional device metadata를 받을 수 있는 경계와 settings 관리 UI까지만 다룬다.
- **권한 상승**: settings 관리 API는 browser session만 허용하고 bearer CLI token을 관리 권한으로 인정하지 않는다.
- **raw token 노출**: 생성 응답 외 list/store/serialized response에서 raw token과 digest를 제거하고 security test로 고정한다.
- **device 집계 기대치**: analyzer 정확도와 무관하게 device 목록은 만들 수 있지만, 실제 device별 사용량 숫자는 submit 연동 이후 의미가 커진다. 이번 task에서는 최소 metadata와 lastSubmittedAt 중심으로 구현한다.
- **기존 latest snapshot contract 회귀**: device metadata는 submit wrapper/service metadata로 처리하고 UsageSnapshot 내부 구조를 변경하지 않는다.
