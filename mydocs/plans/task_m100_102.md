# Task #102 수행계획서 — 모바일 Share Studio SNS 대상 정리와 X·Threads 공유 URL 보정

GitHub Issue: [#102](https://github.com/postmelee/codex-usage-profile/issues/102)
마일스톤: M100

## 목적

모바일 OS에서 앱의 작성 화면으로 안정적으로 이어지지 않는 Facebook·LinkedIn
공유 버튼을 Share Studio에서 제외하고, `X · Threads · Reddit · Save` 네 액션을
한 줄로 제공한다. 화면 너비가 아니라 실행 환경을 기준으로 대상을 선택해 좁은
데스크톱에서는 기존 여섯 액션을 유지한다.

동시에 X가 공식 작성 Web Intent를 사용하도록 경로를 바로잡고, Threads 앱이 영어
공유 문구의 공백을 `+`로 표시하는 직렬화 불일치를 `%20`으로 보정한다. Reddit,
다운로드와 보조 복사 액션은 유지하며 provider API, OAuth 또는 Web Share 기능은
추가하지 않는다.

## 배경

- 2026-08-13 iOS Safari 실측에서 Facebook과 LinkedIn HTTPS 공유 링크는 앱을 열지만
  작성 화면을 열거나 본문을 채우지 못했다. 현재 구현은 네이티브 SDK나 앱 설치
  감지가 아니라 일반 `<a target="_blank">`와 provider HTTPS URL을 사용한다.
- X 대상은 [`shareStudio.js`](../../src/profile-ui/shareStudio.js)의
  `https://x.com/intent/post`를 사용한다. X 공식 Web Intents 문서가 지정한 작성
  경로는 `https://x.com/intent/tweet`이다.
- 공유 query는 `URL.searchParams.set()`으로 직렬화돼 공백이 form-urlencoded의 `+`가
  된다. Threads iOS 앱은 영어 `text` 값을 같은 규칙으로 복원하지 않아 첨부 실측에서
  `See+my+Codex+usage+activity.`로 입력했다.
- 모바일 CSS는 네 열 grid지만 여섯 액션이므로 현재 4+2 두 줄이 된다. 또한
  `max-width: 360px`에서는 두 열로 다시 줄여 네 액션도 두 줄이 된다.
- 기존 Playwright의 `Share card dialog fits a mobile viewport` 테스트는 viewport만
  390×844로 바꾸고 desktop browser context를 유지한다. 실행 환경 분기 이후에는 이
  테스트를 좁은 데스크톱 회귀로 보존하고, 실제 iPhone·Android context를 별도로
  검증해야 한다.
- #101 Stage 4도 같은 Share Studio 파일을 수정할 계획이다. 작업지시자 승인에 따라
  #102를 먼저 완료·병합하고 #101은 Stage 4 전에 최신 `devel`을 반영한다.

## 범위

### 포함

- `navigator.userAgentData.mobile`을 우선하고 iPhone·iPod·Android User-Agent를
  fallback으로 사용하는 모바일 실행 환경 판별
- `MacIntel`과 `maxTouchPoints > 1` 조합으로 desktop-class User-Agent를 쓰는 iPadOS 판별
- 모바일 실행 환경에서 Facebook·LinkedIn share target을 생성·렌더링 대상에서 제외
- 데스크톱에서는 viewport 너비와 무관하게 X, Threads, LinkedIn, Facebook, Reddit과
  Save 여섯 액션 유지
- X 작성 URL을 `https://x.com/intent/tweet`으로 변경하고 기존 `text`, `url` 유지
- Threads의 raw query 공백만 `%20`으로 직렬화하고 실제 `+` 문자는 `%2B`로 보존
- 360px 이하를 포함한 모바일 네 액션 한 줄 배치와 44px 이상 hit target 검증
- 영어·한국어 URL, iPhone·Android·iPadOS, 좁은 desktop viewport 단위·E2E 회귀
- 기존 공식 사용자 문서 `docs/readme-card.md`의 Share Studio 대상 설명 최소 현행화

### 제외

- viewport breakpoint로 Facebook·LinkedIn의 기능 노출 여부를 결정하는 처리
- Facebook·LinkedIn 앱 설치 여부 감지
- Facebook·LinkedIn provider API, OAuth, 네이티브 SDK 또는 본문 자동 입력 보장
- #39 Animated GIF·Web Share와 native share sheet
- SNS 자동 게시, 이미지 자동 업로드와 clipboard 계약 변경
- Threads `.net` 도메인 변경
- #101 revision 공유 문서·플랫폼 cache identity 실험
- social preview 이미지, Open Graph metadata와 공개 profile route 변경
- 별도 승인 없는 production 배포와 실제 SNS 게시 완료

## 설계 방향

- **실행 환경과 layout 분리**: 모바일 여부는 viewport나 CSS media query로 추론하지
  않는다. `shareStudio.js`의 I/O 없는 순수 helper가 navigator 형태의 입력을 받아
  판정하고, `ShareStudio`는 최초 render에서 동기적으로 결과를 계산한다. effect 뒤
  필터링하지 않아 버튼 깜빡임과 focus 순서 변화를 만들지 않는다.
- **판별 우선순위**: `userAgentData.mobile`이 boolean이면 그 값을 우선한다. 해당 API가
  없는 Safari 등에서는 `userAgent`의 iPhone·iPod·iPad·Android를 사용하고, 마지막으로
  `platform === "MacIntel" && maxTouchPoints > 1`인 iPadOS를 모바일로 본다. width,
  `pointer: coarse`와 touch 지원만으로는 터치 데스크톱을 제외할 수 없어 사용하지 않는다.
- **target 계약에서 제거**: 모바일에서 Facebook·LinkedIn을 CSS로 감추지 않고
  `buildShareTargets` 결과에서 제외한다. 따라서 DOM, 접근성 트리, animation index와
  keyboard tab 순서에도 존재하지 않는다. 모바일 여부를 명시하지 않은 기존 helper
  caller는 desktop 호환 결과를 유지한다.
- **provider별 URL 보정**: X는 origin과 query를 유지하고 path만 공식 `/intent/tweet`으로
  바꾼다. Threads만 raw URL의 form space `+`를 `%20`으로 바꾼다. 입력의 실제 plus는
  `URLSearchParams`가 `%2B`로 먼저 인코딩하므로 raw `+` 치환과 구분된다. 다른 provider의
  기존 직렬화는 변경하지 않는다.
- **한 줄 layout**: 모바일 기본 네 열 grid를 유지하고 `max-width: 360px`의 Share Studio
  전용 두 열 override를 제거하거나 네 열로 정렬한다. 320px 폭에서도 60px 네 열과 12px
  gap, 양쪽 16px padding이 들어가는지 실측한다. 같은 폭의 desktop UA는 여섯 대상을
  계속 제공하며 필요하면 기존 grid wrapping을 허용한다.
- **#101 병합 순서**: #102가 Share Studio의 provider·environment baseline을 먼저 고정한다.
  #101 Stage 4는 최신 `devel`을 반영한 뒤 revision URL만 이 target 계약 위에 합성하고,
  모바일에서 Facebook·LinkedIn을 다시 노출하지 않아야 한다.

## 잠정 단계

- **Stage 1 — 모바일 대상과 provider URL 순수 계약 고정**

- **Stage 2 — Share Studio 연결과 모바일 한 줄 layout**

  - 검증 관점: 깜빡임·focus drift·문서 overflow 없이 모바일 4개와 desktop 6개가
    실행 환경 기준으로 구분되는가.
- **Stage 3 — 사용자 문서 현행화와 전체 회귀**

## 리스크

- **User-Agent 판별 한계**: 브라우저 UA 축소·spoofing으로 오분류할 수 있다. UA-CH boolean을
  우선하고 Safari/iPadOS에 필요한 최소 fallback만 두며 viewport나 touch 단독 추론은 피한다.
- **앱 미설치 모바일**: 모바일에 Facebook·LinkedIn 앱이 없으면 웹 sharer가 동작할 수도 있지만
  설치 여부는 브라우저가 신뢰성 있게 제공하지 않는다. 관찰된 실패와 단순한 4개 primary action을
  우선하는 제품 정책으로 모바일 OS 전체에서 제외한다.
- **Threads 이중 인코딩**: 전체 문자열에 `encodeURIComponent`를 다시 적용하면 URL parameter가
  깨질 수 있다. `URLSearchParams` 직렬화 후 raw space marker만 provider별로 바꾸고 decoded 값과
  raw href를 함께 테스트한다.
- **작은 화면 회귀**: 기존 360px 이하 두 열 규칙을 바꾸면 label overflow가 생길 수 있다.
  320px에서 실제 bounds, 한 줄 여부와 document overflow를 측정한다.
- **#101 파일 충돌**: 두 task가 같은 Share Studio와 공식 문서를 수정한다. 승인된 순서대로 #102를
  먼저 병합하고 #101 Stage 4 전에 최신 `devel` 반영과 mobile target 회귀 검증을 요구한다.

## 승인 요청 사항

- 위 포함·제외 범위와 3단계 구성
- viewport가 아닌 navigator 기반 실행 환경 판별과 UA-CH → UA → iPadOS fallback 순서
- 모바일 target 결과에서 Facebook·LinkedIn을 제거해 DOM·접근성 트리에도 두지 않는 방향
- X는 `/intent/tweet`, Threads만 `%20`으로 보정하고 다른 provider 직렬화는 유지하는 방향
- 360px 이하 두 열 override를 제거·보정해 320px 이상에서 네 액션을 한 줄로 두는 layout
- 공식 문서는 `docs/readme-card.md`만 최소 수정하고 README·아키텍처·운영 문서는 변경하지 않는 판단
- #102를 먼저 병합하고 #101 Stage 4가 최신 `devel`을 반영하는 병합 순서

승인되면 `task_m100_102_impl.md`에서 단계별 산출물, 검증 명령과 커밋 메시지를 구체화한다.
