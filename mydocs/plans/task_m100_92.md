# Task #92 수행계획서 — 모바일 공유 카드 전환과 계정 메뉴 터치 회귀 보정

- GitHub Issue: [#92](https://github.com/postmelee/codex-usage-profile/issues/92)
- Milestone: M100 — v1.0 MVP
- 상태: 구현 승인 대기

## 1. 목적

모바일 Safari와 Chrome에서 공통으로 확인된 다음 회귀를 보정한다.

1. 홈의 공유 버튼으로 Share Studio를 열 때 카드가 모바일 뷰포트보다 과도하게 확대되는 전환
2. 계정 메뉴 항목을 터치하면 메뉴만 닫히고 Profile·Settings 이동 또는 Log out 동작이 실행되지 않는 문제

데스크톱의 카드 공간 전환, 키보드 접근성, 카드 캐시·readiness 계약은 유지한다. 보정 후 실제 모바일 Safari와 Chrome에서 재검증할 수 있는 상태를 만들고, 결과가 확인되기 전까지 Task #84의 Stage 5와 마케팅 진행을 차단한다.

## 2. 배경과 현재 판단

- 두 결함은 Task #84 Gate C 공개 전환 뒤 실제 모바일 Safari와 Chrome에서 동일하게 관찰됐다. Safari 전용 문제가 아니라 모바일 입력·레이아웃 경로의 공통 회귀로 다룬다.
- 공유 전환은 `useCardHandoffMotion`이 출발 카드와 모달 카드의 사각형 차이로 `translate + scale` 시작 프레임을 만드는 구조다. 모바일에서 출발·도착 레이아웃 비율이나 뷰포트 조건이 안전하지 않은데도 공간 전환을 실행해 과도한 확대 프레임이 나타날 가능성이 높다.
- 계정 메뉴는 컨테이너의 `blur`에서 `relatedTarget`이 메뉴 내부가 아니면 즉시 닫힌다. 모바일 터치 브라우저가 `relatedTarget`을 제공하지 않는 경우 링크의 활성화 전에 메뉴가 언마운트될 가능성이 높다.
- 위 내용은 구현 전 가설이다. Stage 1에서 실패하는 회귀 검증과 이벤트·프레임 관찰로 원인을 확정한 뒤 최소 범위로 보정한다.

## 3. 범위

### 포함

- 모바일 뷰포트에서 Share Studio가 열리는 첫 프레임과 최종 카드 크기·위치를 재현하고 회귀 계약으로 고정
- 포인터·호버·뷰포트 및 출발/도착 사각형의 안전성을 기준으로 공간 전환 적용 여부 결정
- 모바일 또는 안전하지 않은 사각형에서는 카드가 목표 레이아웃을 벗어나지 않는 안정적인 전환 사용
- 필요 시 카드 컨테이너의 `max-width`, `min-width`, overflow 등 모바일 레이아웃 안전장치 보정
- 모바일 터치에서 Profile·Settings·Log out 활성화가 메뉴 닫힘보다 먼저 완료되도록 계정 메뉴 dismiss 생명주기 보정
- 외부 클릭, Escape, 키보드 탐색, 데스크톱 공간 전환 회귀 방지
- Chromium 모바일 에뮬레이션과 가능한 WebKit 경로, 실제 모바일 Safari·Chrome 검증
- Task #84 재개 조건과 실측 결과 기록

### 제외

- 모바일에서 영어로 표시되는 locale 동작
- Threads 공유 문구 및 intent 보정
- 공유 대상 추가, 카드·메뉴 재디자인 등 신규 기능
- API, 데이터베이스 migration, 사용량 집계, 이미지·OG·미디어 캐시 계약 변경
- Task #91 문서 및 Task #84 Stage 5 구현·마케팅 작업

## 4. 설계 방향

### 4.1 공유 카드 전환

- User-Agent 문자열로 플랫폼을 분기하지 않는다.
- 포인터 특성, hover 가능 여부, visual/layout viewport, 출발·도착 사각형 유효성을 이용해 공간 전환이 안전한지 판정한다.
- 데스크톱에서 사각형이 유효한 경우 기존 FLIP 기반 공간 전환을 유지한다.
- coarse pointer 또는 안전하지 않은 모바일 레이아웃에서는 모달의 최종 크기·위치를 처음부터 고정하고 opacity 중심 전환을 사용한다.
- 시작 프레임에서도 카드 경계가 유효 뷰포트를 과도하게 벗어나지 않는지를 테스트한다. 최종 상태만 확인하는 기존 모바일 검증을 보강한다.
- CSS 안전장치는 재현으로 필요성이 확인된 속성만 추가한다.

### 4.2 계정 메뉴 터치 활성화

- 항목 활성화 결과가 확정되기 전에 `blur`만으로 메뉴를 동기적으로 언마운트하지 않는다.
- 메뉴 항목은 자신의 활성화 처리 뒤 메뉴를 닫고, 외부 pointer down과 Escape는 기존 dismiss 책임을 유지한다.
- 포커스가 실제로 메뉴 밖으로 이동한 경우의 닫힘이 필요하면 다음 프레임의 `activeElement`를 확인하는 방식 등 터치 활성화를 방해하지 않는 순서를 사용한다.
- Profile·Settings 경로와 Log out 의미는 변경하지 않는다.

## 6. 단계 계획

### Stage 1 — 재현과 회귀 계약 확정

- 모바일 Share Studio 시작 프레임의 transform·경계와 계정 메뉴 터치 활성화 실패를 재현한다.
- 기존 데스크톱 모션과 키보드 동작을 기준선으로 기록한다.
- 원인을 증명하는 집중 회귀 테스트를 작성하고 보정 계약을 확정한다.
- 단계 종료 보고와 검증 뒤 다음 단계 승인을 요청한다.

### Stage 2 — 모바일 공유 카드 전환 보정

- 안전한 공간 전환 판정을 구현한다.
- 모바일/불안전 조건에서는 목표 레이아웃 고정 전환을 적용한다.
- 필요한 범위의 카드 컨테이너 레이아웃 안전장치를 반영한다.
- 데스크톱 전환과 reduced-motion 계약을 함께 검증한다.

### Stage 3 — 계정 메뉴 터치 생명주기 보정

- 터치 활성화보다 앞서는 blur dismiss를 보정한다.
- Profile·Settings·Log out, 외부 클릭, Escape, 키보드 포커스 이동을 검증한다.
- 모바일 Chromium과 가능한 WebKit 경로에서 집중 회귀 검증을 수행한다.

### Stage 4 — 통합 검증과 모바일 실측 인계

- 단위·E2E·프로덕션 빌드 검증을 수행한다.
- 로컬 또는 승인된 배포 환경에서 실제 모바일 Safari·Chrome 실측 경로를 제공한다.
- 작업지시자의 두 브라우저 확인 결과를 기록한다.
- Task #84 Stage 5 재개 가능 여부를 최종 보고서와 PR에 명시한다.

## 9. 승인 요청 사항

다음 내용을 승인받은 뒤 구현계획서 작성과 Stage 1로 진행한다.

1. locale 영어 표시와 Threads intent는 Task #92 범위에서 제외한다.
2. 모바일/coarse pointer 또는 불안전한 사각형에서는 공간 확대 대신 최종 위치 고정 opacity 전환을 사용한다.
3. 계정 메뉴는 항목 활성화를 우선하고 외부 pointer down·Escape·활성화 후 닫힘으로 dismiss 책임을 정리한다.
4. 실제 모바일 Safari와 Chrome 실측이 완료되기 전까지 Task #84 Stage 5와 마케팅을 재개하지 않는다.
5. 사용자·공개 문서는 변경하지 않고 내부 작업 문서와 PR 검증 기록만 갱신한다.
