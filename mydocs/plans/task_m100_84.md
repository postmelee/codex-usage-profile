# Task #84 수행계획서 — main 릴리스 승격 및 production 공개 전환

GitHub Issue: [#84](https://github.com/postmelee/codex-usage-profile/issues/84)
마일스톤: M100

## 목적

Task #83과 PR #85까지 누적된 정확한 `devel` 후보를 `main` 릴리스 기준으로
승격하고, 그 exact `main` source로 새 owner-only Sites saved version을 만든 뒤
기능·migration·artifact 계약을 재검증한다. 별도 Gate C 승인을 받은 경우에만
production을 public으로 전환하고, application 응답과 X·Threads·카카오톡의 실제
미리보기를 함께 측정한다.

정상 결과일 때만 public 상태를 유지한다. exact source, privacy, media 또는 비용
보호선이 하나라도 실패하면 public 상태에서 원인 분석을 계속하지 않고 custom
owner-only와 검증된 이전 saved version 순서로 먼저 원복한다.

## 배경

- #83과 PR #85는 Sites artifact의 절대 경로 문제, D1 migration `1..5`, canonical
  공유 문서, social fallback, owner profile 경로와 카드 loading/resource UX를
  보정했다.
- 현재 production은 saved version 23, custom owner-only다. 이 saved version은
  Stage 4.6 source `c030339d848f961c54358d9d3523b340bed09670`을 사용한다.
- PR #85 Stage 4.7은 card image lease lifecycle과 hosted migration SQL/spec drift
  guard를 보정했지만 saved version 23에는 배포되지 않았다.
- 이번 task 시작 시 고정한 `origin/devel`은 PR #85 merge commit
  `242674cca76b167642108fb85f739fbdcf9fd4d4`다.
- 시작 시 `origin/main`은 `e75609db133ae43e9a36d7cc9994c813bcaa621c`이고,
  이 commit이 `origin/main`과 `origin/devel`의 merge-base다. `devel`은 419 commits
  앞서며 `main`에만 있는 commit은 없다. 누적 release PR은 671 files 규모이므로
  commit/tree provenance와 CI를 일반 task PR보다 엄격히 확인한다.
- 실제 Sites front door에서 root query는 정적 `index.html`로 처리되고 extension
  없는 `/u/{handle}`은 `/`로 redirect된다. Worker 전달과 handle별 initial metadata가
  검증된 canonical 공유 문서는 `/api/share/{handle}`이다.

## 설계 방향

### 1. 일반 task PR과 release PR 분리

- `local/task84`는 계획·단계 증적·최종 보고와 승인된 운영 문서 변경을 담는다.
- 일반 task 게시 절차는 `local/task84 → publish/task84 → devel`을 유지한다.
- 제품 릴리스 승격은 별도 release PR `devel → main`으로 수행한다.
- release PR head는 task branch가 아니라 고정된 `devel`이어야 한다. Task #84 계획
  commit이 아직 `devel`에 없다는 이유로 release source를 task branch로 바꾸지 않는다.
- release PR merge는 작업지시자가 직접 수행한다. 자동/self merge하지 않는다.

### 2. Candidate와 merge tree 고정

- Stage 1 시작 시 `origin/devel`, `origin/main`, merge-base, ahead/behind와 diff를 다시
  기록한다.
- candidate 검증 뒤 `devel`이 움직이면 기존 결과를 재사용하지 않고 새 SHA로
  candidate를 다시 고정해 영향 검토와 필요한 검증을 반복한다.
- release PR merge 뒤 exact `origin/main` SHA와 parent를 기록하고 candidate와
  `git diff --exit-code`로 tree equality를 확인한다. release merge commit SHA가
  candidate SHA와 다르더라도 tree가 같아야 한다.

### 3. Exact main build와 owner-only 경계

- task branch working tree의 artifact를 production에 사용하지 않는다.
- merge된 exact `main` SHA를 checkout한 별도 clean worktree에서 dependency 상태,
  build, finalizer, verifier와 archive 검사를 다시 실행한다.
- archive는 exact `main`에서 새로 만들고 배포 직전 digest와 금지 문자열 검사를
  기록한다. 이전 task의 archive를 재사용하지 않는다.
- Sites saved version 생성·owner-only 배포는 Stage 3 진입 승인 뒤 수행한다.
- `.openai/hosting.json`이 있는 프로젝트이므로 실제 Sites build/배포 시
  `sites-building`, 이어서 `sites-hosting` 절차를 적용한다.

### 4. Gate C는 별도 승인과 fail-closed 절차

- owner-only exact-main smoke가 모두 통과해도 public 전환을 자동으로 이어서 하지
  않는다. saved version, source SHA, access/environment revision, rollback target,
  비용·quota 상태와 disposable 데이터 범위를 제시하고 Gate C 승인을 받는다.
- public 전환 뒤 private/missing 비열거, OAuth/CLI, publish/unpublish, 네 README PNG,
  canonical share HTML과 social image를 application에서 먼저 확인한다.
- 외부 플랫폼 결과는 같은 시점의 application response/ETag/revision과 분리 기록한다.
  플랫폼 cache 지연만으로 추측성 cache 보정을 수행하지 않는다.
- stop trigger가 발생하면 먼저 custom owner-only로 닫고 필요 시 이전 saved version을
  배포한다. public 상태에서 진단을 계속하지 않는다.

### 5. Release 뒤 문서 상태

- README placeholder 교체와 마케팅 문구는 후속 작업으로 남긴다.
- 본 task에서는 기존 운영 진실 원천의 saved version/source/access와 canonical Gate C
  결과만 현행화한다.
- 공식 문서 변경은 public 유지 또는 rollback 결과가 확정된 뒤 한 번만 수행한다.

## 리스크

- **누적 release PR 규모**: `main`이 419 commits 뒤라 diff가 크다. candidate SHA,
  merge-base, ahead/behind, tree equality와 CI를 함께 기록하고 review 없는 merge를 금지한다.
- **Task branch와 release source 혼동**: task 문서 branch artifact를 배포하면 exact main
  provenance가 깨진다. release PR head는 `devel`, production build는 merge된 exact main
  clean worktree로 고정한다.
- **Stage 4.7 원격 미검증**: saved version 23은 Stage 4.7을 포함하지 않는다. exact main
  owner-only saved version과 전체 smoke 전에는 Gate C로 진행하지 않는다.
- **Sites route 제약**: `/u/{handle}` HTML과 root query initial metadata는 Worker 전달이
  보장되지 않는다. `/api/share/{handle}`만 SNS canonical로 사용한다.
- **외부 플랫폼 cache**: X·Threads·카카오톡 결과가 application 최신 응답보다 늦을 수
  있다. ETag/revision/원본 metadata와 플랫폼 결과를 분리해 제품 결함을 판정한다.
- **provider degradation**: avatar 또는 personalized social provider 실패 시 fallback이
  나타날 수 있다. application fail-closed 계약과 플랫폼 cache를 구분하고 근거 없는
  cache/provider 정책 변경은 하지 않는다.
- **비용·quota**: public smoke가 plan upgrade나 자동 과금을 요구하면 즉시 중단하고
  owner-only로 유지한다.
- **rollback과 additive migration**: application rollback과 schema downgrade를 혼동하지
  않는다. 이전 saved version은 migration `1..5` 호환을 확인한 뒤에만 rollback target으로
  사용하고 data/schema downgrade는 수행하지 않는다.
- **테스트 데이터 잔류**: Gate C 전에 disposable identity/token/session과 cleanup 범위를
