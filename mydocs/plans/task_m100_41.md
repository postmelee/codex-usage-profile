# 수행계획서 — Task #41: Neon production structured store 및 migration 구현

GitHub Issue: [#41](https://github.com/postmelee/codex-usage-profile/issues/41)
마일스톤: M100

## 목적

Cloud Run 다중 인스턴스 production runtime이 사용할 durable structured store를 Neon(PostgreSQL)으로 구현한다. 현재 owner/OAuth/session/CLI credential/device/usage/visibility 상태는 동기식 memory·file store에만 존재하며 단일 인스턴스 로컬 개발용이다. 이 task는 (1) provider 중립 store contract의 원자성·멱등성·owner isolation을 실제 DB transaction으로 보장하는 async Postgres adapter(배포 대상 Neon), (2) versioned schema migration, (3) 기존 local file data를 Neon으로 seeding하는 migration과 rollback을 구현해 `PROFILE_STORE_MODE=external`에서 production runtime이 안전하게 기동되도록 한다.

## 배경

- #37에서 MVP canonical architecture를 Cloud Run + Neon + R2로 확정했고, [`docs/production-hosting.md`](../../docs/production-hosting.md)의 "Structured Store Contract"와 "후속 작업" 1·2번이 이 task 범위를 명시한다.
- [`src/profile-backend/store-contract.js`](../../src/profile-backend/store-contract.js)는 store 표면(30개 method)과 5개 atomic operation(OAuth callback 완료, CLI login 승인/교환, Account Usage submit, visibility 변경)의 직렬화 키·invariant·rollback 정책을 provider 중립으로 정의하지만, 아직 계약 fixture(memory/file store)만 존재한다.
- 현재 서비스 write path(`oauth-runtime.js`, `cli-login.js`, `account-usage-submit.js`, `accounts.js`)는 store를 **동기식**으로 호출하고, 원자 연산을 개별 read-modify-write로 수행한다. Postgres(Neon) adapter는 네트워크 I/O 기반이라 async 전환과 명시적 transaction 경계가 필수다.
- [`src/profile-runtime/production-server.js`](../../src/profile-runtime/production-server.js)의 `createProductionStore`는 `storeMode === "external"`일 때 전용 adapter 주입이 없으면 fail closed하도록 이미 구성되어 있다. 이 task가 그 adapter를 채운다.
- PostgreSQL driver(`pg` 등)는 아직 의존성에 없다. 신규 도입이 필요하다.

## 설계 방향

- **async 계약 정렬 (핵심 결정)**: store contract를 "동기 또는 Promise 반환 허용" 계약으로 정의하고, 서비스·http handler write/read path를 `await`로 통일한다. `await`는 동기 값에도 안전하므로 memory/file store 계약 fixture는 인터페이스를 유지한 채 회귀 통과, Postgres adapter만 실제 Promise를 반환한다. 이 전환이 이번 task에서 가장 넓은 diff를 만든다.
- **atomic operation을 transaction scope로 구현 (async 전환의 필수 전제, 2026-07-21 승인 갱신)**: 당초 "5개 연산을 준비된 레코드로 named store method에 넘김" 설계는, 판정 로직(usage stale/conflict 비교, OAuth handle 유일성 루프)이 **잠금 없는 read 시점**에 실행되어 다중 인스턴스 경쟁 안전성을 만족하지 못함을 코드 검토에서 확인했다. 따라서 store가 `transaction(fn)`을 노출하고, 각 원자 연산의 read-modify-write **전체**가 그 스코프 안에서 실행되도록 한다. Postgres adapter는 직렬화 키(`oauthState.id`/`cliLoginChallenge.id`/`owner.id`) read를 `FOR UPDATE`로 잠근다. 5개 연산(`completeOAuthCallback`, `approveCliLogin`, `exchangeCliLogin`, `submitAccountUsage`, `updateVisibility`)은 개념적으로 유지되며 판정이 잠금 구간 안으로 들어간다. 현재 서비스의 read-modify-write는 동기식이라 "우연히" 원자적이지만 write path를 `await`로 바꾸면 in-process race window가 생기므로, transaction scope는 async 전환 정합성의 필수 조건이다. memory/file store의 `transaction`은 단일 스레드 스냅샷/복원으로 all-or-nothing을 보장(잠금 불필요), Postgres만 BEGIN/COMMIT + FOR UPDATE. 비즈니스 로직(crypto·GitHub 호출·handle 루프)은 store로 새지 않고 tx-bound sub-service로 실행한다.
- **Postgres adapter 구조 (벤더 중립)**: 어댑터는 표준 Postgres wire protocol + `pg` connection pool 위에 구현하고 Neon 고유 요소를 코드에 두지 않는다. "Neon임"은 connection string과 운영 문서에만 존재한다. 디렉터리는 `src/profile-backend/postgres/`로 두어 로컬 Docker Postgres 테스트·타 관리형 Postgres 이식을 무비용으로 유지한다. edge용 `@neondatabase/serverless`는 배제하고(Cloud Run은 장수 컨테이너라 표준 TCP `pg`가 정석) `pg`를 사용한다. unique constraint(provider identity, handle, token digest, device/user code, owner+device key, owner/handle latest record)는 schema DDL에서 강제하고, 경쟁은 `SELECT … FOR UPDATE` 또는 conditional `UPDATE … WHERE` compare-and-swap으로 직렬화한다. 부분 commit 금지.
- **Cloud Run × Neon 연결 관리**: Cloud Run은 0→N 인스턴스로 확장되어 각자 pool을 가지므로, Neon **pooled(pgbouncer) endpoint**를 사용하고 인스턴스당 pool max를 소수(2~5)로 제한하며 `statement_timeout`을 설정한다. migration은 인스턴스 부팅 시 자동 실행하지 않는다(다중 인스턴스 동시 기동 경쟁). 배포 단계의 별도 job으로 분리하거나 advisory lock으로 단일 실행을 보장한다. startup은 liveness(`/healthz`)와 dependency readiness(Neon 연결·migration 상태)를 구분한다.
- **secret 최소화**: raw CLI token과 GitHub OAuth access token은 저장하지 않고 digest/파생 값만 저장한다(현재 memory store와 동일 원칙). schema에 raw secret 컬럼을 두지 않고, 저장 직전 `security.js`의 forbidden-secret 검사를 재사용한다.
- **migration 도구 (실데이터 없음 — seeding 성격)**: production은 아직 존재한 적이 없고 file store 데이터는 개발자 로컬에만 있으므로, 이 도구는 사실상 `exportState()` 스냅샷을 Neon으로 seeding하는 성격이다. 이슈 수용 기준이 명시하므로 `exportState`/`hydrate` 재사용으로 얇게 구현한다. `--dry-run`은 트랜잭션 후 rollback, 실제 실행은 commit, 재실행은 unique constraint 기반 idempotent upsert, `--rollback`은 이전 상태 복원. 여기에 과공수를 쓰지 않는다.
- **기존 패턴 유지**: `ProfileBackendError`/error code, `requireFields` 검증, 테스트는 `node --test`와 `__tests__/*.test.js` 규칙을 따른다. 프레임워크·불필요한 의존성을 추가하지 않는 저장소 기조를 유지한다.

## 잠정 단계

- **Stage 1 — async 계약 정렬과 atomic operation 승격**
  - store contract에 5 atomic operation method 추가, memory/file store 구현, store 호출 서비스 9개 + http write path의 `await` 전환
  - 검증 관점: 기존 store/서비스/http 회귀가 async 전환 후에도 통과, 원자 연산 계약 test(memory)가 기존 개별 write와 동일 결과 고정
- **Stage 2 — Postgres schema와 versioned migration**
  - `0001_init.sql` DDL, unique constraint, up/down runner, advisory lock, clean database bootstrap
  - 검증 관점: migration up→down→up 재현, clean DB bootstrap, constraint 존재 확인
- **Stage 3 — Postgres async adapter와 runtime wiring**
  - 전체 contract + 5 transaction(SQL FOR UPDATE / compare-and-swap) 구현, pool·statement_timeout, `createProductionStore` external branch, liveness/readiness 분리
  - 검증 관점: contract test를 Postgres adapter로 재실행(`TEST_DATABASE_URL` 있을 때), `PROFILE_STORE_MODE=external` 기동, owner scope 우회 불가
- **Stage 4 — file→Postgres seeding migration (최소 구현)**
  - `exportState`/`hydrate` 재사용 seeding 스크립트, dry-run/실행/재실행 idempotent/rollback. 실데이터 부재를 감안해 얇게 구현
  - 검증 관점: fixture seeding, 재실행 무변화, rollback 후 원상 복구
- **Stage 5 — concurrency·failure injection·secret·retention 문서**
  - failure injection 상한을 **5개 atomic operation × {중복 소비, 부분 commit} 매트릭스**로 고정. secret/log grep, retention/backup/PII 문서(`docs/production-hosting.md` 절)
