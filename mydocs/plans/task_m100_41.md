# 수행계획서 — Task #41: Neon production structured store 및 migration 구현

GitHub Issue: [#41](https://github.com/postmelee/codex-usage-profile/issues/41)
마일스톤: M100

## 목적

Cloud Run 다중 인스턴스 production runtime이 사용할 durable structured store를 Neon(PostgreSQL)으로 구현한다. 현재 owner/OAuth/session/CLI credential/device/usage/visibility 상태는 동기식 memory·file store에만 존재하며 단일 인스턴스 로컬 개발용이다. 이 task는 (1) provider 중립 store contract의 원자성·멱등성·owner isolation을 실제 DB transaction으로 보장하는 async Neon adapter, (2) versioned schema migration, (3) 기존 local file data를 Neon으로 이전하는 one-shot migration과 rollback을 구현해 `PROFILE_STORE_MODE=external`에서 production runtime이 안전하게 기동되도록 한다.

## 배경

- #37에서 MVP canonical architecture를 Cloud Run + Neon + R2로 확정했고, [`docs/production-hosting.md`](../../docs/production-hosting.md)의 "Structured Store Contract"와 "후속 작업" 1·2번이 이 task 범위를 명시한다.
- [`src/profile-backend/store-contract.js`](../../src/profile-backend/store-contract.js)는 store 표면(30개 method)과 5개 atomic operation(OAuth callback 완료, CLI login 승인/교환, Account Usage submit, visibility 변경)의 직렬화 키·invariant·rollback 정책을 provider 중립으로 정의하지만, 아직 계약 fixture(memory/file store)만 존재한다.
- 현재 서비스 write path(`oauth-runtime.js`, `cli-login.js`, `account-usage-submit.js`, `accounts.js`)는 store를 **동기식**으로 호출하고, 원자 연산을 개별 read-modify-write로 수행한다. Neon adapter는 네트워크 I/O 기반이라 async 전환과 명시적 transaction 경계가 필수다.
- [`src/profile-runtime/production-server.js`](../../src/profile-runtime/production-server.js)의 `createProductionStore`는 `storeMode === "external"`일 때 전용 adapter 주입이 없으면 fail closed하도록 이미 구성되어 있다. 이 task가 그 adapter를 채운다.
- PostgreSQL driver(`pg` 등)는 아직 의존성에 없다. 신규 도입이 필요하다.

## 범위

### 포함

- Neon/PostgreSQL schema와 up/down versioned migration, clean database bootstrap
- owner/provider identity, OAuth state, session, CLI challenge/token digest, device, usage latest record, visibility의 Neon 저장
- async repository adapter(`createNeonProfileBackendStore`)와 production runtime wiring(`createProductionStore` external branch, startup readiness check)
- 5개 atomic operation을 실제 SQL transaction으로 구현하고 stale/conflict/idempotent/new 판정과 unique constraint 보장
- store contract를 async 계약으로 정렬(memory/file store와 서비스 write path의 async 전환)
- local file store → Neon one-shot migration(dry-run, 실행, 재실행 idempotent, rollback)
- credential·PII 최소화 확인과 retention/backup 기본 정책 문서화

### 제외

- R2 object storage, public card materialization, immutable revision write (#41 제외 명시)
- 실제 Cloud Run resource 생성, custom domain, 원격 Neon 프로비저닝
- Share Studio, GIF, tooltip UI

## 설계 방향

- **async 계약 정렬 (핵심 결정)**: store contract를 "동기 또는 Promise 반환 허용" 계약으로 정의하고, 서비스·http handler write/read path를 `await`로 통일한다. `await`는 동기 값에도 안전하므로 memory/file store 계약 fixture는 인터페이스를 유지한 채 회귀 통과, Neon adapter만 실제 Promise를 반환한다. 이 전환이 이번 task에서 가장 넓은 diff를 만든다.
- **atomic operation을 1급 store method로 승격**: contract가 정의한 5개 연산을 store 표면 method(예: `completeOAuthCallback`, `approveCliLogin`, `exchangeCliLogin`, `submitAccountUsage`, `updateVisibility`)로 추가한다. memory/file store는 기존 개별 method를 순차 호출하는 단순 구현으로, Neon adapter는 단일 SQL transaction으로 구현해 양쪽이 동일 계약·동일 contract test를 통과한다. 서비스는 개별 read-modify-write 대신 이 원자 method를 호출하도록 정리한다.
- **Neon adapter 구조**: `pg` connection pool 위에 repository를 구현한다. unique constraint(provider identity, handle, token digest, device/user code, owner+device key, owner/handle latest record)는 schema DDL에서 강제하고, 경쟁은 `SELECT … FOR UPDATE` 또는 conditional `UPDATE … WHERE` compare-and-swap으로 직렬화한다. 부분 commit 금지.
- **secret 최소화**: raw CLI token과 GitHub OAuth access token은 저장하지 않고 digest/파생 값만 저장한다(현재 memory store와 동일 원칙). schema에 raw secret 컬럼을 두지 않고, 저장 직전 `security.js`의 forbidden-secret 검사를 재사용한다.
- **migration 도구**: `exportState()`로 얻은 file store 스냅샷을 Neon으로 적재하는 one-shot 스크립트. `--dry-run`은 트랜잭션 후 rollback, 실제 실행은 commit, 재실행은 unique constraint 기반 idempotent upsert, `--rollback`은 이전 상태 복원.
- **기존 패턴 유지**: `ProfileBackendError`/error code, `requireFields` 검증, 테스트는 `node --test`와 `__tests__/*.test.js` 규칙을 따른다.

## 잠정 단계

- **Stage 1 — async 계약 정렬과 atomic operation 승격**
  - store contract에 5 atomic operation method 추가, memory/file store 구현, 서비스·http write path의 `await` 전환
  - 검증 관점: 기존 store/서비스/http 회귀가 async 전환 후에도 통과, 원자 연산 계약 test(memory) 통과
- **Stage 2 — Neon schema와 versioned migration**
  - `0001_init.sql` DDL, unique constraint, up/down runner, clean database bootstrap
  - 검증 관점: migration up→down→up 재현, clean DB bootstrap, constraint 존재 확인
- **Stage 3 — Neon async adapter와 runtime wiring**
  - 전체 contract + 5 transaction(SQL FOR UPDATE / compare-and-swap) 구현, `createProductionStore` external branch, startup readiness check
  - 검증 관점: contract test를 Neon adapter로 재실행, `PROFILE_STORE_MODE=external` 기동, owner scope 우회 불가
- **Stage 4 — file→Neon one-shot migration**
  - `exportState` 스냅샷 적재 스크립트, dry-run/실행/재실행 idempotent/rollback
  - 검증 관점: fixture migration, 재실행 무변화, rollback 후 원상 복구
- **Stage 5 — concurrency·failure injection·secret·retention 문서**
  - OAuth/device/submit/visibility 경쟁·부분 commit 실패 주입 test, secret/log grep, retention/backup/PII 정책 문서
  - 검증 관점: 중복 소비·부분 commit 부재, raw token·OAuth access token 미저장, `npm test`·`git diff --check`

## 리스크

- **async 전환의 넓은 diff**: 서비스·http write path 전반이 바뀐다. → Stage 1을 독립 단계로 분리해 회귀를 먼저 고정하고, memory/file store 계약을 유지해 diff 폭발을 억제한다.
- **PostgreSQL integration test 실행 환경**: 실제 Neon/Postgres 인스턴스 접근이 이 환경에서 제한될 수 있다. → 로컬 Postgres 기동, 임베디드/컨테이너, 또는 계약 회귀 우선 중 어느 방식으로 integration test를 실행할지 승인 필요(아래 승인 요청).
- **`pg` 신규 의존성 도입**: 공급망·오프라인 설치 이슈. → 의존성 추가 승인 필요, driver 선택(`pg` vs `postgres`) 확정.
- **원자성 회귀 위험**: 기존 개별 write를 transaction으로 묶는 과정에서 동작 변화 가능. → 승격 method가 기존 개별 method와 동일 결과를 내는지 계약 test로 고정.
- **migration 데이터 손실**: one-shot 적재 실수. → dry-run 기본, rollback 경로 필수, 재실행 idempotent 보장.

## 승인 요청 사항

1. **async 계약 전환 방향**: store contract를 async 허용 계약으로 바꾸고 서비스·http write path를 전면 `await` 전환하는 설계 승인.
2. **atomic operation 승격**: 5개 연산을 store 표면 1급 method로 추가하고 서비스가 이를 경유하도록 정리하는 방향 승인.
3. **`pg` 의존성 도입**과 driver 선택(`pg` 권장) 승인.
4. **PostgreSQL integration test 실행 전략**: 실제 Postgres 기동 방식(로컬/컨테이너/임베디드) 또는 이 환경에서의 실행 가능 범위 결정.
5. **retention/backup/PII 문서 위치**: `docs/production-hosting.md` 절 확장 vs 신규 `docs/data-retention.md` 중 선택.
6. **Neon 연결 env 이름 확정**: 서버 전용 secret 이름(예: `NEON_DATABASE_URL`)과 non-secret 운영 값 명명.
7. 범위 제외 항목(R2/Cloud Run 실제 프로비저닝/Share UI) 유지 확인.

승인되면 `task_m100_41_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
