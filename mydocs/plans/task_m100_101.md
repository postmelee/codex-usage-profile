# Task #101 수행계획서 — X·LinkedIn 소셜 미리보기 revision 경로 캐시 갱신 실험

GitHub Issue: [#101](https://github.com/postmelee/codex-usage-profile/issues/101)
마일스톤: M100

## 목적

현재 카드가 갱신돼도 고정 `/api/share/{handle}` 문서의 이전 미리보기를 재사용하는 X와
LinkedIn을 위해, 쿼리 문자열이 없는 revision 경로형 공유 문서를 실험한다. 최신 카드의
공유 URL, `canonical`, `og:url`, Open Graph·Twitter 이미지 revision을 같은 정체성으로
정렬하고 실제 플랫폼에서 새 게시물 미리보기가 갱신되는지 확인한다.

실험이 X와 LinkedIn에서 통과한 뒤에만 Share Studio의 공유 링크 복사와 X, LinkedIn,
Threads, Facebook, Reddit 버튼을 같은 revision 경로로 전환한다. 기존 고정 공유 문서,
공개 프로필 SPA와 README 카드 URL은 하위 호환으로 유지하며, 과거 카드 보존용 DB나
플랫폼 자동 게시 기능은 추가하지 않는다.

## 배경

- 배포 상태에서 Threads, Facebook, Reddit은 고정 `/api/share/{handle}`를 다시 공유하면
  변경된 카드를 거의 즉시 표시했다.
- X와 LinkedIn은 같은 고정 URL에서 이전 카드를 계속 표시했다. 공유 URL에
  `?v={revision}`을 붙였을 때 X는 일정 시간 뒤 최신 카드를 표시했지만 LinkedIn은
  이전 이미지를 유지했다.
- 현재 [`open-graph.js`](../../src/profile-runtime/open-graph.js)는 공유 문서의
  `canonical`·`og:url`을 고정 `/api/share/{handle}`로 만들고, 이미지만
  `/u/{handle}/social.png?v={revision}`으로 구분한다. X·LinkedIn이 공유 문서 자체를
  캐시하면 새 이미지 주소를 다시 발견하지 못한다.
- [`public-profile-document.js`](../../src/profile-runtime/public-profile-document.js)는
  `/api/share/{handle}`와 `/u/{handle}`만 문서 요청으로 인식한다. Share Studio의
  [`buildPublicProfileShareUrl`](../../src/profile-ui/shareStudio.js)은 쿼리 없는 고정
  share URL만 만든다.
- 현재 이미지 revision은 owner `updatedAt`과 usage `uploadedAt` 중 최신 시각의 epoch
  milliseconds다. 같은 기준을 UI URL 생성과 문서 metadata에 공통 적용해야 한다.
- LinkedIn은 동일 URL의 오래된 미리보기를 Post Inspector로 갱신하거나 재수집을 기다리도록
  안내한다. X Web Intent는 URL 전달만 제공하고 즉시 카드 재수집을 보장하지 않는다.
- 이 작업은 완료된 #78의 캐시 후속 실험이다. #84의 `main` 승격·production 공개 전환과
  현재 production 상태 변경은 별도 범위로 유지한다.

## 설계 방향

- **공통 URL 계약**: runtime과 UI가 revision 계산·handle·URL 인코딩을 중복 구현하지 않도록
  브라우저에서도 사용할 수 있는 순수 공통 모듈을 둔다. revision token은 현재 계약과 같은
  `max(owner.updatedAt, usage.uploadedAt)`의 10진 epoch milliseconds로 고정하고, 유효한
  timestamp와 안전한 정수만 허용한다.
- **경로형 cache identity**: 최신 공유 URL은
  `/api/share/{handle}/r/{revision}`으로 만들며 query와 hash를 비운다. revision은 외부
  플랫폼 cache key를 분리하는 identity이지 DB history key가 아니다.
- **현재 revision 정합성**: 공개 프로필의 현재 revision과 경로 revision이 일치할 때
  `canonical`과 `og:url`을 요청된 revision URL로 맞추고, `og:image`,
  `og:image:secure_url`, `twitter:image`에는 같은 token을 사용한다. stale token 요청은
  과거 데이터를 가장하지 않고 현재 revision metadata를 가리키게 하며, invalid token은
  문서 route로 인정하지 않는다. 세부 응답 방식은 구현계획서에서 테스트 우선으로 고정한다.
- **고정 route 하위 호환**: 기존 `/api/share/{handle}`는 계속 응답하고 현재 self canonical
  계약을 유지한다. revision route 실측 전에 고정 route를 redirect하거나 기존 SNS 버튼을
  바꾸지 않아 실험 변수를 분리한다.
- **fallback 비열거**: 공개 profile과 정합한 social object가 있을 때만 revision identity를
  노출한다. private·missing은 현재와 동일하게 site root canonical과 packaged sample을 사용해
  handle 존재 여부를 구분하지 못하게 한다.
- **cache header 분리 금지**: 1차 실험은 URL identity와 metadata 정렬 효과만 측정한다.
  기존 HTML·PNG cache-control을 동시에 바꾸지 않는다. 헤더 변경이 필요해지면 Stage 3 결과를
  근거로 범위 재승인을 받는다.
- **SPA 착지 유지**: `/api/share/{handle}/r/{revision}`을 사람이 열어도 기존 공개 profile을
  조회·표시하도록 client public route parser를 확장한다. revision은 profile API lookup에는
  전달하지 않는다.
- **Share Studio data source**: owner 화면에 이미 있는 `owner.updatedAt`과
  `usage.uploadedAt`을 Share Studio에 명시적으로 전달한다. 카드 설정 저장은 최신 owner를,
  submit은 최신 usage를 profile state에 반영한 뒤 공유 URL을 만들도록 기존 readiness 흐름을
  유지한다. timestamp가 없거나 invalid하면 고정 share URL로 fail safe한다.
- **플랫폼 gate**: Stage 3에서는 UI 전환 전 revision URL을 직접 붙여넣어 X와 LinkedIn을
  검증한다. 두 플랫폼에서 최신 revision B가 확인돼야 Stage 4의 전체 SNS 전환을 진행한다.
  실패하면 Threads·Facebook·Reddit까지 새 경로로 바꾸지 않고 결과를 보고한 뒤 설계 변경
  승인을 요청한다.
- **#84 비간섭**: task101 worktree와 검증 배포를 분리하고, production access·saved version·
  `main`은 건드리지 않는다. #84가 같은 문서나 Sites target을 먼저 변경하면 Stage 시작 전에
  최신 `devel`을 반영하고 충돌·배포 target을 다시 확인한다.

## 리스크

- **LinkedIn canonical 정규화**: 경로 revision도 stable URL로 합쳐 캐시할 수 있다. Stage 3에서
  requested URL, final HTML, Post Inspector 결과를 같은 시각에 기록하고 실패 시 UI rollout을
  중단한다.
- **X cold processing 지연**: 새 URL은 최신성을 얻는 대신 최초 이미지 처리 시간이 걸릴 수 있다.
  crawler fetch 성공과 composer 표시 시간을 분리해 측정하며 즉시성을 성공 조건으로 과장하지 않는다.
- **revision 계산 불일치**: runtime과 UI가 서로 다른 timestamp를 쓰면 공유 URL과 이미지 token이
  어긋난다. 공통 순수 함수와 동일 fixture로 owner·usage 변경을 검증한다.
- **stale URL 의미 혼선**: DB history가 없으므로 과거 revision URL이 과거 카드를 보장하지 않는다.
  stale 요청은 과거 snapshot으로 표현하지 않고 현재 revision으로 수렴시키는 계약을 테스트와 문서에
  명시한다.
- **private handle 열거**: revision path의 응답 차이가 존재 여부를 드러낼 수 있다. 현재 site root
  fallback과 sample image를 유지하고 private·missing 응답을 대조한다.
- **route 충돌**: `/api/share/{handle}/r/{revision}`이 backend API 또는 static asset으로 잘못 분류될
  수 있다. 공통 document request predicate와 세 runtime route matrix를 검증한다.
- **#84·동시 worktree 충돌**: 공유 문서와 운영 문서가 release 작업과 겹칠 수 있다. 각 Stage 시작 전
  origin/devel 및 활성 task 범위를 확인하고 production target을 공유하지 않는다.
- **외부 플랫폼 비결정성**: 로그인·지역·플랫폼 내부 캐시에 따라 결과가 달라질 수 있다. application
  증거와 수동 screenshot·시각을 함께 기록하고 provider 실패를 제품 응답 실패로 오판하지 않는다.

## 승인 요청 사항

- 위 포함·제외 범위와 5단계 gate 구성
- 쿼리 없는 `/api/share/{handle}/r/{revision}`을 실험 URL로 사용하는 계약
- revision token을 owner `updatedAt`과 usage `uploadedAt` 중 최신 epoch milliseconds로 유지하는 판단
- matching revision만 self canonical로 두고 stale URL은 현재 revision으로 수렴시키는 방향
