# 브라우저 locale 기반 전역 한·영 UI 정합성 구현 수행계획서

GitHub Issue: [#68](https://github.com/postmelee/codex-usage-profile/issues/68)
마일스톤: M100

## 목적

웹 UI의 사용자 노출 문구와 날짜·숫자·토큰 표시를 브라우저 언어에 맞춰 영어 또는 한국어로 일관되게 제공한다. `ko-*` 브라우저는 한국어, 그 밖의 브라우저는 영어를 사용하며 사용자가 별도 언어 선택기를 조작하지 않아도 모든 활성 화면, 상태, 접근성 문구가 같은 locale을 따르게 한다.

초기 문서 언어와 React 렌더링 언어를 일치시키고 실행 중 브라우저 언어 변경도 반영한다. 기존 카드 렌더러의 `?locale=ko` 계약과 Share Studio의 한·영 지원은 유지하면서 중복된 locale 판정과 포맷팅 경로를 하나의 웹 UI 계층으로 통합한다.

## 배경

현재 Share Studio와 일부 heatmap·카드 공유 경로는 한·영 locale을 개별적으로 처리하지만, Home, Profile, Settings, device approval, 메뉴, 오류·빈 상태에는 영어 문구가 직접 작성되어 있다. 그 결과 한 화면에서도 한국어 날짜 툴팁과 영어 UI가 혼재하며, `index.html`의 `lang="en"`도 실제 브라우저 언어와 동기화되지 않는다. 숫자와 날짜 포맷도 `en-US` 고정 또는 기능별 독립 구현이 섞여 있다.

로컬에 설치된 Codex 앱의 Profile 구현을 읽기 전용으로 조사한 결과, 안정적인 메시지 ID, 영어 기본 문구, 값 보간, locale 기반 formatter를 분리하는 구조를 확인했다. 이 task는 그 구조적 원칙만 참고하고 프로젝트가 소유할 수 있는 독립적인 메시지 사전과 formatter를 작성한다. 번들 코드를 복사하거나 라이선스가 불명확한 번역 자산을 재사용하지 않는다.

선행 작업인 #35와 PR #67에서 owner/public Profile, token activity, 카드 공유 흐름이 정리되었으므로 이 task에서 그 활성 UI 경로를 전역 locale 계층으로 묶는다. 다크·라이트 테마는 별도 Issue #69에서 다룬다.

## 범위

- `ko`와 `ko-*`는 한국어, 그 밖의 값은 영어로 정규화
- React 최초 렌더 전 `<html lang>` 설정과 `languagechange` 이벤트에 따른 UI·문서 언어 동기화
- Home·marketing landing, 공통 shell/header/menu, owner/public Profile, Settings, device approval, Share Studio의 사용자 노출 문구
- loading·empty·success·error 상태, 버튼·label·tooltip·ARIA 등 접근성 문구
- 날짜·숫자·token·heatmap tooltip·통계·공유 문구의 locale 일치
- Share Studio의 기존 한·영 사전과 card share locale 전달을 전역 locale 계층에 연결
- 영어·한국어·미지원 locale 및 실행 중 locale 변경에 대한 단위·통합·E2E 검증

## 설계 방향

- 새 국제화 의존성은 추가하지 않는다. 두 locale만 지원하고 이미 경량 사전 패턴이 있으므로 프로젝트 내부 모듈로 메시지 ID, 영어 fallback, 값 보간, 숫자·날짜 formatter를 제공한다.
- 메시지 사전은 기능별 컴포넌트에 흩어 두지 않고 `src/profile-ui/messages.js`에 모은다. locale 판정과 순수 formatter는 `src/profile-ui/i18n.js`, React 상태와 hook은 `src/profile-ui/LocaleProvider.jsx`로 분리한다.
- 메시지는 안정적인 의미 기반 ID를 사용한다. 영어 사전을 완전한 기준 사전으로 두고 한국어 누락 시 영어로 fallback하며, 누락된 ID가 화면에 그대로 노출되지 않도록 개발·테스트에서 검출한다.
- 최초 locale은 `navigator.languages`를 우선 순회해 지원 언어를 찾고, 없으면 `navigator.language`, 최종적으로 `en`을 사용한다. 브라우저 언어 목록에서 미지원 언어가 먼저 와도 뒤의 `ko-*`를 선택한다.
- React mount 전에 locale을 판정하여 `document.documentElement.lang`을 설정하고, Provider가 같은 값을 초기 상태로 사용한다. 이후 `languagechange`에서 다시 판정해 문구와 `lang`을 함께 갱신한다.
- `Intl.DateTimeFormat`과 `Intl.NumberFormat` 인스턴스는 locale·옵션별로 재사용한다. compact token 표시는 현행 의미와 단위를 유지하고, exact token count는 locale 구분자를 적용한다.
- 현재 `resolveShareLocale`, heatmap locale 판정, Share Studio 사전은 호환 adapter 또는 공통 함수로 연결해 외부 호출 계약을 보존한다. 카드 이미지 요청의 기존 `?locale=ko`/영어 기본 계약은 변경하지 않는다.
- 알려진 API 상태·오류 코드는 locale 메시지로 매핑하고, 알 수 없는 서버 문자열은 그대로 사용자에게 노출하지 않고 locale별 일반 오류로 fallback한다. 진단에 필요한 코드나 HTTP 상태는 데이터 계약으로 유지하되 번역하지 않는다.
- 활성 route와 공유 컴포넌트를 기준으로 문구를 이관한다. 사용되지 않는 legacy UI는 import graph 또는 계약 테스트에서 실제 사용이 확인될 때만 변경해 불필요한 범위 확대를 피한다.
- Codex 앱에서 확인한 message ID·default fallback·값 보간 방식은 구조 참고 자료로만 사용하고, 모든 문구와 코드는 이 저장소에서 독립 작성한다.

## 리스크

- **초기 언어 깜빡임**: React 렌더 전 `lang`과 초기 locale을 같은 resolver로 설정해 첫 화면부터 일치시킨다.
- **문구 누락·혼합 locale**: 영어 기준 사전 키 일치 테스트, 활성 화면 E2E, source inventory를 함께 사용한다.
- **formatter 의미 회귀**: compact/exact token과 날짜 범위의 현행 의미를 fixture로 고정하고 locale별 출력만 변경한다.
- **오류 메시지 정보 손실**: 알려진 오류는 안정적인 코드 기준으로 번역하고 알 수 없는 문자열은 안전한 일반 문구로 표시하되 진단용 상태 코드는 유지한다.
- **기존 공유·카드 계약 손상**: 기존 helper API는 adapter로 보존하고 card renderer 자체는 변경하지 않은 채 양 locale 회귀 테스트를 수행한다.
- **범위 팽창**: 테마, 수동 선택기, CLI, backend, 공식 제품 문서는 제외하고 발견된 별도 요구는 후속 Issue로 분리한다.
- **외부 코드 권리 문제**: Codex 앱 구현은 구조적 참고에만 사용하고 코드와 번역은 독립 작성한다.

## 승인 요청 사항

- **권고안 A — 경량 내부 국제화 계층**: 신규 라이브러리 없이 메시지 ID·영어 기준 사전·한국어 사전·fallback·formatter·React Provider를 저장소 내부에 구현한다.
- 브라우저 선택 규칙을 `navigator.languages`의 첫 지원 locale → `navigator.language` → `en`으로 확정하고 `ko-*`만 한국어로 처리한다.
- 수동 언어 선택기와 locale 저장은 만들지 않고 `languagechange`를 실시간 반영한다.
- 최초 React 렌더 전과 이후 모두 `<html lang>`을 UI locale과 동기화한다.
- 알려진 오류는 번역하고 알 수 없는 서버 문자열은 locale별 일반 오류로 대체한다.
- 기존 카드 렌더러는 범위에서 제외하고 웹 UI locale을 기존 card/share locale 계약에만 전달한다.
- Codex 앱 코드는 message ID·fallback·보간 구조만 참고하며 직접 복사하지 않는다.
- 위 범위와 4개 Stage, 문서 위치 판단, production 미배포 조건으로 구현계획서 작성 단계에 진입한다.

승인되면 `task_m100_68_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
