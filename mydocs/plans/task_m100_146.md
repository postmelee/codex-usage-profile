# Task #146 수행계획서 — 라이트 카드 Border Beam 테마 대비 보정

GitHub Issue: [#146](https://github.com/postmelee/codex-usage-profile/issues/146)
마일스톤: M100

## 목적

라이브 프로필 미리보기와 저장 GIF의 라이트 카드에서 Border Beam 애니메이션이 흰색 배경과 섞여 약하게 보이는 문제를 해결한다. 다크 카드는 기존 발광형 Ocean Beam과 승인 golden을 그대로 유지하고, 라이트 카드는 다크와 동일한 `md` 둘레 회전·위상·폭·4.8초 주기를 사용하되 graphite/blue 색상과 대비 강도만 라이트 전용으로 조정한다. 카드 크기 및 전체 이미지 비율도 동일하게 유지한다.

Task #146을 병합한 뒤 보류 중인 릴리스 Task #144가 새 exact-main 후보를 다시 고정하고 Stage5 검증과 production 배포를 이어갈 수 있도록 검증 근거와 인계 조건도 남긴다.

## 배경

Task #144의 Stage5 합성 스모크 중 라이트 카드의 애니메이션 대비가 약하다는 문제가 발견되었다. 현재 `CardImageFrame`은 정규화된 카드 테마를 `data-card-theme`에 반영하지만, 이를 감싸는 `BorderBeam`은 `theme` 속성을 받지 않아 컴포넌트 기본값인 다크 테마를 사용한다. 그 결과 라이트 카드에도 흰색 계열 Beam이 그려져 카드 배경과 구분하기 어렵다.

Task #39에서 웹과 GIF가 공유하는 애니메이션 프리셋은 `4.8초 / ocean / brightness 1.05 / md / strength 0.82`로 고정되었다. Stage 1은 라이브 웹 컴포넌트의 테마 소유권 전달 누락을 보정했지만, Stage 2의 작업지시자 시각 검수에서 라이브러리 내장 라이트 `md` Beam과 기존 저장 GIF 모두 효과를 식별하기 어려운 것으로 확인되었다. 계산 스타일 문자열과 서로 다른 프레임 해시만으로 시각 수용성을 통과 처리한 기존 Stage 2 판단은 철회한다.

2026-08-30 작업지시자 승인에 따라 범위를 확장한다. 다크는 기존 라이브 프리셋과 승인 Chrome golden을 보존하고, 라이트는 흰 배경에서 명도를 어둡게 깎는 전용 색상·opacity 합성과 Chrome golden을 사용한다. 첫 보정에서 라이트를 하단 좌→우 `line` 모션으로 바꾼 것은 요구사항 오해로 거절됐다. 최종 방향은 두 테마가 같은 `md` geometry·둘레 회전·위상·프레임·주기를 공유하고 색상·대비 레이어만 분리하는 것이다.

## 범위

### 포함

- `MarketingCardPreview`에서 카드 테마를 한 번 정규화하고 `BorderBeam`과 `CardImageFrame`에 동일한 값으로 전달
- 라이트 카드가 라이브러리의 라이트 테마 Beam 색상·그림자 대비를 사용한다는 소스/브라우저 계약 검증
- 다크 카드의 Beam 프리셋, 계산 스타일과 동작이 기존과 동일하다는 회귀 검증
- 라이트·다크 카드 모두 이미지 원본 크기 `1497×918`, 표시 비율 `499:306`, 프레임 크기·곡률이 동일하다는 검증
- 카드 테마 전환 중 기존 노드 유지, 로딩 handoff, reduced-motion 비활성화 계약 회귀 검증
- 라이트 라이브 Beam도 다크와 같은 `md` 둘레 회전을 사용하고 graphite/blue 색상·opacity만 분리하며 다크 라이브 프리셋은 무변경 유지
- GIF export 요청에 정규화된 카드 테마를 명시적으로 전달하고 Worker가 테마별 Beam asset을 선택
- 기존 다크 `ocean-beam-golden-v1` binary·렌더 결과 보존과 동일 `md` phase의 신규 라이트 대비 Chrome golden 추가
- 라이트 저장 GIF의 다크와 동일한 전체 96프레임 둘레 이동, 육안 식별성, 투명 tight canvas와 출력 계약 검증
- Task #144 재개 시 새 병합 커밋을 exact-main 후보로 다시 고정해야 한다는 인계 기록

## 설계 방향

- `MarketingCardPreview`에서 `normalizeCardTheme(cardTheme)` 결과를 단일 지역 값으로 만들고 `BorderBeam.theme`과 `CardImageFrame.cardTheme` 양쪽에 전달한다. 표시 카드와 효과가 서로 다른 테마를 해석할 수 없게 한다.
- 공통 `md` 모션 위에 테마별 시각 프리셋을 둔다. 다크는 기존 값을 유지하고 라이트도 같은 conic mask·둘레 회전·4.8초 phase를 사용하되 graphite stroke, 더 선명한 Ocean 색과 opacity scale만 조정한다.
- 라이브 라이트 프리셋은 카드 크기나 wrapper 구조를 바꾸지 않는 `BorderBeam` 입력과 beam layer CSS 변수로 제한한다. 정지 프레임 문자열이 아니라 한 주기 사분면 캡처와 실제 픽셀 대비로 수용성을 판단한다.
- GIF controller와 Worker 사이에 `cardTheme`을 별도 필드로 전달한다. 다크는 기존 golden을, 라이트는 동일 `md` phase로 캡처한 라이트 대비 Chrome golden을 선택하며 둘 다 동일 encoder와 출력 계약을 사용한다.
- 다크 테마는 기존 기본 다크 프리셋과 동일한 속성 및 계산 스타일을 유지해야 한다. 라이트 수정의 부수 효과로 다크 Beam의 색상, 밝기, 채도, 속도, 크기, 강도를 바꾸지 않는다.
- 카드 이미지와 외곽 프레임의 DOM 구조 및 CSS 기하는 변경하지 않는다. 자동화 검증에서 라이트·다크의 원본 크기, 종횡비, 외곽 프레임 치수를 직접 비교한다.
- Task #146에서는 로컬 production build와 실제 Share Studio GIF 생성으로 시각 QA를 완료한다. #144가 이미 고정한 exact-main 후보를 벗어난 원격 Stage5 변경은 하지 않으며, #146 PR 병합 뒤 #144에서 후보 재고정·main 승격·Stage5 재배포·원격 QA를 다시 수행한다.

## 리스크

- **라이트 대비가 여전히 약할 가능성**: 정지 프레임 문자열이 아니라 한 주기 픽셀 대비와 작업지시자 시각 검수로 판단하고 수용 전 Stage 2를 완료하지 않는다.
- **테마별 GIF cache 혼선**: source key와 Worker request 양쪽에 canonical `cardTheme`을 포함하고 export preset version을 올린다.
- **라이트 golden과 라이브 불일치**: 동일 installed Chrome·동일 라이트 `md` effect config에서 96 phase를 캡처하고 대표 frame signature·사분면·loop seam을 고정한다.
- **다크 표현 회귀**: 수정 전후 다크 속성과 의사 요소 계산 스타일을 비교하고, 다크/라이트 동일 기하 검증을 자동화한다.
- **테마 전환 중 효과와 이미지 불일치**: 정규화 값을 단일 소유권으로 묶고 기존 decoded-preview handoff 테스트에 Beam 테마 검증을 추가한다.
- **Task #144 후보 드리프트**: #146 브랜치에서 원격 Stage5를 변경하지 않는다. 병합 뒤 #144가 exact-main 후보를 새로 고정하고 main 승격 및 배포 검증을 다시 수행한다.
- **선택자 또는 계산 스타일 테스트의 취약성**: 라이브러리 내부 구현 전체를 복제하지 않고 공개 속성, 핵심 색상 계열, 애니메이션 활성 상태와 기하 계약만 검증한다.

## 승인 요청 사항

- 라이브 미리보기에서 카드와 Border Beam이 동일한 정규화 테마를 사용하도록 하는 설계
- 다크 라이브/GIF를 보존하고 라이트 라이브·GIF는 같은 모션 위에서 색상·opacity 합성만 분리하는 확장 범위
- `998×612 / 20fps / 96프레임 / 4.8초`와 카드 크기·비율을 보존하는 범위
- Task #146에서는 로컬 production build QA까지만 수행하고, 원격 Stage5·production 검증은 병합 후 Task #144에서 새 exact-main 기준으로 재개하는 인계 순서
