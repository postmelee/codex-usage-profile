# Task M100 #19 수행계획서

GitHub Issue: [#19](https://github.com/postmelee/codex-usage-profile/issues/19)
마일스톤: M100

## 목적

이 task의 목적은 `UsageSnapshot v2`를 `codex-usage-analyzer`, `codex-usage-profile`, 향후 별도 카드 웹페이지가 공유할 수 있는 공용 데이터 계약으로 정의하는 것이다.

완료 후에는 로컬 분석기가 어떤 필드를 생성해야 하는지, 웹 서비스가 어떤 필드를 저장/조회/렌더링해야 하는지, GitHub 로그인에서 가져오는 사용자 표시 정보가 어디에서 병합되는지 명확해야 한다. 특히 total tokens, input/output/cache breakdown, favorite model, top skills/plugins, profile activity stats를 한 계약 안에서 다루되 GitHub username/avatar/bio 같은 GitHub-facing fields는 analyzer payload에 넣지 않는 경계를 확정한다.

## 배경

- M100 MVP 흐름은 GitHub 로그인, 로컬 CLI submit, 공개 프로필 조회, README 카드 이미지 갱신으로 확장되었다.
- 기존 snapshot v1은 Codex 프로필 UI 재현을 위한 최소 필드에 집중했다. 이제 token breakdown, model usage, favorite model, 향후 카드형 프로필에 필요한 공격/스탯 매핑까지 고려해야 한다.
- 사용량 분석 책임을 `codex-usage-analyzer`로 분리하려면, 먼저 analyzer가 출력할 JSON 계약과 profile 웹 서비스가 병합할 GitHub profile data 경계를 고정해야 한다.
- #20은 실제 analyzer 레포/패키지 분리 작업이므로, #19에서는 구현보다 계약, 책임 경계, migration 기준을 먼저 확정한다.

## 범위

### 포함

- `UsageSnapshot v2` 최상위 구조와 필수/선택 필드 정의
- Codex profile-style 필드 정리
  - total tokens
  - peak tokens
  - longest task
  - current/longest streak
  - daily usage
  - activity insights
  - top skills/plugins
- token breakdown 필드 정리
  - input tokens
  - output tokens
  - cache read tokens
  - cache write tokens
  - reasoning tokens
- model usage 필드 정리
  - favorite model
  - model별 사용량
  - 일자별/집계별 확장 가능성
- analyzer 책임과 profile 웹 서비스 책임 분리
- GitHub-facing fields 병합 위치 정의
  - GitHub login
  - avatar
  - display name
  - bio
  - profile URL
- snapshot v1과 v2의 compatibility/migration 방침
- #5, #6, #17, #15, #20에 넘길 의존 관계와 후속 기준 정리

### 제외

- `codex-usage-analyzer` 새 레포 생성
- analyzer SDK/CLI 스캐폴드 구현
- 실제 로컬 사용량 parser 구현
- GitHub OAuth UI 또는 settings UI 구현
- README 카드 PNG endpoint 구현
- 향후 카드 웹페이지 레포 생성
- npm publish 자동화

## 설계 방향

- `schemaVersion: 2`를 기준으로 v1과 명확히 구분한다.
- analyzer snapshot은 사용량 분석 결과만 담는다. GitHub OAuth identity, GitHub avatar, GitHub bio, GitHub access token, 서비스 session 정보는 담지 않는다.
- 웹 서비스는 GitHub login/session으로 얻은 owner/profile record와 analyzer snapshot을 병합해 공개 profile/card view model을 만든다.
- 필드 이름은 외부 소비자가 이해하기 쉬운 domain name을 우선한다. 단, 기존 v1 selector와 UI mapping을 완전히 끊지 않도록 migration alias 또는 변환 정책을 계획한다.
- token breakdown은 전체 합계와 일자별 확장 가능성을 둘 다 고려한다. v2 첫 구현에서는 총합 필드를 필수 후보로, per-day/per-model breakdown은 선택 필드 후보로 검토한다.
- model usage와 top skills/plugins는 향후 analyzer가 데이터 원천별로 채울 수 있도록 source metadata와 confidence/availability 표현을 검토한다.
- credential-like 값은 v2 계약에서도 명시적으로 금지한다.

## 잠정 단계

- **Stage 1 — v1 계약과 후속 요구사항 정리**
  - 기존 snapshot v1 필드, 현재 프로필 UI 소비 필드, #5/#6/#20이 요구하는 v2 필드를 표로 정리한다.
  - GitHub-facing fields와 analyzer fields의 경계를 초안으로 고정한다.
- **Stage 2 — UsageSnapshot v2 공식 계약 문서 작성**
  - `docs/usage-snapshot-v2.md`에 top-level schema, field semantics, required/optional 기준, 금지 필드, migration 규칙을 작성한다.
  - token breakdown, model usage, top skills/plugins, activity stats를 포함한다.
- **Stage 3 — Runtime contract skeleton과 검증 추가**
  - 필요한 범위에서 v2 validator/type/fixture를 추가하거나 v1 schema와 공존하는 구조를 만든다.
  - credential-like 값 차단과 필수 필드 validation을 테스트한다.
- **Stage 4 — 기존 이슈 의존성/README 연결 정리**
  - README 또는 관련 문서에 analyzer/profile 책임 경계를 짧게 연결한다.
  - #5/#6/#17/#15/#20이 이어받을 기준과 미결정 항목을 단계 보고서/최종 보고서에 정리한다.

  - README 링크와 후속 이슈 handoff 확인
  - `git diff --check`

### 통합 검증

- `UsageSnapshot v2` 계약이 현재 profile UI, README card, 향후 카드형 웹페이지가 필요한 데이터를 설명한다.
- analyzer payload에 GitHub username/avatar/bio 같은 GitHub-facing fields가 포함되지 않는다.
- web profile layer가 GitHub profile record와 analyzer snapshot을 병합한다는 책임 경계가 문서화된다.
- #20 analyzer 분리 작업이 바로 SDK/CLI 공개 API를 설계할 수 있을 정도로 입력/출력 계약이 명확하다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **계약 과확장**: 현재 확보 가능한 데이터보다 많은 필드를 필수로 만들면 analyzer 구현이 막힌다. 확실한 핵심 필드만 required로 두고 source별 가용성 차이는 optional 또는 availability metadata로 다룬다.
- **GitHub identity 혼입**: 카드 UI 요구사항 때문에 GitHub profile data를 snapshot에 넣고 싶어질 수 있다. analyzer snapshot과 web owner/profile record를 분리해 저장/렌더링 단계에서 병합한다.
- **v1 회귀**: 기존 profile preview와 selector가 v1에 의존한다. v2 skeleton을 추가하더라도 v1 path를 깨지 않도록 compatibility layer를 둔다.
- **공식 문서 위치 신설**: 현재 `docs/`가 없다. 이 task에서 `docs/` 신설을 승인받되, 내부 조사 노트는 `mydocs/tech/`에 남겨 문서 성격을 분리한다.
- **후속 레포 경계 불명확**: #20 전에는 실제 analyzer 패키지를 만들지 않는다. #19는 패키지 코드 분리 대신 계약과 책임 경계까지만 확정한다.

## 승인 요청 사항

- `docs/usage-snapshot-v2.md`를 공식 데이터 계약 문서로 신설하는 것을 승인해 달라.
- `mydocs/tech/task_m100_19_snapshot_v2_notes.md`를 내부 조사/의사결정 노트로 함께 작성하는 것을 승인해 달라.
- #19에서는 analyzer 레포 생성과 실제 parser 구현을 제외하고, v2 계약 문서와 필요한 최소 validator/type/test skeleton까지만 다루는 것을 승인해 달라.
- GitHub-facing fields는 analyzer snapshot에서 제외하고 웹 서비스 GitHub login/profile layer에서 병합하는 책임 경계를 승인해 달라.

승인되면 `task_m100_19_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
