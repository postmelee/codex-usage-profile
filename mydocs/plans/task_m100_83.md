# Task #83 수행계획서 — 누적 Sites 후보 production artifact preflight와 owner-only 배포 검증

GitHub Issue: [#83](https://github.com/postmelee/codex-usage-profile/issues/83)
마일스톤: M100

## 목적

Task #74·#78·#81이 누적된 Sites 후보에서 production artifact에 포함된 절대 로컬 경로를 제거하고, 동일 문제가 다시 배포 archive에 유입되지 않도록 재현 가능한 검증 경계를 고정한다. 보정 뒤에는 검증한 exact source commit과 그 commit에서 만든 artifact만 기존 Sites project의 owner-only saved version으로 배포한다.

owner-only 후보에서 D1 migration `1..5` readiness, maintenance 비활성화, OAuth·CLI·private preview·publish/unpublish·README 카드·canonical OG 문서·social image 계약을 확인한다. 별도 승인된 Gate B에서만 잠시 public access를 열어 `/api/share/{handle}` 캐시 헤더와 submit 직후 `og:image?v=` 갱신을 실측하고, 즉시 owner-only·private·credential/data 정리 baseline으로 복원한다. 완료 결과는 후속 릴리스 [#84](https://github.com/postmelee/codex-usage-profile/issues/84)의 명시적 선행 증적으로 넘긴다.

## 배경

현재 `npm run build:production`과 `npm run verify:sites-fullstack`은 통과하지만 `npm run verify:sites-production`은 `dist/server/.vite/manifest.json`의 `/Users/...` 경로 때문에 실패한다. 이 manifest에는 renderer Wasm과 글꼴 원본의 절대 경로가 기록되며, Sites packaging helper는 `dist/` 전체를 archive에 포함하므로 검증을 우회해 배포할 수 없다. production verifier의 절대 경로 차단은 credential·로컬 환경 유출을 막는 독립 보안 경계이므로 완화하지 않는다.

`/api/share/{handle}`은 짧은 shared-cache 지시자를 선언하지만 application이 Workers Cache API를 직접 사용하지 않는다. ChatGPT Sites 외부 계층이 동적 HTML에 적용하는 실제 캐시는 로컬 계약만으로 확정할 수 없으므로, 보정 코드에 추측성 cache configuration을 추가하지 않고 Gate B에서 `CF-Cache-Status`, `Age`, `x-request-id`, `og:image?v=`를 시간 순서로 측정한다.

Gate A 1차 실행 뒤 production baseline은 saved version 8, owner-only custom access,
migration `1..2`, maintenance disabled, operator secret absent다. package에 migration
SQL이 있어도 Sites deployment가 application `schema_migrations`를 자동 갱신하지
않았고 protected readiness가 `migration_not_ready`로 중단됐다. 원격 mutation은
단계별 read-only snapshot과 별도 Gate 승인 뒤에만 수행하며, application rollback은
이전 saved version을 사용하고 data/schema downgrade는 수행하지 않는다.

source 보정 version 9의 첫 protected `migrate`는 local real-workerd와 달리
production에서 generic `maintenance_unavailable`로 중단됐다. access를 즉시
owner-only로 복원하고 environment revision 63의 disabled/secret-absent/
service `normal`로 같은 version을 재배포했다. Sites가 package migration을
물리 schema에 선적용했지만 application metadata에는 기록하지 않은 경우를
안전하게 수용하도록 known column contract exact-match reconciliation을 추가한다.

hosted schema reconciliation을 각각 `PRAGMA table_info`와 `sqlite_master` exact
DDL fragment로 축소한 version 10·11도 protected `migrate`에서 같은 generic
오류로 중단됐다. 각 실패 뒤 access revision 33·35의 owner-only와 environment
revision 65·67의 disabled/secret-absent/service `normal` baseline을 복원했다.
추가 schema 추측은 중단하고, 다음 후보는 inspection·reconciliation·apply·
verification 경계별 고정 오류 코드만 반환한다. provider 오류, SQL, schema 원문,
identity는 응답에 포함하지 않으며 식별된 한 단계만 후속 보정한다.

version 12의 제한된 진단 결과는 `migration_apply_unavailable`이었다. inspection과
reconciliation은 통과하므로 다음 후보는 generic runner의 initialize·read·batch
진행 상태, exact manifest version과 SQL 적용/metadata-only 구분만 추가한다. D1
공식 batch 계약과 달리 DDL 자체가 금지된다는 추측은 채택하지 않고, 오류 원문과
statement 내용은 계속 반환하지 않는다.

version 13의 세부 진단은 public policy 전파 확인 뒤
`migration_apply_sql_v1_unavailable`을 반환했다. 이는 hosted physical schema가
적용됐지만 application `schema_migrations`가 비어 있어 migration 1을 재실행한
경로다. base migration 1·2의 모든 explicit table/index DDL을 `sqlite_master`와
normalized exact-match하고, migration 3~5의 승인된 additive column fragment를
제거한 base contract까지 일치할 때만 metadata-only로 기록한다. 일부 object만
존재하거나 drift가 있으면 mutation 전 conflict로 중단한다.

Stage 4 Gate B 1차 public smoke에서는 `/`, 비인증 API와 missing media 경계가
각각 `200`, `401`, `404`로 통과했지만 extension 없는 `/u/{handle}` HTML이 public
access에서도 Worker에 도달하지 않고 `/`로 `307` 전환됐다. 즉시 custom
owner-only access revision 47, environment revision 77의 service `normal`,
maintenance disabled/secret-absent baseline으로 복원했고 anonymous health `401`,
protected health `200`, operator route `404`를 재확인했다. owner-only protected
진단에서 기존 `/?profile={handle}`은 `200`, `.html` 대안은 `404`였으므로 실제
Sites가 전달하는 query compatibility 경로에 동적 metadata를 연결하는 Stage 3.7
보정 뒤에만 Gate B를 다시 요청한다.

Stage 3.7 source commit의 owner-only version 15 배포는 성공했지만 protected
`/?profile={handle}` GET/HEAD는 Worker structured event 없이 정적 `index.html`을
반환했고 canonical/OG/Twitter metadata가 없었다. 같은 version에서 기존
`/u/{handle}`은 Worker가 동적 fallback metadata를 생성했고 `/api/...` 요청도
Worker에 도달했다. 즉 root query compatibility 가정이 production에서 반증됐으므로
Stage 3.8에서 Sites가 확인된 Worker dispatch prefix인 `/api/share/{handle}`을
canonical HTML로 사용한다. version 15는 계속 owner-only·normal·maintenance
disabled/secret-absent 상태이며 readiness bridge와 Gate B는 시작하지 않았다.

Stage 3.8 exact commit의 owner-only version 16 배포, protected API share metadata와
migration `1..5` readiness는 통과했다. 그러나 Gate B 2차 public smoke에서 기존
version 7 publication의 README `card.png`는 `200`인 반면 HTML이 가리키는
`social.png`와 version query URL은 `404`였다. missing HTML fallback도 같은 운영자
social object에 의존해 깨진 이미지를 선언했다. public access를 즉시 owner-only로
복원하고 anonymous `401`, protected health `200`, operator route `404`, normal/
maintenance disabled/secret-absent baseline을 재확인했다. 기존 publication을 실제
계정 mutation으로 재발행하는 임시 조치는 하지 않고 Stage 3.9에서 social object
가용성을 확인해 개인화 이미지 또는 packaged static fallback만 선언한다.

Stage 3.9 exact source `4541e3be7fc1dce6d7e54bbe01ce279d1ceba05f`의 saved
version 17은 packaged social fallback과 public media 계약을 owner-only에서 확인한
뒤 최종 Gate B를 통과했다. anonymous/private/missing 경계, README dark/light ×
en/ko, canonical OG/Twitter, social GET/HEAD/304와 publish/unpublish 리비전 신선도가
유지됐다. 반복 요청에서 shared-cache HIT나 stale `Age` 증거는 없었지만 application
revision과 media ETag가 즉시 갱신돼 cache source 변경을 release blocker로 분류하지
않았다. X 작성 화면의 실제 링크 카드도 작업지시자가 정상 표시를 확인했다. 측정 뒤
disposable state를 정리하고 access를 custom owner-only로 복원했다.

Gate B 뒤 발견한 legacy `/profile` Sites front-door 이탈은 Stage 3.10에서
`/?view=profile` canonical owner route로 보정했다. exact source
`e431cc88ba73b02341a170fe5c38117d4552e42a`를 saved version 18로 owner-only 배포해
메뉴, 공개 CTA, 실제 OAuth 복귀와 protected owner profile을 집중 확인했다. 현재
access revision 56, environment revision 85, owner 1명·추가 user/group 0명,
maintenance disabled/operator secret absent/service normal이며 readiness는 exact
`[1,2,3,4,5]`다. Stage 3.10은 공개 profile/cache/OG/media source를 변경하지 않아
Gate B public mutation을 반복하지 않았고, 영구 public Gate C와 `main` 릴리스는
#84로 넘긴다.

Stage 4 완료 뒤 version 18 owner-only 후보를 실제 브라우저에서 재검증하는 과정에서
동적 카드 PNG의 준비 상태와 UI motion이 분리된 회귀를 확인했다. 공개 profile JSON이
준비되면 카드 이미지의 `load`·`decode` 완료 여부와 무관하게 intro의 900ms flip이
시작되고, 공개·소유자 profile과 Share Studio는 홈에 이미 있는 카드 Skeleton을
활성화하지 않는다. 소유자 profile에서는 테마·언어 draft 변경 시 이전 카드를
보존하거나 pending 상태를 알리지 않아 서버 렌더링 지연이 빈 화면 또는 늦은 교체로
보인다. 이는 공개 공유 링크의 첫 진입과 카드 편집이라는 #84 핵심 사용자 흐름을
직접 훼손하므로 최종 보고를 중단하고 Stage 4.1 release blocker 보정으로 다룬다.

Stage 4.1 local source 검증 뒤 실제 후보의 카드와 GitHub 계정 avatar를 대조하는
과정에서 카드 내부 avatar만 initials fallback으로 남는 현상을 확인했다. 서버 avatar
loader는 외부 fetch 실패를 모두 `null`로 축약하고 그 실패까지 LRU에 저장하므로 한 번의
일시 장애가 같은 Worker instance의 이후 렌더에도 전파된다. 동시에 공통 card readiness는
component instance마다 Blob URL을 새로 만들고 unmount 때 즉시 폐기해, 같은 tab에서 이미
decode한 동일 source를 profile·공유 intro·Share Studio·홈 사이에 재사용하지 못한다.
응답 cache header와 publication 계약은 정상이며 이 문제는 서버 avatar 복구성과 client
resource lifetime의 결함이므로 Stage 4.2 release blocker 보정으로 분리한다.

Stage 4.2 exact source를 owner-only saved version 19로 배포한 뒤 실제 Workerd에서
avatar URL 자체는 `200 image/jpeg`인데 `fetch(..., { redirect: "error" })`만
`TypeError`로 실패하는 호환성 결함을 확인했다. 같은 후보의 Share Studio 첫 진입은
이미 decode된 owner card를 즉시 숨기고 별도 public card를 fetch·decode하는 동안
Skeleton을 hero 위치에 노출해, 준비 완료 시 카드가 뒤늦게 handoff motion에 합류한다.
이는 재진입 cache와 별개인 최초 공유 연속성 결함이므로 Stage 4.3에서 Workerd redirect
호환과 source-image handoff를 함께 보정한다.

Stage 4.3 exact source를 owner-only saved version 20으로 배포한 뒤 실제 Share Studio의
warm handoff를 프레임 단위로 확인했다. source card가 중앙에 안착한 뒤 public target으로
교체되는 순간 기본 image crossfade가 새로 시작해 opacity가 다시 낮아지므로 한 번
깜빡인다. 공개 profile의 구조형 Skeleton도 각 placeholder가 아니라 page wrapper 하나에
sheen이 적용돼 큰 박스가 움직이는 것처럼 보이고, 소유자 profile은 같은 정보 구조임에도
텍스트 loading state를 사용한다. Stage 4.4는 warm target의 중복 fade를 제거하고 공개·
소유자 profile의 identity-free 구조형 Skeleton과 reduced-motion 계약을 통합한다.

## 범위

### 포함

- `dist/server/.vite/manifest.json` 절대 경로 유입 원인과 runtime 필요성 확인
- 불필요한 build metadata 제외 또는 재현 가능한 경로 정규화 중 최소 보정
- production verifier의 absolute-path·credential·secret 차단 계약 유지
- build 결과와 Sites package archive 모두에 대한 금지 문자열·파일 목록 검사
- 전체 테스트, E2E, production build, full-stack/production artifact 검증
- 검증한 exact commit과 동일 artifact의 기존 Sites project owner-only saved version 배포
- D1 migration `1..5` 적용 상태와 protected readiness exact-match 확인
- production Worker에 manifest exact migration SQL을 bundle하고 identity-less
  maintenance `migrate` operation으로 pending known migration만 적용
- maintenance disabled, operator secret absent, operator route `404`, `/healthz` `200` 확인
- owner-only OAuth/session/logout, packed CLI login/submit/revoke, private preview, 설정 저장과 publish/unpublish smoke
- dark/light × en/ko README PNG와 `social.png`의 GET/HEAD/304/404 검증
- Sites 호환 `/?profile={handle}` canonical·OG·Twitter metadata와
  private/missing 동일 폴백 검증
- production Worker 전달이 확인된 `/api/share/{handle}` canonical·OG·Twitter
  metadata와 private/missing 동일 폴백 검증
- 기존 publication의 social object 가용성·README authority 정합성 확인과
  2400x1260 packaged static social fallback
- HTML 공유 URL은 query compatibility 경로로, README/social media URL은 기존
  `/u/{handle}/card.png`·`/u/{handle}/social.png`로 분리
- 별도 승인된 Gate B public smoke, cache/revision 실측과 즉시 owner-only 원복
- disposable profile/token/session/D1/R2 정리와 recent error event 비노출 확인
- cache 최적화 필요성 판단과 #84 handoff 증적 기록
- 홈·공개 profile·공개 card intro·소유자 profile·Share Studio의 동적 카드 PNG에
  공통 loading/ready/error와 `load`·`decode` readiness 계약 적용
- 공개 profile의 identity-free 구조형 loading Skeleton과 card aspect-ratio 공간 예약
- 준비되지 않은 카드의 flip/handoff/tilt/beam 중단, 준비 완료 뒤 motion 시작과
  `prefers-reduced-motion` 대체 전환
- 소유자 card draft 변경 시 마지막으로 준비된 이미지를 유지하고 새 이미지를
  preload한 뒤 교체하며 stale completion race를 차단
- private preview render/cache key와 in-flight 중복을 감사하고 설정만 바뀐 경우
  avatar cache를 불필요하게 무효화하지 않는 최소 성능 보정
- delayed/failed image와 source 교체를 재현하는 Node/UI E2E 및 owner-only 실제 smoke
- GitHub avatar의 transient fetch 실패 1회 재시도, 실패 결과 비캐시와 개인정보 없는
  구조형 관측 이벤트
- 동일 tab의 card source별 decoded Blob·in-flight를 공유하는 bounded memory cache,
  owner scope 격리와 logout/source revision 무효화
- 홈을 포함한 card image 소비자가 같은 shared resource contract를 사용하고, 즉시 화면
  전환·Share Studio 재진입에서 동일 source를 다시 요청하지 않는 회귀 검증
- Workerd가 지원하는 `redirect: "manual"` avatar fetch와 3xx non-ok 거부를 결합해
  allowlisted GitHub avatar host 밖으로 redirect를 따라가지 않는 hosted 호환 경계
- Share Studio 최초 진입에서 이미 decode된 source card bitmap을 handoff layer로 유지하고,
  public card가 준비되면 target에서 원자적으로 교체하는 warm-interaction 계약
- owner/public card URL·cache key와 응답 header는 계속 분리하고, cold direct entry의
  Skeleton 및 각 route의 독립 profile load는 유지

## 설계 방향

- **차단 계약 유지**: `verify:sites-production`의 절대 경로 패턴을 완화하거나 해당 manifest를 검사 예외로 만들지 않는다. production runtime과 Sites package에 필요하지 않은 metadata라면 build 완료 시 artifact에서 제거하고, 필요하다면 절대 경로만 안정적인 상대 식별자로 정규화한다.
- **runtime 필요성부터 증명**: manifest를 제거하기 전에 `wrangler.json`, Worker entry, emitted JS/Wasm/font 참조와 package archive를 대조한다. runtime이 참조하지 않는다는 테스트 증거가 있을 때만 제외한다.
- **최소 source 변경**: 우선 후보는 `build/sites-fullstack-vite-plugin.js`와 관련 회귀 테스트다. Cloudflare plugin hook 순서 때문에 정리 시점이 불안정하면 `vite.sites-fullstack.config.js`의 plugin ordering 또는 명시적 post-build 경계를 함께 검토하되, Worker·renderer 제품 코드는 수정하지 않는다.
- **verifier 독립성**: full-stack verifier는 runtime shape와 migration manifest를, production verifier는 exact binding·migration allowlist·secret/path·size를 계속 독립 검증한다. fix가 verifier를 약화하는 방식이면 채택하지 않는다.
- **exact provenance**: local 검증이 끝난 commit을 source로 push하고 같은 commit에서 다시 만든 `dist/`를 Sites helper로 package한다. saved version의 `commit_sha`, artifact와 단계 보고서의 candidate SHA를 일치시킨다.
- **migration/readiness 분리**: migration `3..5` 적용은 mutation이며 readiness는 read-only다. production Worker가 manifest의 exact SQL만 bundle하고 maintenance `migrate`는 owner/data selector와 arbitrary SQL을 받지 않는다. 적용 전 unexpected version을 read-only로 거부하고, owner-only·maintenance window에서 적용한 뒤 `appliedVersions`와 `expectedVersions`가 순서까지 `[1,2,3,4,5]`인지 확인한다. missing·unexpected version이면 기능 smoke와 public Gate를 중단한다.
- **hosted schema reconciliation**: missing metadata `3..5`의 known column이
  이미 있으면 table/column type, nullability, default와 CHECK fragment가 candidate
  contract와 exact-match할 때만 migration metadata를 기록한다. column이 없으면
  bundled SQL을 적용하고, partial 또는 drifted schema는 mutation 전 conflict로
  중단한다.
- **제한된 migration 단계 진단**: generic provider 실패를 반복 추측하지 않도록
  inspection·reconciliation·apply·verification 경계를 고정된 503 코드로만
  구분한다. 원인 객체는 응답에 직렬화하지 않고 conflict와 readiness 계약은
  기존 status/code를 유지한다.
- **원격 Gate 분리**: owner-only 배포·environment·migration은 Gate A, 잠시 public access를 여는 실측은 Gate B로 분리한다. 각 Gate 직전 project/version/access/environment/quota와 rollback target을 read-only로 제시하고 별도 승인을 받는다.
- **fail-closed rollback**: 배포·readiness·maintenance 비활성화·smoke 중 하나라도 실패하면 public으로 진행하지 않는다. owner-only access, 이전 saved version 또는 승인된 candidate, maintenance disabled/secret-absent를 복원하고 operator route와 health를 재확인한다.
- **캐시 판단은 측정 기반**: 같은 URL의 반복 GET/HEAD, submit 직후와 경과 후 요청을 순서대로 측정한다. application HTML/ETag/리비전 갱신과 외부 cache header를 분리해 기록하며, privacy·publish 정합성 문제만 release blocker로 분류한다. 단순 최적화는 별도 이슈로 넘긴다.
- **Sites HTML/media URL 분리**: public profile HTML은 실제 front door를 통과하는
  `/api/share/{handle}`을 canonical share URL로 사용하고, 확장자 경로로 이미
  Worker에 도달하는 `card.png`·`social.png`는 유지한다. Node/dev와 Sites Worker는
  기존 `/u/{handle}`·root query도 하위 호환으로 처리하되 Share Studio와 metadata는
  지원이 실측된 API share URL만 생성한다.
- **깨진 OG 이미지 fail-closed**: D1 public projection 뒤 R2 dark authority와 social
  publication id·owner가 일치할 때만 개인화 `social.png?v=`를 선언한다. legacy,
  missing, renderer-unavailable publication은 실제 계정 mutation이나 on-demand write
  없이 packaged 2400x1260 sample PNG를 사용한다.
- **카드 readiness 단일 계약**: 카드 이미지 표면은 source별 generation을 갖는
  `loading → ready|error` 상태를 공유한다. 최초 source는 exact `499 / 306` Skeleton으로
  공간을 예약하고, source 교체 중에는 마지막 decoded 이미지를 보존한다. 새 source의
  `load`와 가능한 `decode()`가 완료된 뒤에만 visible source를 원자적으로 교체한다.
- **motion은 준비 상태의 소비자**: intro flip과 Share Studio handoff는 DOM mount나
  URL 존재가 아니라 card `ready`를 시작 조건으로 사용한다. loading/error에서는
  spatial motion·tilt·beam을 실행하지 않고, reduced-motion에서는 짧은 fade 또는
  즉시 교체만 사용한다.
- **성능과 cache 분리**: Skeleton은 지연을 숨기는 대체물이 아니다. private preview의
  unique render와 in-flight 중복, avatar cache key를 focused 측정으로 보정하되 외부
  shared cache를 추가하지 않고 privacy·publication 일관성 계약을 유지한다.
- **Stage 4.2 tab-memory cache**: Stage 4.1의 component-local Blob 수명은 같은 화면 안의
  중복만 줄일 뿐 route·surface를 넘는 재사용을 보장하지 않는다. 외부 HTTP cache header는
  그대로 두고 decoded resource와 pending promise만 bounded tab memory에서 공유한다.
  private source는 owner scope를 key에 포함하고 영속 저장하지 않으며, 실패는 저장하지
  않는다. TTL/LRU 만료 또는 owner/logout/revision 변경 시 object URL을 회수한다.
- **avatar fail-soft 복구**: GitHub avatar fetch는 bounded timeout과 transient 1회 재시도만
  허용한다. 성공 bytes만 avatar LRU에 저장하고 실패는 initials fallback으로 응답하되
  provider URL·owner·error 원문 없이 code/attempt/retrying만 관측한다. renderer와 card
  response cache key, private/public header는 바꾸지 않는다.
- **Workerd redirect 호환**: avatar request는 `redirect: "manual"`로 보내고 기존
  `response.ok`·content-type·byte limit 검사를 그대로 통과한 bytes만 수용한다. 3xx는
  body를 읽거나 Location을 따라가지 않고 non-retryable fallback으로 처리한다.
- **warm share handoff**: Share Studio는 source rect뿐 아니라 현재 화면의 decoded image
  resource를 입력받는다. source bitmap으로 motion을 즉시 시작하고 public target bitmap은
  background에서 준비한 뒤 target settle 이후 짧게 교체한다. source가 없거나 direct cold
  entry인 경우에만 기존 Skeleton/readiness를 사용하며 원본 source는 overlay가 준비되기
  전 숨기지 않는다.

## 잠정 단계

- **Stage 1 — production artifact local-path 보정**
  - 절대 경로 유입 원인과 manifest runtime 필요성 재현
  - 최소 build artifact 정리와 회귀 테스트
  - 검증 관점: runtime 파일은 유지하면서 production verifier를 우회 없이 통과하는가
- **Stage 2 — exact local candidate와 archive preflight**
  - 전체 test/E2E/build/verifier 실행, Sites helper archive 파일 목록·금지 문자열 검사
  - exact candidate SHA, artifact size/count와 rollback 호환성 확정
  - 검증 관점: clean commit과 최종 package archive가 같은 provenance와 보안 계약을 만족하는가
- **Stage 3 — Gate A owner-only 배포와 전체 기능 smoke**
  - read-only remote snapshot과 별도 Gate A 승인
  - hosted migration blocker 보정, exact commit saved version, migration `1..5`
    readiness, maintenance 복원과 owner-only 전체 smoke
  - 검증 관점: public access 없이 OAuth·CLI·D1/R2·README/social media와 rollback이 통과하는가
- **Stage 3.7 — Sites 호환 공유 문서 경로 보정**
  - Gate B 1차 실패를 재현 가능한 front-door 계약으로 기록
  - `/?profile={handle}` query HTML에 동적 canonical/OG/Twitter를 주입하고
    Share Studio가 같은 URL을 생성하도록 보정
  - `/u/{handle}/card.png`·`social.png`의 media 계약과 기존 런타임 `/u/{handle}`
    하위 호환은 유지
  - 검증 관점: 실제 Sites가 전달하는 URL과 crawler가 받는 initial HTML이 일치하는가
- **Stage 3.8 — Worker 전달 공유 문서 경로 보정**
  - version 15 protected root query가 정적 asset으로 우회되는 production blocker 기록
  - `/api/share/{handle}`을 canonical/Share Studio/frontend route로 사용하고 기존
    `/u/{handle}`·root query source 하위 호환과 media 경로는 유지
  - 검증 관점: production에서 확인된 Worker dispatch prefix와 crawler initial
    HTML이 일치하는가
- **Stage 3.9 — social preview 자산 가용성 보정**
  - Gate B 2차에서 확인한 legacy README `200`/social `404` 불일치를 기록
  - D1 공개 상태와 R2 authority/social 정합성을 읽기 전용으로 결합하고, 정합한
    social object가 없으면 packaged 2400x1260 sample PNG를 metadata에 사용
  - missing/private fallback의 실제 사용자 handle 의존성을 제거하고 social route를
    identity-less `public_card`로 분류
  - 검증 관점: 모든 `og:image`가 실제 `200 image/png`이고 legacy/public/missing
    조건에서도 존재하지 않는 R2 URL을 선언하지 않는가
- **Stage 3.10 — Sites 소유자 프로필 경로 보정**
  - Gate B 뒤 발견한 `/profile` front-door 이탈을 `/?view=profile`로 보정
  - 메뉴, OAuth 복귀, device/public CTA와 CLI profile metadata를 canonical owner
    route로 통일하고 `/profile` Node/dev 하위 호환 유지
  - 검증 관점: 공개 계약을 변경하지 않고 owner-only Sites에서 실제 profile로
    복귀하는가
- **Stage 4 — Gate B public cache 실측과 baseline 원복**
  - Stage 3.9 owner-only 재배포와 별도 Gate B 재승인 뒤 제한된 public smoke
  - `/api/share/{handle}` canonical/OG/Twitter·private/missing HTML 폴백 실측
  - 반복 요청과 submit 전후 cache/revision 측정, 즉시 owner-only·private·revoked·disposable cleanup baseline 복원
  - 검증 관점: 공개 경계와 리비전 신선도가 유지되고 #84로 넘길 재현 가능한 증적이 남는가
- **Stage 4.1 — 카드 readiness·Skeleton·motion 회귀 보정**
  - 모든 동적 카드 PNG 표면의 공통 readiness와 exact aspect-ratio Skeleton 적용
  - 공개 profile의 원형 loading indicator를 identity-free 구조형 Skeleton으로 교체
  - intro flip·Share Studio handoff를 decoded image 준비 뒤로 gate하고 error/reduced-motion 처리
  - 소유자 draft 카드의 last-ready 보존, pending source race 차단과 private render 지연 최소 보정
  - 검증 관점: 느리거나 실패하는 이미지에서도 빈 카드·alt 텍스트 flip·layout shift가 없고,
    실제 Sites 후보에서 카드 편집과 공개 공유 진입이 안정적인가
- **Stage 4.2 — avatar 복구성과 card resource 재사용 보정**
  - avatar transient fetch 재시도, 실패 결과 비캐시와 안전한 failure event 추가
  - card readiness 아래에 tab-memory resource/in-flight cache를 두고 owner scope·TTL·LRU·
    failure eviction·object URL 수명 계약 고정
  - 홈·profile·public intro·Share Studio의 동일 source 재사용과 logout/revision 격리 검증
  - 검증 관점: 일시 avatar 장애가 고착되지 않고 동일 tab의 이미 준비된 카드가 다른
    surface에서 다시 네트워크/decode 지연을 만들지 않으며 private bytes가 섞이지 않는가
- **Stage 4.3 — hosted avatar 호환과 공유 handoff 연속성 보정**
  - avatar fetch를 Workerd-compatible manual redirect 처리로 바꾸고 3xx fail-closed 유지
  - Home·owner profile의 decoded source bitmap을 Share Studio handoff에 전달하고 public
    target 준비 뒤에만 교체
  - 최초 공유에서 source 즉시 숨김·hero Skeleton·late motion 합류를 제거하고 failure,
    close-before-ready, reduced-motion과 설정 저장 경로를 검증
  - 검증 관점: hosted avatar가 실제 bytes로 렌더되고 첫 공유가 이미 보인 카드에서 끊김
    없이 이어지며 public URL/cache/privacy 계약이 유지되는가
- **Stage 4.4 — 공유 전환·프로필 Skeleton 연속성 보정**
  - warm handoff의 source→public target 교체에는 image-level crossfade를 다시 시작하지
    않고, source가 없는 cold path의 readiness fade만 유지
  - 공개 profile의 page-wide sheen을 제거하고 identity·stats·activity·card placeholder가
    독립적으로 loading 상태를 표현하도록 구조화
  - 소유자 profile loading도 같은 identity-free 구조형 Skeleton으로 통일하고
    `prefers-reduced-motion`에서는 모든 Skeleton sheen을 중지
  - 검증 관점: 공간 이동이 끝난 카드가 다시 깜빡이지 않고 두 profile route가 동일한
    정보 위계·접근성·layout 안정성을 유지하는가

## 리스크

- **build hook 순서**: 정리 hook이 Cloudflare plugin보다 먼저 끝나면 manifest가 다시 생성될 수 있다. 실제 hook 순서를 테스트로 고정하고 최종 `dist/`에서 검증한다.
- **필수 runtime metadata 오삭제**: `.vite` 전체를 근거 없이 제거하면 Worker asset 참조가 깨질 수 있다. emitted entry/config/import를 대조하고 불필요성이 증명된 파일만 제외한다.
- **verifier 우회**: 검사 예외나 path pattern 축소는 다른 로컬·credential 노출을 허용할 수 있다. verifier는 독립적으로 유지하고 artifact producer를 보정한다.
- **migration 뒤 application rollback**: migration `3..5` 적용 뒤 owner-only saved version 8로 돌아갈 수 있어야 한다. additive/backward-compatible 근거와 backup 가능성을 Gate A 전에 확인하고 schema downgrade는 하지 않는다.
- **원격 데이터·credential**: OAuth code, session, token, owner/usage와 backup payload가 로그·문서·archive에 남을 수 있다. exact disposable scope와 redacted count/digest만 보고하고 cleanup을 검증한다.
- **cache 오판**: 외부 edge cache와 application 리비전 갱신을 혼동할 수 있다. 시간 순서, response header, HTML revision과 image ETag를 함께 기록한다.
- **공개 상태 잔류**: Gate B 중간 실패가 public access를 남길 수 있다. 실패 원인 분석 전에 owner-only를 먼저 복원하고 anonymous gate를 재확인한다.
- **Sites front-door 경로 불일치**: local Worker 성공만으로 extension 없는 동적
  HTML을 수용하지 않는다. owner-only protected query `200`과 별도 public Gate의
  initial HTML metadata가 모두 통과해야 공개 share URL로 승격한다.
- **Sites quota·과금**: public beta quota나 plan 정책이 바뀔 수 있다. Gate마다 추가 결제·자동 초과 과금 표시를 확인하고 요구되면 mutation을 중단한다.
- **Skeleton으로 실제 지연 은폐**: visual placeholder 통과만으로 성능 완료 처리하지
  않는다. request/render 시계열과 source별 ready 시간을 함께 측정하고 중복 render와
  과도한 invalidation만 최소 보정한다.
- **stale image race**: 빠른 테마·언어 전환에서 이전 request가 늦게 완료되어 최신
  draft를 덮을 수 있다. source generation exact-match 뒤에만 visible source를 commit한다.
- **motion 재시작/미완성 asset**: state rerender가 flip을 반복하거나 error asset을
  움직일 수 있다. ready generation당 opening 1회와 error settle을 focused test로 고정한다.
- **private resource 혼합**: URL만 cache key로 쓰면 다른 owner session의 private bitmap이
  재사용될 수 있다. private key에 owner scope를 강제하고 logout/owner 변경 시 clear하며
  persistent browser storage는 사용하지 않는다.
- **Blob 조기 회수·누수**: component cleanup마다 revoke하면 재사용이 사라지고 무제한
  보존하면 tab memory가 누적된다. refcount와 bounded TTL/LRU를 함께 적용하고 eviction 때만
  object URL을 revoke한다.
- **avatar 장애 고착**: 실패 `null`을 LRU에 넣으면 transient GitHub 장애가 장기 initials로
  보인다. 성공 bytes만 cache하고 bounded retry 뒤 fallback하되 safe event로 원인을 구분한다.

## 승인 요청 사항

- production verifier를 완화하지 않고 artifact producer에서 불필요한 manifest를 제거하거나 필요한 경우 상대 경로로 정규화하는 방향
- build metadata의 runtime 필요성을 먼저 증명하고 최소 파일만 다루는 범위
- 공식 문서는 장기 운영 사실이 달라질 때만 기존 `docs/` 문서를 최소 갱신하고, 원시 실측은 `mydocs/` task 증적에 두는 위치 판단
- Stage 1~4.3과 Stage 3.7 보정 구성, Stage 3 Gate A·Stage 4 Gate B를 각각 별도
  승인으로 중단하는 절차
- migration `3..5` 적용과 read-only readiness를 구분하고 exact `1..5`만 통과시키는 기준
- Gate B 뒤 영구 공개가 아니라 owner-only baseline으로 즉시 원복하며, #84에서 Gate C와 `main` 릴리스를 수행하는 handoff 경계
- Stage 4.1의 공통 card readiness, Skeleton 적용 범위, decoded image 뒤 motion gate,
  private/public cache 계약 불변과 owner-only 재배포·집중 smoke 경계
- Stage 4.2의 avatar transient recovery·failure 비캐시·safe observability와 persistent
  storage 없는 owner-scoped tab-memory card resource cache 경계
- Stage 4.3의 Workerd manual redirect fail-closed와 decoded source-image handoff,
  public target ready 뒤 교체 및 Home-only profile refresh를 채택하지 않는 경계
