# Task #108 수행계획서 — canonical production Site migration과 stage5 테스트 전용 전환

## 목적

현재 public validation origin인
`https://codex-usage-profile-stage5.meleeisdeveloping.chatgpt.site`와 실제
production 역할을 분리한다. 새
`https://codex-usage-profile.meleeisdeveloping.chatgpt.site`를 canonical
production으로 승격하고, 기존 stage5는 owner-only 기본값과 synthetic test data를
사용하는 개발 검증 Site로 전환한다.

두 Site는 exact source, artifact, schema/migration과 test contract만 공유한다.
Sites project, D1, R2, OAuth/secret, session·device token, rate-limit state와 access
policy는 공유하지 않는다. 새 production의 public cutover, CLI package publish,
stage5 역할 전환과 test data 폐기를 서로 독립적인 승인 Gate로 운영하고, 이후
release에서 재사용할 Local → stage5 → production runbook을 남긴다.

  audit 당시 같은 stage5 project는 Task #101 validation version 33/source

  rollback/export 확인 뒤 별도 data disposal Gate에서만 수행한다.
- OpenAI Sites 공식 문서에 따르면 배포 URL은 모두 production deployment이고,

  전략을 먼저 고정하지 않으면 stage artifact를 production project에 배포하는
  cross-target 사고를 만들 수 있다.
- CLI `0.1.1`, Device Approval guidance와 package smoke는 stage5를 production
  default로 고정한다. 새 production을 실제 기본값으로 만들려면 immutable npm

## 설계 방향

### 환경과 데이터 경계

- **Local**: loopback origin, local fixture/real-workerd와 failure-injection 전용이다.
  production/stage D1·R2·OAuth secret을 사용하지 않는다.
- **stage5**: 별도 Sites project·D1·R2와 test OAuth/secret을 사용하는 owner-only 기본
  환경이다. X·LinkedIn 등 anonymous crawler 검증 때만 별도 승인과 제한된 시간으로
  public access를 열고 즉시 다시 제한한다.
- **production**: 새 canonical hostname, 별도 Sites project·D1·R2와 production
  OAuth/secret을 사용한다. exact release commit의 approved saved version만 배포한다.
- source, migration, logical binding 이름과 test suite는 공유하지만 provider resource
  identity와 durable data는 공유하지 않는다. production→stage 자동 복제는 금지하고
  synthetic seed만 허용한다.
- 두 Site 유지가 plan/quota상 불가능하면 공유 D1/R2로 우회하지 않는다. remote
  mutation 전에 작업을 중단하고 `production 1 Site + 미배포 saved version + local`
  fallback을 별도로 승인받는다.

### Project linkage와 cross-target 방지

- Stage 1에서 공식 Sites project linkage 동작과 `.openai/hosting.json`의 단일
  `project_id` 제약을 실제 상태로 대조한다.
- tracked canonical manifest, environment별 materialized manifest 또는 지원되는 project
  selector 중 재현 가능하고 secret을 포함하지 않는 방법만 채택한다. 지원되지 않는
  임의 dual-manifest 형식은 만들지 않는다.
- 배포 preflight는 target role, project identity, expected D1/R2 identity, exact source
  SHA와 expected origin이 모두 일치하지 않으면 save/deploy를 중단해야 한다.
- canonical repository default는 최종 production project를 가리키되 stage5 운영도
  source checkout을 오염시키지 않는 repeatable 절차를 runbook에 남긴다.

### Release와 remote Gate 순서

- Task #108은 source change와 remote migration을 함께 요구한다. 미병합 task source를
  production에 공개하지 않기 위해 Stage 2 종료 시 **Issue를 close하지 않는 source
  integration checkpoint PR**을 `devel`에 병합하고 task branch를 최신 `devel`로
  재고정하는 방식을 잠정 채택한다.
- integrated candidate는 별도 `devel → main` release PR과 exact tree/provenance 검증을
  거친다. 새 production은 exact `main` saved version만 public 후보로 사용한다.
- remote mutation은 다음 Gate로 분리한다.
  - **Gate A — resource provisioning**: 새 production Site·D1·R2 생성과 owner-only linkage
  - **Gate B — production public cutover**: owner-only full smoke 뒤 public access 전환
  - **Gate C — CLI npm patch publish**: public production smoke 뒤 immutable patch/tag publish
  - **Gate D — stage5 role transition**: 새 CLI와 production 관찰 뒤 stage5 owner-only 전환
  - **Gate E — data disposal**: inventory/export/rollback 확인 뒤 test state 삭제
- Gate B와 C가 끝날 때까지 stage5 public validation은 유지해 기존 CLI `0.1.1` 사용자
  경로를 끊지 않는다. Gate C의 잠정 package version은 `0.1.2`이며 구현계획서에서
  immutable package/version/tag contract를 다시 확인한다.

### URL과 사용자 계약

- 새 production에서 README Markdown은 fixed
  `https://{canonical}/api/share/{handle}` href와 query 없는
  `https://{canonical}/u/{handle}/card.png` src를 사용한다.
- submit·card settings 저장은 README Markdown을 바꾸지 않고, 링크 복사와
  X·LinkedIn·Threads·Facebook·Reddit target revision만 갱신한다.
- stage5 UI/CLI test는 명시적인 origin override를 사용하고 production package default를
  stage5로 되돌리지 않는다.
- root README와 공개 문서의 전면 편집은 #90에 남긴다. 이 task는 동작에 필요한 hostname,
  fixed URL, CLI version/명령과 runbook만 최소 변경한다.

### Rollback과 disposal

- production public rollback은 직전 access policy와 이전 approved saved version을
  구분한다. application rollback, access close와 OAuth/CLI origin rollback 순서를
  runbook에 명시한다.
- stage5 version 32/source
  `6cf2bab664e5a1f0b1e6051cc35887721c307e99`는 기존 application rollback provenance로
  보존하되 새 production에서 실제 사용할 rollback saved version을 별도로 검증한다.
- data disposal은 public cutover 성공만으로 자동 진행하지 않는다. owner/session/token,
  D1 tables/migration metadata, R2 stable/immutable object, local credential를 inventory하고
  export/복구 가능성과 production 비공유를 증명한 뒤 승인받는다.

- stage5는 owner-only 기본, 별도 D1/R2와 synthetic test state만 가지며 production
  credential/data/rate-limit state를 공유하지 않는다.
- submit/settings 저장 전후 README Markdown은 동일하고 링크 복사·다섯 SNS target
  revision만 새 값으로 갱신된다.
- Local → stage5 → production, temporary public crawler smoke, application/access/OAuth/
  CLI rollback과 data disposal 절차가 runbook으로 재현 가능하다.
- PR 준비 직전 `git status --short`가 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **모든 Sites URL은 production deployment**: stage5도 public이면 실제 외부 접근과
  crawler traffic을 받는다. owner-only 기본과 짧은 public Gate를 강제한다.
- **plan·storage 한도**: 두 Site가 전체 한도를 공유한다. 유료 전환·추가 과금 요구나
  capacity 부족은 stop condition이며 shared storage로 우회하지 않는다.
- **단일 hosting manifest와 cross-target**: 잘못된 `project_id`는 production/stage
  오배포를 만든다. supported project selection과 identity preflight 없이는 save/deploy를
  실행하지 않는다.
- **source integration 순서**: task source가 devel/main에 들어가기 전 production
  공개는 provenance를 깨뜨린다. checkpoint PR과 release PR의 다중 PR 절차를 명시적으로
  승인받고 각 tree equality를 검증한다.
- **OAuth·CLI cutover gap**: callback, Site access와 npm latest의 순서가 어긋나면 login/
  submit이 끊긴다. stage5 public 유지, packed CLI 검증, production public 뒤 npm publish,
  새 CLI 확인 뒤 stage5 전환 순서를 지킨다.
- **npm immutability**: `0.1.2`와 tag는 재사용할 수 없다. version/tag/payload/provenance를
  Gate C 직전에 다시 확인하고 승인 없이는 publish하지 않는다.
- **data disposal 비가역성**: D1/R2/session/token 삭제는 복구되지 않을 수 있다.
  inventory·export·production 비공유와 exact target 승인이 하나라도 없으면 apply하지 않는다.
- **SNS provider cache**: revision identity는 새 crawler key를 제공하지만 즉시 표시 SLA를
  보장하지 않는다. application metadata와 provider 결과를 분리 기록한다.
- **문서 범위 충돌**: #90의 전면 README/GitHub metadata 작업과 중복될 수 있다. #108은
  migration에 필요한 hostname·CLI·fixed URL·runbook만 변경한다.

## 승인 요청 사항

- Local + 별도 stage5 Site + 별도 production Site의 3환경 구조와 D1/R2/secret/identity
  state 비공유 원칙
- 기존 `docs/sites-operations.md`를 공식 승격·rollback runbook으로 확장하고
  `docs/production-hosting.md`에서 교차 참조하는 문서 위치 판단
- 6개 Stage와 Gate A(resource), Gate B(public), Gate C(npm), Gate D(stage role),
  Gate E(data disposal)를 각각 별도 승인받는 진행 방식
- 미병합 source 공개를 피하기 위한 non-closing source integration checkpoint PR →
  `devel → main` release PR → exact-main production deployment의 다중 PR 순서
- CLI patch release 잠정 version `0.1.2`와 production public 확인 뒤 npm publish,
  새 `@latest` 확인 뒤 stage5 owner-only 전환 순서
- dual-Site capacity가 부족하면 shared D1/R2 대신 one-Site fallback으로 중단·재승인하는
  stop condition
- root README는 기능적 canonical URL만 최소 수정하고 전면 문구·badge·repository metadata는
  #90에 남기는 범위 경계

승인되면 `task_m100_108_impl.md`에서 Stage별 exact source/remote mutation, 산출물,
검증 명령, 커밋과 checkpoint/release/final PR 절차를 구체화한다.
