# Task #91 수행계획서 — CLI 로그인·사용량 제출 후 터미널 GitHub star 프롬프트 추가

GitHub Issue: [#91](https://github.com/postmelee/codex-usage-profile/issues/91)
마일스톤: M100

## 목적

Codex Usage Profile CLI의 실제 대화형 로그인과 사용량 제출이 성공한 뒤, 기존 성공 결과를 출력하기 전에 프로젝트 저장소를 GitHub에서 star할지 터미널에서 묻는다. 사용자가 Enter 또는 `y`/`yes`를 입력하면 브라우저를 열지 않고 로컬 `gh` CLI의 현재 인증 계정으로 `postmelee/codex-usage-profile`을 star한다.

GitHub star는 제품의 GitHub OAuth token이나 submit credential을 사용하지 않는 선택적 로컬 통합으로 제한한다. `gh` 미설치·미인증·권한 부족·network 오류가 로그인 또는 제출 결과와 exit status를 바꾸지 않게 하고, `submit --json`과 비대화형 실행의 출력 계약을 그대로 보존한다.

## 배경

현재 CLI는 `runLogin()`에서 device login 완료 직후 `Login complete.`를 출력하고, `runSubmit()`에서 server submit 성공 응답을 받은 뒤 `writeSubmitOutput()`으로 human 또는 JSON 결과를 출력한다. 이 경계 사이에 성공 결과를 보존한 채 선택적 프롬프트를 실행할 수 있지만, prompt와 subprocess가 output projection에 섞이면 JSON 오염이나 automation 정지로 이어질 수 있다.

참고한 tokscale 구현은 interactive TTY와 로컬 `gh`가 준비된 경우 authenticated user의 star 상태를 확인하고, 응답이 긍정이면 `PUT /user/starred/{owner}/{repo}`를 호출한다. Codex Usage Profile은 web login에서 받은 GitHub OAuth token을 사용자 조회 뒤 폐기하므로 server scope 확대나 token 저장으로 이 기능을 구현하지 않는다. 로컬 `gh`의 active account를 프롬프트에 명시하고 고정 endpoint만 호출해 외부 변경 주체와 대상을 사용자에게 보여준다.

작업지시자는 Issue #91 등록 전에 `(Y/n)`의 Enter 기본값을 `Yes`로 명시 승인했다. 따라서 빈 입력은 star 실행으로 해석하되, 프롬프트가 표시되지 않는 환경에서는 어떤 star mutation도 실행하지 않는다.

## 범위

### 포함

- 신규 device login이 실제 완료된 interactive `login`에서 성공 결과 직전 star prompt 실행
- interactive `submit`에서 server submit 성공 응답을 확보한 뒤 human 결과 직전 star prompt 실행
- 자동 login 후 이어지는 `submit`에서는 submit 경계에서 한 번만 prompt 실행
- stdin과 stdout이 모두 TTY이고 `--json`이 아닐 때만 prompt 허용
- 로컬 `gh` active account 조회와 프롬프트의 `@login` 표시
- authenticated user의 기존 star 상태 확인과 이미 starred인 경우 prompt 생략
- `(Y/n)` 입력 계약: Enter·`y`·`yes`는 star, `n`·`no`는 건너뛰기, 그 외 입력은 허용값 재요청
- 고정 인자의 `gh api --silent --method PUT /user/starred/postmelee/codex-usage-profile` 실행
- `gh` 탐색·인증·상태 확인·star 실패를 fail-soft로 처리하고 원래 성공 결과와 exit code 보존
- child process timeout, shell 비사용, credential·token·raw stderr 비노출
- prompt helper와 login/submit orchestration의 단위·회귀 테스트
- 사용자 CLI guide와 npm package README에 optional `gh` 통합, 기본 Yes, 적용·제외 환경과 active account 경계 기록

### 제외

- GitHub OAuth scope 확대, OAuth access token 또는 refresh token 저장
- web backend나 device-login API를 통한 server-side star
- repository browser 자동 열기
- non-TTY, pipe/redirection, `submit --json`과 unattended automation에서 prompt 또는 star 실행
- 사용자가 prompt를 보지 않은 상태의 star 실행
- 실패한 login/submit, `status`, `logout`, `--help`, `--version`에서 prompt 실행
- 기존 credential이 유효해 `Already signed in`만 출력하는 login shortcut에서 prompt 실행
- unstar, 임의 repository 입력, 범용 GitHub activity 명령
- local star cache 또는 장기 GitHub 상태 저장
- CLI credential schema와 Account Usage Contract 변경

## 설계 방향

- **선택적 통합 모듈 분리**: `src/github-star.js`에 TTY eligibility, `gh` active account 조회, star 상태 확인, 입력 정규화와 PUT 실행을 모은다. login/submit orchestration은 성공 응답을 확보한 뒤 helper를 호출하고 기존 결과 writer는 그대로 유지한다.
- **결과 경계 보존**: `runLogin()`은 새 device login 완료 뒤 `Login complete.` 직전에 helper를 호출한다. `runSubmit()`은 `submitAccountUsage()`가 성공한 뒤 `writeSubmitOutput()` 직전에 한 번 호출한다. helper 예외는 내부에서 흡수해 이미 성공한 제품 동작을 실패로 바꾸지 않는다.
- **TTY와 JSON fail-closed**: `runCli()`가 주입 가능한 stdin을 받고 stdin/stdout 모두 `isTTY === true`인지 확인한다. `--json`은 helper를 호출하지 않아 stdout이 단일 JSON document로 유지된다. TTY 조건을 만족하지 않으면 `gh` 탐색도 하지 않는다.
- **명시된 외부 변경 주체**: `gh api user --jq .login`으로 확인한 active account만 `@login`으로 보여준다. 이 조회가 실패하면 prompt와 mutation을 모두 생략한다. 제품 profile owner와 로컬 `gh` account가 다를 수 있으므로 star 주체는 항상 prompt의 계정으로 해석한다.
- **기존 상태 확인**: 고정 GET endpoint로 star 상태를 확인한다. starred 응답이면 아무 질문 없이 결과를 출력하고, 명시적인 not-star 응답일 때만 prompt한다. 인증·권한·network처럼 상태를 확정할 수 없는 실패는 not-star로 추정하지 않고 prompt를 생략한다.
- **Enter 기본 Yes**: 빈 문자열, `y`, `yes`만 긍정으로 처리하고 `n`, `no`는 거절로 처리한다. 다른 입력은 재질문해 오타를 암묵적인 mutation으로 바꾸지 않는다. prompt 문구는 `(Y/n)`을 사용한다.
- **고정 subprocess 계약**: Node child process API를 shell 없이 executable과 argument array로 호출한다. owner/repository/endpoint는 상수로 고정하고 사용자 입력을 command에 삽입하지 않는다. 각 `gh` 호출에는 bounded timeout과 output limit을 적용하며 token이나 raw failure body를 출력하지 않는다.
- **cache 미사용**: 별도 파일을 만들지 않고 eligible invocation마다 GitHub의 현재 starred 상태를 확인한다. positive cache migration과 stale state 문제를 만들지 않는 대신 subprocess timeout으로 지연 상한을 둔다.
- **테스트 주입 경계**: `gh` runner와 prompt I/O를 주입 가능하게 구성해 test가 실제 GitHub account나 star 상태를 읽거나 바꾸지 않게 한다. command integration test는 호출 횟수·순서·결과 출력 순서와 secret 비노출을 검증한다.
- **기존 출력 projection 유지**: star 안내와 결과는 human output에만 추가하고 `projectSubmitOutput()`/`writeSubmitOutput()`의 allowlist와 credential redaction은 변경하지 않는다.

### 통합 검증

- interactive login과 submit mock에서 prompt가 기존 성공 결과보다 먼저 나타난다.
- Enter 입력은 고정 repository에 대한 star PUT 한 번으로 이어지고 `n`은 mutation 없이 결과를 출력한다.
- already-starred, `gh` unavailable/unauthenticated/forbidden/timeout에서 prompt 또는 제품 실패가 발생하지 않는다.
- `submit --json` stdout은 ANSI·prompt·부가 문구가 없는 parse 가능한 단일 JSON document다.
- command와 문서 어디에도 GitHub token, submit token, raw stderr 또는 사용자별 로컬 경로가 포함되지 않는다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **Enter의 외부 mutation**: 일반적인 destructive prompt와 달리 Enter가 star를 실행한다. 작업지시자가 명시 승인한 `(Y/n)`을 정확히 표시하고 interactive TTY에서 active `@account`와 대상 프로젝트를 함께 보여주며 `n` 경로를 제공한다.
- **제품 계정과 `gh` 계정 불일치**: server OAuth token을 재사용하지 않으므로 두 계정이 다를 수 있다. active `gh` login을 prompt에 명시하고 그 계정으로만 star함을 문서화한다.
- **선택적 도구가 제품 성공을 가리는 문제**: `gh` 조회와 network가 느리거나 실패하면 성공 결과가 지연될 수 있다. 모든 subprocess를 bounded timeout으로 제한하고 상태를 확정할 수 없으면 prompt를 생략해 결과를 즉시 계속한다.
- **JSON·automation 오염**: prompt가 stdout에 섞이거나 stdin을 기다리면 automation이 깨진다. TTY와 `--json` gate를 orchestration에서 먼저 적용하고 JSON 회귀 테스트를 유지한다.
- **shell injection과 credential 노출**: shell 문자열이나 사용자 입력을 command에 사용하면 위험하다. executable과 fixed argument array만 사용하고 stderr/body/token은 사용자 출력과 테스트 snapshot에서 제외한다.
- **cross-platform `gh` 실행 차이**: macOS/Linux/Windows의 shell 문법을 사용하지 않고 Node child process의 direct executable 호출만 사용하며 missing executable을 정상적인 optional-unavailable 상태로 처리한다.

## 승인 요청 사항

- 신규 interactive login과 성공한 human submit 결과 직전에 local `gh` star prompt를 실행하는 범위
- Enter·`y`·`yes`를 긍정으로 처리하는 `(Y/n)` 계약과 그 외 입력 재질문 정책
- active local `gh` account를 prompt에 표시하고 server GitHub OAuth/credential schema를 변경하지 않는 경계
- 별도 local cache 없이 current star 상태를 bounded 조회하고 모든 `gh` 실패를 fail-soft로 처리하는 설계
- 공식 문서는 `docs/cli-submit.md`와 CLI package README만 수정하고 root README는 유지하는 위치 판단
- Stage 1 core, Stage 2 command integration, Stage 3 docs·통합 검증의 3단계 진행
