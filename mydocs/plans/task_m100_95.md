# Task #95 수행계획서 — 인증·화면 복귀 시 Home 카드 단일 reveal 보장

GitHub Issue: [#95](https://github.com/postmelee/codex-usage-profile/issues/95)
마일스톤: M100

## 목적

모바일 Safari·Chrome에서 GitHub 로그인 뒤 Home으로 돌아오거나 Profile 등 다른 화면에서
Home으로 이동할 때 카드가 한 번 나타난 뒤 다시 Skeleton으로 돌아갔다가 재등장하는 회귀를
보정한다. Home 최초 진입은 auth, owner profile과 최종 card target을 확정하고 이미지 decode가
끝날 때까지 같은 Skeleton을 유지한 뒤 한 번만 `ready`로 reveal해야 한다.

anonymous operator, authenticated owner, no-usage sample, profile/card 오류 fallback, logout과
revision refresh의 기존 의미는 유지한다. card image resource cache와 object URL lease,
readiness·reduced-motion·공유 source 계약을 약화하지 않고 v1.0 릴리즈 전 실제 모바일에서
단조로운 `loading → ready` 상태 전환을 확인한다.

## 배경

- Task #92 실제 모바일 검증 뒤 로그인 복귀와 Profile→Home 이동에서 Home 카드가
  `loading → ready → loading → ready`처럼 보이는 현상을 확인했다.
- 현재 `App`은 mount 뒤 `/api/auth/me`를 비동기로 조회하며, `HomePage`는 auth가 아직
  `loading`이어도 operator target을 pending으로 가진 transition을 즉시 생성한다.
- 인증이 확인되면 owner profile을 다시 비동기로 조회하고, 조회 중에는 operator를
  `desiredCardSource`로 유지했다가 owner 또는 sample target으로 교체한다.
- `cardLoading`은 auth/profile resolving과 transition status를 각각 확인하지만, 먼저 resolve된
  중간 target이 paint된 뒤 최종 target을 위한 새 transition이 시작되는 상태 이력을 금지하지
  않는다. 모바일의 느린 network·decode·paint 순서에서 이 틈이 눈에 보이는 것으로 추정한다.
- 기존 Playwright는 loading/ready 최종 상태, Skeleton 기하, owner decode, logout stale completion과
  fallback을 검증하지만 `ready` 뒤 `loading`으로 후퇴하지 않는 단조성은 측정하지 않는다.
- #92는 share handoff·계정 메뉴·카드 frame 기하를 보정했으므로 본 문제를 Home target
  authority와 초기 reveal의 별도 릴리즈 차단 이슈로 분리했다. #84 Gate C와 마케팅은 #95와
  #96 완료 뒤 exact candidate 재검증 전까지 중단한다.

위 원인 설명은 착수 시점의 코드·실측 기반 가설이다. Stage 1에서 auth/profile/image 응답 순서를
통제하고 paint 사이 상태 이력을 기록해 중간 operator 또는 stale owner 노출 경계를 확정한 뒤
구현 방향을 고정한다.

## 설계 방향

- User-Agent나 임의 timeout으로 깜빡임을 가리지 않는다. auth/profile/target의 명시적 authority와
  generation을 기준으로 표시 가능 여부를 결정한다.
- 최초 Home reveal에서는 auth 상태가 확정되기 전 operator를 최종 target으로 간주하지 않는다.
  authenticated owner는 profile 결과가 owner/sample/error target을 확정할 때까지 Skeleton을
  유지한다. anonymous가 확정된 뒤에는 operator target을 정상적으로 load·decode한다.
- 최종 target 선택은 가능하면 UI effect에서 분리한 순수 resolver/state helper로 표현해
  `unresolved`와 `selected target`을 구분한다. 정확한 파일 분리는 Stage 1 재현 결과와 기존
  `homeCardTransition` 책임을 비교해 구현계획서에서 확정한다.
- 최초 reveal과 이미 안정된 visible card의 refresh를 구분한다. 최초 또는 auth owner scope 변경은
  잘못된 identity의 last-ready card를 노출하지 않으며, 같은 owner의 publish revision refresh는
  현재 last-ready/resource reuse 계약을 유지한다.
- async profile/image completion은 owner scope와 transition generation이 일치할 때만 commit한다.
  stale completion, failed decode, logout은 기존 fail-close와 resource release를 유지한다.
- 검증은 최종 DOM만 보지 않고 `data-card-status`, source kind/URL, Skeleton active 상태와 image
  commit의 시간 순서를 수집해 `ready → loading` 또는 중간 operator/owner reveal을 실패로
  판정한다.
- 기존 full navigation을 실제 제품 경로로 수용한다. SPA 전환은 이 회귀를 해결하기 위한 범위로
  확대하지 않는다.

## 잠정 단계

- **Stage 1 — 상태 이력 재현과 단일 reveal 계약 확정**
  - auth, profile, operator/owner image 응답 순서를 각각 지연해 실제 `ready → loading`과 중간
    source 노출을 재현한다.
  - OAuth 복귀에 해당하는 Home mount, Profile→Home full navigation, cold/warm cache 기준선을
    Chromium mobile과 WebKit에서 기록한다.
  - 실패하는 단위·E2E 회귀를 추가하고 target authority, 초기 reveal과 refresh의 경계를 확정한다.
- **Stage 2 — 최종 Home target authority와 단조 transition 구현**
  - unresolved auth/profile 상태와 selected target을 분리하고 최초 중간 target commit을 차단한다.
  - owner scope·generation 정합, image decode 뒤 단일 commit과 Skeleton 연속성을 구현한다.
  - anonymous operator, owner, no-usage sample, profile/card 오류 경로를 단위·집중 E2E로 검증한다.
- **Stage 3 — 복귀·logout·cache·revision 회귀 보강**
  - OAuth/직접 Home 복귀, Profile brand link, 새로고침, logout과 owner scope change를 검증한다.
  - cold/warm cache, concurrent acquisition, last-ready refresh와 object URL release가 유지되는지
    확인한다.
  - desktop/mobile Chromium과 WebKit에서 ready 상태 단조성과 DOM commit 횟수를 고정한다.
- **Stage 4 — 통합 검증과 실제 모바일 Gate**
  - 전체 Node·Playwright, production build, Sites verifier·local full-stack smoke를 실행한다.
  - 승인된 배포 또는 로컬 검증 경로를 제공하고 실제 모바일 Safari·Chrome에서 로그인 복귀와
    Profile→Home을 재측정한다.
  - #96 처리와 #84 exact release candidate 재검증에 필요한 결과를 최종 보고한다.

### 통합 검증

- authenticated 초기 Home은 최종 owner/sample/error target이 decode될 때까지 Skeleton을 유지한
  뒤 한 번만 ready가 된다.
- anonymous 초기 Home은 auth 확정 뒤 operator를 한 번만 reveal한다.
- 상태 이력에 `ready → loading`, 중간 operator 또는 이전 owner 노출이 없다.
- logout은 owner source와 resource를 제거하고 operator loading→ready로 안전하게 reset한다.
- 같은 owner의 revision refresh와 warm cache reuse는 기존 last-ready·lease 계약을 유지한다.
- reduced-motion, card geometry, Share Studio source snapshot과 접근성 status 회귀가 없다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **anonymous operator 표시 지연**: auth가 확정될 때까지 operator reveal을 보류하므로 최초
  anonymous 화면의 Skeleton 시간이 늘 수 있다. auth 응답 전 identity 오판을 피하는 것을
  우선하고, warm resource reuse로 image 준비 비용을 줄인다.
- **초기 reveal과 refresh 혼동**: 모든 target 변경에서 visible을 제거하면 publish revision이나
  재시도 UX가 회귀한다. auth/owner scope가 확정되지 않은 최초 상태와 동일 owner refresh를
  별도 계약으로 테스트한다.
- **fallback 이중 reveal**: owner image 실패 뒤 sample fallback을 ready로 commit하기 전까지
  Skeleton을 유지하고, 실패한 owner가 먼저 paint되지 않음을 상태 이력으로 검증한다.
- **stale identity 노출**: logout·계정 변경 중 이전 owner Blob이 남을 수 있다. scope와 generation
  일치, resource cache clear와 release 횟수를 함께 검증한다.
- **브라우저 timing 차이**: Chromium에서 보이지 않는 짧은 paint가 WebKit 실제 기기에서만
  나타날 수 있다. 지연 route 기반 자동 상태 이력과 실제 Safari·Chrome Gate를 모두 요구한다.
- **진행 중 task와 충돌**: #84와 #91 worktree를 건드리지 않고 독립 `local/task95`에서 작업하며,
  #84 Gate C와 마케팅은 #95·#96 완료 뒤까지 중단한다.

## 승인 요청 사항

- 최초 Home은 auth가 확정되기 전 operator card를 최종 target으로 reveal하지 않고 Skeleton을
  유지한다.
- authenticated Home은 owner profile이 owner/sample/error target을 확정할 때까지 Skeleton을
  유지하며, 최종 이미지 decode 뒤 한 번만 reveal한다.
- 같은 owner의 publish revision 등 안정 상태 refresh는 기존 last-ready card를 유지하되,
  최초 mount·logout·owner scope 변경에서는 stale identity를 보존하지 않는다.
- Profile→Home은 기존 full navigation을 유지하며 SPA router 도입은 제외한다.
- 공개 문서는 변경하지 않고 내부 작업 문서와 PR 검증 결과만 갱신한다.
- 실제 모바일 Safari·Chrome Gate 전에는 #95 완료 및 #84 재개 판정을 하지 않는다.

승인되면 `task_m100_95_impl.md`에서 Stage별 상태 모델, 회귀 fixture, 검증 명령과 커밋 경계를
구체화한다.
