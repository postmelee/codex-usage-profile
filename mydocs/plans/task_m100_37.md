# Task M100 #37 수행계획서

GitHub Issue: [#37](https://github.com/postmelee/codex-usage-profile/issues/37)
마일스톤: M100

## 목적

Codex Usage Profile의 production 배포 기준을 Cloud Run + Neon + R2 단일 제품 구조로 확정하고, 동일 저장소의 landing UI를 ChatGPT Sites에 이벤트·홍보용 marketing mirror로 배포할 수 있는지 작은 POC로 검증한다. Cloud Run은 GitHub OAuth, browser session, device login, CLI submit, 사용자 card와 PNG rendering의 유일한 canonical runtime으로 유지한다.

ChatGPT Sites는 Cloud Run과 경쟁하는 두 번째 제품 frontend/backend가 아니라 sample card, 제품 소개, Quickstart와 Cloud Run 이동 CTA만 제공하는 정적 marketing mirror로 한정한다. Sites 배포는 OpenAI Sites 관련 이벤트·홍보 기회를 활용하기 위한 비차단 산출물이며, 실패하거나 지원 범위가 바뀌어도 Cloud Run 단독 MVP 출시 일정과 기능에 영향을 주지 않아야 한다.

## 배경

현재 저장소는 Vite frontend와 Node HTTP runtime을 같은 저장소에서 실행한다. `src/profile-runtime/dev-server.js`는 `node:http`와 Vite middleware를 결합하고, `src/profile-backend/durable-store.js`는 단일 JSON 파일을 영속 저장소로 사용하며, `src/profile-card/renderer.js`는 `@napi-rs/canvas`로 PNG를 생성한다. 이 구성은 로컬 MVP에는 충분하지만 container health, process lifecycle, concurrent writes, shared persistence, public media delivery가 필요한 production 계약은 아직 없다.

M100의 다음 production 작업 전에 runtime과 platform 책임을 확정해야 한다. [ChatGPT Sites 문서](https://learn.chatgpt.com/docs/sites)는 기존 web project의 hosting과 platform resource 사용을 지원하지만, 현재 제품의 GitHub OAuth/session/device submit backend를 그대로 소유한다는 보장은 없다. 반면 [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract)는 Node runtime과 native PNG renderer를 포함한 canonical application host에 적합하다.

따라서 본 task에서는 Cloud Run을 제품 runtime, Neon을 structured record의 장기 진실 원천, R2를 공개 card media의 진실 원천으로 설계한다. 실제 전체 migration은 후속 task로 남기고, 이번 spike는 Cloud Run 배포 artifact와 adapter boundary를 먼저 검증한 뒤 Sites marketing artifact의 호환성과 시각 동등성을 별도로 검증한다.

## 범위

### 포함

- Cloud Run 제품 UI와 Sites marketing UI가 공유할 landing component/CSS 경계
- Cloud Run container가 `PORT`와 `0.0.0.0` 계약을 지키고 health endpoint를 제공하는 POC
- production Node host에서 API, static frontend, `@napi-rs/canvas` PNG renderer가 함께 동작하는 smoke path
- ChatGPT Sites에서 sample card, 제품 소개, Quickstart와 CTA가 shared marketing UI source로 빌드되는 POC
- Sites의 `Create your card`/`Open app` CTA가 Cloud Run canonical app의 `/`로 이동하는 단순 navigation
- Sites artifact가 API, 사용자 데이터, credential, session, OAuth와 provider storage를 포함하지 않는 회귀 테스트
- Neon repository adapter와 R2 card media adapter가 후속 migration에서 구현할 최소 interface 및 단일 진실 원천 정의
- Sites 미사용 또는 배포 실패 시 Cloud Run 단독 fallback 검증
- desktop/mobile 대표 viewport의 Cloud Run landing과 Sites marketing mirror 시각 비교
- architecture decision과 deployment boundary의 공식 문서화

### 제외

- 전체 JSON durable store를 Neon schema와 transaction으로 이관하는 작업
- production R2 bucket에 card를 실제 materialize하고 CDN cache invalidation을 완성하는 작업
- custom domain, DNS, TLS와 최종 production secret 등록
- npm package publish와 CLI 기본 server origin 확정
- Sites가 GitHub OAuth callback, browser session, device approval 또는 submit API를 직접 소유하는 구조
- Sites가 실제 사용자 계정, public/private card, usage data 또는 Cloud Run API를 조회하는 구조
- Sites에서 GitHub 로그인 상태, settings, publish/share와 사용자별 CTA를 모사하는 구조
- Sites runtime storage와 Neon에 같은 owner/usage/session 데이터를 이중 기록하는 구조
- cross-subdomain shared session cookie 도입
- production observability, backup, retention, account deletion의 전체 구현

## 설계 방향

- **Canonical runtime**: Cloud Run만 OAuth, session, device flow, CLI submit, owner visibility mutation, PNG render를 처리한다. Sites에는 credential, session secret, GitHub client secret 또는 submit token을 배치하지 않는다.
- **Sites 역할**: Sites는 sample fixture 기반 landing과 marketing content만 렌더링한다. `Create your card` 또는 `Open app` CTA는 Cloud Run `/`로 이동하며 GitHub OAuth URL을 직접 구성하지 않는다. 두 origin 사이에서 session이나 사용자 데이터를 복제·공유하지 않는다.
- **Shared UI**: Hero, sample card, Quickstart, CTA 등 marketing component와 CSS만 공통 source로 사용한다. Cloud Run의 account/session loader와 owner UI를 Sites에 capability flag로 숨기는 방식보다 Sites 전용 최소 entry에서 marketing component만 import하는 구조를 우선한다.
- **Cloud Run host**: local Vite middleware에 결합된 `dev-server.js`를 production 진입점으로 그대로 사용하지 않는다. Fetch-style backend handler와 Node host adapter를 재사용하는 작은 production server를 두고 static asset serving, graceful shutdown, body limit, forwarded origin 정책을 명시한다.
- **Container 계약**: container는 `PORT` 환경변수를 사용하고 `0.0.0.0`에 bind하며, read-only image + writable temporary filesystem을 가정한다. persistent JSON file은 production source of truth로 간주하지 않는다.
- **Neon 경계**: owner, OAuth state, browser session, CLI challenge/token digest, device, usage revision, visibility를 structured data 후보로 둔다. 이번 task는 현재 store API와의 adapter seam 및 transaction/concurrency 요구를 문서·계약 테스트 수준에서 확정한다.
- **R2 경계**: 공개 PNG/GIF와 immutable revision object, stable public key/redirect 또는 revalidation 전략을 media 후보로 둔다. private preview와 on-demand render 권한은 Cloud Run이 보유하고, 이번 task에서는 실제 production write를 수행하지 않는다.
- **Security**: Sites는 Cloud Run API를 호출하지 않으므로 Sites를 위한 CORS와 credentialed request를 추가하지 않는다. OAuth `redirect_to`, cookie와 CSRF는 Cloud Run same-origin 제품 경계에서만 유지한다.
- **Fail-open 금지**: Sites는 사용자 계정이나 usage 상태를 추론하지 않고 항상 명시적인 sample card와 Cloud Run 이동 CTA를 표시한다. canonical app URL이 없으면 CTA를 비활성화하며 임의 production URL로 대체하지 않는다.
- **시각 검증**: 같은 marketing component, fixture와 locale로 Cloud Run landing과 Sites mirror를 렌더한다. Cloud Run에만 있는 account action은 시각 비교 대상에서 제외하며, 그 외 차이 또는 UI 변경은 작업지시자 직접 검증과 승인을 받은 뒤 다음 단계로 진행한다.

## 잠정 단계

- **Stage 1 — Cloud Run runtime과 marketing component 계약**
  - Cloud Run deployment config와 shared marketing component 경계를 정의
  - browser-only marketing artifact에서 server/native/account module이 제외되고 Cloud Run Home이 기존 제품 흐름을 보존하는 단위 테스트 추가

  - production Node server, Docker artifact와 container smoke path 구현

- **Stage 3 — Neon/R2 adapter boundary와 Cloud Run 보안 계약**
  - structured store와 media store의 source-of-truth, idempotency, cache, failure policy를 공식 문서와 contract test 후보로 확정

- **Stage 4 — Sites marketing mirror POC**
  - Sites manifest/build entry를 추가하고 shared Hero/sample card/Quickstart/CTA를 빌드
  - API·account·session·storage가 없는 정적 marketing artifact와 Cloud Run `/` navigation을 검증
- **Stage 5 — Cloud Run 우선 검증·marketing 시각 비교와 fallback 결론**
  - Cloud Run canonical artifact를 먼저 통합 smoke하고 가능한 범위에서 Sites marketing deployment와 desktop/mobile 비교 수행
  - Sites remote 배포는 MVP release gate에서 제외하고 Cloud Run 단독 fallback 및 후속 production task 입력을 확정

- Sites CTA는 Cloud Run `/`로 이동하며 로그인과 사용자 card 작업은 전부 Cloud Run에서 시작한다.

## 리스크

- **Sites capability 변화**: public beta 제약과 지원 framework가 바뀔 수 있다. Sites adapter를 optional로 유지하고 Cloud Run artifact에 의존시키지 않는다.
- **동일 UI와 동일 기능의 혼동**: Sites는 marketing component만 공유하고 실제 사용자 기능은 제공하지 않는다. CTA와 문서에서 Cloud Run 제품 전환을 명시하고 fake signed-in/card state를 만들지 않는다.
- **이벤트 목적의 범위 확장**: 이벤트 참가를 위해 제품 backend까지 Sites에 복제하면 MVP 일정과 보안 경계가 흔들린다. sample marketing mirror만 허용하고 Sites를 release gate에서 제외한다.
- **Native renderer container 호환성**: `@napi-rs/canvas`의 target architecture와 base image 조합이 실패할 수 있다. production과 동일한 Linux image에서 PNG decode까지 smoke한다.
- **파일 저장소의 production 오용**: container filesystem은 ephemeral이며 instance 간 공유되지 않는다. POC fixture 외 `PROFILE_STORE_FILE`을 production durability로 문서화하지 않는다.
- **두 landing의 시각 drift**: host별 JSX/CSS fork가 생기면 시각·접근성 회귀가 발생한다. marketing component와 CSS를 공유하고 host entry만 분리한다.
- **외부 계정·비용·secret 의존**: Cloud Run, Sites, Neon, R2 remote smoke는 계정과 secret이 필요할 수 있다. 승인되지 않은 유료 resource를 만들지 않고 local artifact 검증과 remote 검증을 분리한다.
- **후속 migration 과대 확장**: 이번 task에서 Neon/R2 전체 구현으로 넘어가지 않는다. adapter boundary와 decision만 확정하고 data migration은 별도 issue로 넘긴다.

## 승인 요청 사항

- Cloud Run + Neon + R2를 단일 canonical MVP 구조로 두고 Sites를 이벤트·홍보용 marketing mirror로 제한하는 방향
- Sites에서 사용자 계정·card·API를 다루지 않고 CTA로 Cloud Run `/`에 이동하는 방향
- cross-origin API/session, provider binding과 D1/Neon 이중 저장을 모두 제외하는 보안·데이터 경계
- 공식 architecture 문서를 `docs/production-hosting.md`에 두는 문서 위치 판단
- 이번 task는 Cloud Run container·Sites marketing mirror POC와 adapter contract까지 수행하고 Neon/R2 전체 migration, custom domain, npm publish는 후속 task로 남기는 범위
- 외부 provider credential이 필요한 remote 배포는 비용·resource 생성을 별도 승인받고, 승인되지 않으면 local artifact smoke를 수용 기준의 검증 근거로 사용하는 방향

승인되면 `task_m100_37_impl.md`의 수정된 5개 Stage를 기준으로 Stage 1 구현을 시작한다.
