# Task M100 #37 수행계획서

GitHub Issue: [#37](https://github.com/postmelee/codex-usage-profile/issues/37)
마일스톤: M100

## 목적

Codex Usage Profile의 production 배포 기준을 Cloud Run + Neon + R2로 확정하고, 동일 저장소의 공개 landing/card UI를 ChatGPT Sites에도 선택적으로 배포할 수 있는지 작은 POC로 검증한다. Cloud Run은 GitHub OAuth, browser session, device login, CLI submit, PNG rendering의 유일한 canonical runtime으로 유지한다.

ChatGPT Sites는 Cloud Run과 경쟁하는 두 번째 제품 backend가 아니라 익명 landing, Quickstart, 공개 카드 진입점을 제공하는 보조 frontend로 한정한다. Sites 배포가 실패하거나 지원 범위가 바뀌어도 Cloud Run 단독으로 전체 MVP를 배포할 수 있어야 한다.

## 배경

현재 저장소는 Vite frontend와 Node HTTP runtime을 같은 저장소에서 실행한다. `src/profile-runtime/dev-server.js`는 `node:http`와 Vite middleware를 결합하고, `src/profile-backend/durable-store.js`는 단일 JSON 파일을 영속 저장소로 사용하며, `src/profile-card/renderer.js`는 `@napi-rs/canvas`로 PNG를 생성한다. 이 구성은 로컬 MVP에는 충분하지만 container health, process lifecycle, concurrent writes, shared persistence, public media delivery가 필요한 production 계약은 아직 없다.

M100의 다음 production 작업 전에 runtime과 platform 책임을 확정해야 한다. [ChatGPT Sites 문서](https://learn.chatgpt.com/docs/sites)는 기존 web project의 hosting과 platform resource 사용을 지원하지만, 현재 제품의 GitHub OAuth/session/device submit backend를 그대로 소유한다는 보장은 없다. 반면 [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract)는 Node runtime과 native PNG renderer를 포함한 canonical application host에 적합하다.

따라서 본 task에서는 Cloud Run을 제품 runtime, Neon을 structured record의 장기 진실 원천, R2를 공개 card media의 진실 원천으로 설계한다. 실제 전체 migration은 후속 task로 남기고, 이번 spike는 배포 artifact, adapter boundary, 보안 경계와 시각 동등성을 검증한다.

## 범위

### 포함

- Vite frontend의 공통 source와 Cloud Run/Sites별 build·runtime 진입점 분리

- Sites와 Cloud Run 사이의 anonymous/public data, redirect allowlist, CORS, cookie, CSRF 경계 정의와 회귀 테스트
- Neon repository adapter와 R2 card media adapter가 후속 migration에서 구현할 최소 interface 및 단일 진실 원천 정의
- Sites 미사용 또는 배포 실패 시 Cloud Run 단독 fallback 검증
- desktop/mobile 대표 viewport의 Cloud Run/Sites landing 시각 비교
- architecture decision과 deployment boundary의 공식 문서화

### 제외

- 전체 JSON durable store를 Neon schema와 transaction으로 이관하는 작업
- production R2 bucket에 card를 실제 materialize하고 CDN cache invalidation을 완성하는 작업
- custom domain, DNS, TLS와 최종 production secret 등록
- npm package publish와 CLI 기본 server origin 확정
- Sites가 GitHub OAuth callback, browser session, device approval 또는 submit API를 직접 소유하는 구조
- Sites runtime storage와 Neon에 같은 owner/usage/session 데이터를 이중 기록하는 구조
- cross-subdomain shared session cookie 도입
- production observability, backup, retention, account deletion의 전체 구현

## 설계 방향

- **Canonical runtime**: Cloud Run만 OAuth, session, device flow, CLI submit, owner visibility mutation, PNG render를 처리한다. Sites에는 credential, session secret, GitHub client secret 또는 submit token을 배치하지 않는다.
- **Sites 역할**: Sites는 익명 landing과 공개 정보만 렌더링한다. 로그인 action은 Cloud Run app으로 navigation하며, OAuth callback 이후 authenticated UI도 Cloud Run origin에서 계속 사용한다. 두 origin 사이에서 session을 복제하거나 공유하지 않는다.
- **Shared UI**: React component와 CSS는 공통 source를 사용하되 host capability를 명시적인 adapter/config로 주입한다. Sites build에서 backend-only module과 native dependency가 bundle에 포함되지 않도록 entry boundary를 테스트한다.
- **Cloud Run host**: local Vite middleware에 결합된 `dev-server.js`를 production 진입점으로 그대로 사용하지 않는다. Fetch-style backend handler와 Node host adapter를 재사용하는 작은 production server를 두고 static asset serving, graceful shutdown, body limit, forwarded origin 정책을 명시한다.
- **Container 계약**: container는 `PORT` 환경변수를 사용하고 `0.0.0.0`에 bind하며, read-only image + writable temporary filesystem을 가정한다. persistent JSON file은 production source of truth로 간주하지 않는다.
- **Neon 경계**: owner, OAuth state, browser session, CLI challenge/token digest, device, usage revision, visibility를 structured data 후보로 둔다. 이번 task는 현재 store API와의 adapter seam 및 transaction/concurrency 요구를 문서·계약 테스트 수준에서 확정한다.
- **R2 경계**: 공개 PNG/GIF와 immutable revision object, stable public key/redirect 또는 revalidation 전략을 media 후보로 둔다. private preview와 on-demand render 권한은 Cloud Run이 보유하고, 이번 task에서는 실제 production write를 수행하지 않는다.
- **Security**: Sites origin은 필요 시 공개 GET allowlist만 허용한다. credentialed cross-origin API를 기본값으로 열지 않는다. OAuth `redirect_to`는 server-side allowlist를 통과한 Cloud Run local path만 허용하고, state-changing request는 existing same-origin session·CSRF 방어를 유지한다.
- **Fail-open 금지**: Sites config나 remote public API가 없을 때 로그인된 것처럼 보이거나 mock owner data로 대체하지 않는다. Sites 장애는 Cloud Run canonical URL 링크로 fallback한다.
- **시각 검증**: 같은 fixture와 locale로 Cloud Run/Sites landing을 렌더하고, 기능 차이는 auth handoff 안내에만 제한한다. 시각 차이 또는 UI 변경이 있으면 작업지시자 직접 검증과 승인을 받은 뒤 다음 단계로 진행한다.

## 잠정 단계

- **Stage 1 — Host capability와 production runtime 계약**
  - Cloud Run/Sites capability model, runtime config, health/static/API 경계를 정의
  - Sites build에서 server/native module이 제외되고 Cloud Run host가 기존 backend handler를 보존하는 단위 테스트 추가
- **Stage 2 — Cloud Run container POC**
  - production Node server, Docker artifact와 container smoke path 구현
  - `PORT`, bind address, health, static landing, API error mapping과 PNG render를 local container에서 검증
- **Stage 3 — Sites public frontend POC와 auth handoff**
  - Sites manifest/build entry를 추가하고 shared landing/card/Quickstart UI를 빌드
  - login action이 Cloud Run canonical app으로 이동하며 Sites가 session/API mutation을 소유하지 않음을 검증
- **Stage 4 — Neon/R2 adapter boundary와 보안 계약**
  - structured store와 media store의 source-of-truth, idempotency, cache, failure policy를 공식 문서와 contract test 후보로 확정
  - origin allowlist, cookie, CSRF, redirect와 anonymous public GET 경계를 보강
- **Stage 5 — 이중 배포·시각 비교와 fallback 결론**
  - 가능한 범위에서 Cloud Run과 Sites deployment smoke, desktop/mobile Playwright 비교 수행
  - 외부 credential이 없는 검증은 local artifact 수준으로 명시하고 Cloud Run 단독 fallback 및 후속 production task 입력을 확정

### 통합 검증

- Cloud Run container가 기존 OAuth, session, device flow, account usage submit과 PNG rendering을 canonical same-origin surface로 제공할 수 있다.
- Sites build는 같은 React/CSS source로 익명 landing, public card와 Quickstart를 렌더하지만 backend secret과 state-changing capability를 포함하지 않는다.
- Sites 로그인 action은 Cloud Run app으로 이동하며 OAuth callback 이후 사용자는 Cloud Run authenticated UI를 계속 사용한다.
- Neon과 R2의 후속 구현 대상, transaction/cache source-of-truth와 실패 정책이 공식 문서에 명확히 기록된다.
- Sites 사용 여부와 무관하게 Cloud Run 단독 배포로 MVP 전체 흐름이 유지된다.
- 외부 credential 또는 provider 제약 때문에 실제 remote 배포를 검증하지 못한 항목은 local artifact 검증과 구분되어 보고된다.
- desktop·mobile에서 Cloud Run과 Sites 공개 UI에 incoherent overlap, text clipping, horizontal overflow가 없고 차이가 승인된 auth handoff에 한정된다.
- `git status --short`가 PR 준비 전 빈 출력이다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **Sites capability 변화**: public beta 제약과 지원 framework가 바뀔 수 있다. Sites adapter를 optional로 유지하고 Cloud Run artifact에 의존시키지 않는다.
- **동일 UI와 동일 기능의 혼동**: Sites는 시각 source를 공유하지만 authenticated capability를 공유하지 않는다. CTA와 문서에서 Cloud Run 전환을 명시하고 fake signed-in state를 만들지 않는다.
- **Cross-origin session 확대**: Sites로 session을 되돌리기 위해 parent-domain cookie나 broad credentialed CORS를 열면 공격 표면이 커진다. 이번 범위에서 금지하고 Cloud Run navigation handoff를 사용한다.
- **Native renderer container 호환성**: `@napi-rs/canvas`의 target architecture와 base image 조합이 실패할 수 있다. production과 동일한 Linux image에서 PNG decode까지 smoke한다.
- **파일 저장소의 production 오용**: container filesystem은 ephemeral이며 instance 간 공유되지 않는다. POC fixture 외 `PROFILE_STORE_FILE`을 production durability로 문서화하지 않는다.
- **이중 배포 drift**: host별 JSX/CSS fork가 생기면 시각·접근성 회귀가 발생한다. shared component를 기본으로 하고 capability adapter만 분리한다.
- **외부 계정·비용·secret 의존**: Cloud Run, Sites, Neon, R2 remote smoke는 계정과 secret이 필요할 수 있다. 승인되지 않은 유료 resource를 만들지 않고 local artifact 검증과 remote 검증을 분리한다.
- **후속 migration 과대 확장**: 이번 task에서 Neon/R2 전체 구현으로 넘어가지 않는다. adapter boundary와 decision만 확정하고 data migration은 별도 issue로 넘긴다.

## 승인 요청 사항

- Cloud Run + Neon + R2를 canonical production 구조로 두고 Sites를 optional public frontend로 제한하는 방향
- Sites에서 GitHub OAuth/session을 직접 구현하지 않고 로그인 시 Cloud Run app으로 전환하는 방향
- cross-subdomain session 공유와 D1/Neon 이중 저장을 제외하는 보안·데이터 경계
- 공식 architecture 문서를 `docs/production-hosting.md`에 두는 문서 위치 판단
- 이번 task는 container/Sites POC와 adapter contract까지 수행하고 Neon/R2 전체 migration, custom domain, npm publish는 후속 task로 남기는 범위
- 외부 provider credential이 필요한 remote 배포는 비용·resource 생성을 별도 승인받고, 승인되지 않으면 local artifact smoke를 수용 기준의 검증 근거로 사용하는 방향

승인되면 `task_m100_37_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지와 remote provider 검증 조건을 구체화한다.
