# Task M100 #27 수행계획서

GitHub Issue: [#27](https://github.com/postmelee/codex-usage-profile/issues/27)
마일스톤: M100

## 목적

Settings의 API token 생성 흐름을 MVP 운영 수준으로 hardening한다. 로그인 사용자가 실수나 반복 클릭으로 active API token을 과도하게 생성하지 못하도록 owner당 active token 개수 제한을 두고, 제한 상태를 backend와 UI 양쪽에서 일관되게 표시한다.

또한 session cookie 기반 settings mutation route의 SameSite/CSRF 방어 상태를 점검해 MVP 배포 전 필요한 최소 조치를 반영한다. 이번 task의 완료 상태는 token 생성 제한, revoke 후 재생성, 반복 클릭 방지, settings mutation 보안 점검이 테스트와 보고서로 고정된 상태다.

## 배경

#15에서 GitHub 로그인, Settings shell, API token 생성/조회/revoke, device 조회/rename 기능이 구현됐다. 로컬 smoke 검증 중 로그인된 사용자가 `Create token`을 반복 클릭하면 active token을 계속 생성할 수 있음을 확인했다.

현재 token 생성은 session owner만 가능하고 raw token은 생성 직후 한 번만 표시되므로 기능 자체는 정상이다. 하지만 API token은 bearer credential이므로 MVP 배포 전 active token 개수 제한과 repeated submit 방지를 추가하는 편이 안전하다. 사용 패턴은 개인 로컬 머신, 추가 장치, CI 정도가 핵심이므로 기본 제한은 owner당 active token 3개로 둔다.

## 범위

### 포함

- owner당 active API token 최대 3개 정책 정의 및 구현
- revoked token은 active token 제한 수에서 제외
- `POST /api/settings/tokens` backend 제한
- 제한 초과 시 안정적인 status/code/message 반환
- Settings API Tokens UI에서 제한 상태 표시
- 제한 도달 시 create action 비활성화 또는 명확한 error 표시
- create 요청 중 반복 클릭/중복 submit 방지 회귀 검증
- 같은 이름 중복 허용 여부 판단 및 기록
- session cookie 기반 settings mutation route의 SameSite/CSRF 방어 상태 점검
- MVP에 필요한 최소 보안 조치 구현 또는 후속 분리 판단

### 제외

- analyzer 사용량 추출 정확도 개선
- submit CLI 구현 변경
- README 카드 이미지 endpoint 구현
- GitHub OAuth App 운영 설정 변경
- production rate limit 인프라 전체 구현
- organization/team 단위 token policy
- token scope 세분화 정책

## 설계 방향

- active token 제한 기본값은 3개로 한다. 이 값은 backend 상수로 고정하고, UI가 API 응답 또는 token list 기반으로 같은 제한을 표현한다.
- active token은 `revokedAt`이 없는 token으로 정의한다. soft revoke 정책은 #15 구현을 유지한다.
- backend가 최종 방어선이다. UI disabled만으로 제한을 처리하지 않는다.
- 제한 초과 오류는 기존 `ProfileBackendError` 체계에 맞춰 반환한다. 이미 존재하는 error code 중 의미가 맞으면 `conflict`를 우선 사용한다.
- token name 중복은 이번 task에서 보안 이슈로 보지 않는다. 중복 name은 허용하되 active token 제한과 생성 시각 metadata로 관리 가능하게 두는 방향을 우선 검토한다.
- repeated click은 현재 UI의 submitting state로 방지되는지 확인하고, 부족하면 create button disabled 조건과 state transition을 보강한다.
- CSRF/SameSite 점검은 현재 session cookie serializer, settings mutation route, fetch credential 사용 경계를 함께 확인한다. MVP에서 즉시 필요한 조치가 작으면 이번 task에 포함하고, 별도 token 기반 CSRF 설계처럼 큰 범위는 후속으로 분리한다.
- 공식 사용자 문서는 이번 task에서 새로 만들지 않는다. 보안 정책과 판단은 수행계획서, 구현계획서, 단계 보고서, 테스트로 고정한다.

## 잠정 단계

- **Stage 1 — token limit backend policy**
  - active token 최대 3개 제한을 backend service/route에 적용한다.
  - revoked token 제외, limit 초과 error, 기존 create/list/revoke 회귀를 검증한다.
- **Stage 2 — Settings token limit UI**
  - Settings API Tokens UI가 active token 제한 상태를 표시하도록 보강한다.
  - create 중 반복 클릭 방지와 제한 도달 시 버튼/메시지 동작을 검증한다.
- **Stage 3 — SameSite/CSRF hardening review**
  - session cookie와 settings mutation route의 SameSite/CSRF 방어 상태를 점검한다.
  - MVP에 필요한 최소 조치가 있으면 구현하고, 큰 범위는 후속 이슈로 분리한다.
- **Stage 4 — integration QA and final report**
  - 전체 테스트, build, 가능 범위의 로컬 로그인 smoke를 수행한다.
  - token limit, revoke 후 재생성, 보안 점검 결과를 최종 보고서로 정리한다.

### 통합 검증

- active token이 3개일 때 추가 token 생성이 backend에서 거부된다.
- revoked token이 있으면 다시 token을 생성할 수 있다.
- UI에서 active token 제한 상태를 사용자가 이해할 수 있다.
- create 요청 중 버튼 연타로 중복 token이 생성되지 않는다.
- 기존 token list/create/revoke 정상 흐름이 유지된다.
- SameSite/CSRF 점검 결과가 단계 또는 최종 보고서에 기록된다.
- `git status --short`가 PR 준비 전 작업 산출물 외 불필요 변경 없이 정리된다.
- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **정책 값 과소/과대 설정**: active token 3개가 부족할 수 있다. MVP 사용 패턴 기준으로 3개를 기본값으로 두고, 실제 운영 피드백이 있으면 후속에서 조정한다.
- **UI-only 제한 위험**: UI만 disabled하면 API 직접 호출로 우회 가능하다. backend 제한을 최종 방어선으로 둔다.
- **CSRF 범위 확장**: full CSRF token 도입은 route/form/client 전반으로 커질 수 있다. 이번 task에서는 SameSite/session mutation 경계를 점검하고 MVP 최소 조치만 포함한다.
- **기존 smoke 데이터 영향**: 로컬 `.data`에 생성된 token이 제한 검증에 영향을 줄 수 있다. 테스트는 memory store로 독립 검증하고, 수동 smoke는 필요 시 로컬 store 상태를 확인한 뒤 진행한다.

## 승인 요청 사항

- active API token 제한 기본값을 owner당 3개로 고정하는 방향 승인
- revoked token은 제한 수에서 제외하는 방향 승인
- token name 중복은 이번 task에서 허용하고, 관리 UX 개선이 필요하면 후속으로 분리하는 방향 승인
- CSRF/SameSite는 MVP 최소 조치를 우선하고, full CSRF token 도입이 필요하면 후속 이슈로 분리하는 방향 승인

승인되면 `task_m100_27_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
