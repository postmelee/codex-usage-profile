# Task M100 #20 수행계획서

GitHub Issue: [#20](https://github.com/postmelee/codex-usage-profile/issues/20)
마일스톤: M100

## 목적

`codex-usage-profile` 안에 섞여 있는 usage snapshot contract와 향후 로컬 분석기 책임을 `codex-usage-analyzer`로 분리할 수 있는 구조를 만든다.

이번 task의 완료 상태는 새 분석기 패키지가 독립 SDK/CLI 형태로 export 가능하고, profile 웹 서비스가 해당 출력물인 `UsageSnapshot v2`를 소비하는 경계를 코드와 문서로 확인할 수 있는 상태다.

## 배경

M100 MVP는 사용자가 GitHub로 로그인하고 로컬 터미널에서 `npx codex-usage-profile@latest submit`으로 usage snapshot을 업로드하는 흐름을 목표로 한다. 하지만 사용량 분석 로직이 profile 웹 서비스에 묶여 있으면 향후 `tokenmon` 같은 별도 카드 서비스가 같은 분석기를 재사용하기 어렵다.

#19에서 `UsageSnapshot v2` 계약과 analyzer/profile 책임 경계를 정의했으므로, 이번 task에서는 그 계약을 기준으로 analyzer SDK/CLI 스캐폴드를 준비한다. GitHub 로그인, 사용자 bio, GitHub avatar 같은 GitHub-facing fields는 analyzer가 아니라 웹 서비스 계정 계층에서 병합한다.

## 범위

### 포함

- `codex-usage-analyzer`의 최소 SDK/CLI 공개 API 설계
- 현재 저장소 안에 export-ready workspace package 스캐폴드 추가
- `UsageSnapshot v2` validator/type/fixture를 analyzer package 경계에서 사용할 수 있게 정리
- analyzer CLI 예시 명령 정의: `npx codex-usage-analyzer@latest analyze --json`
- profile 쪽에서 analyzer 결과를 submit API로 받는 migration 경로 문서화
- 향후 `npx tokenmon@latest submit`이 analyzer SDK를 감싸서 사용할 수 있는 wrapper compatibility 확인

### 제외

- `tokenmon` 레포 생성과 카드 UI 구현
- 실제 GitHub 원격 레포 생성, npm publish, release automation 완성
- GitHub OAuth/session/device-code/API token 구현
- README 카드 PNG endpoint 구현
- 로컬 사용량 원천 전체 파서 완성

## 설계 방향

- 실제 원격 레포 생성 전, 현재 저장소 안에 `packages/codex-usage-analyzer/` workspace package를 먼저 만든다. 이 방식은 테스트와 PR 검증이 가능하고, 나중에 새 레포로 history 또는 subtree 이동하기 쉽다.
- analyzer package는 web 계정 정보를 받지 않는다. 입력은 로컬 usage source 또는 fixture이고, 출력은 `UsageSnapshot v2` JSON이다.
- profile package는 GitHub 계정, visibility, submit token, device, public URL, image renderer를 계속 소유한다.
- root package는 private app으로 유지하되 npm workspace를 사용해 analyzer package test/build를 함께 실행할 수 있게 한다.
- 초기 CLI는 실제 원천 파서 완성보다 contract-stable output과 validation path를 우선한다. 실제 parser 확장은 후속 task에서 진행한다.

## 잠정 단계

- **Stage 1 — 분리 경계와 migration inventory 확정**
  - 현재 v2 contract, profile-snapshot import/export, backend submit path 의존성을 조사한다.
  - analyzer package가 소유할 파일과 profile app에 남길 파일을 확정한다.
- **Stage 2 — analyzer workspace package 스캐폴드**
  - `packages/codex-usage-analyzer/`에 SDK entrypoint, CLI entrypoint, package metadata, README를 추가한다.
  - sample fixture 출력이 `UsageSnapshot v2` contract를 통과하게 한다.
- **Stage 3 — v2 contract module migration**
  - v2 validator/type/fixture의 canonical home을 analyzer package로 옮기고, profile 기존 import 경로는 compatibility re-export로 유지한다.
  - 기존 v1 path가 깨지지 않는지 확인한다.
- **Stage 4 — CLI wrapper compatibility와 문서 연결**
  - `analyze --json` smoke path를 테스트한다.
  - `tokenmon` 같은 wrapper가 analyzer SDK를 호출하고 자체 submit을 수행하는 경계를 문서화한다.

### 통합 검증

- profile 기존 v2 validator import 경로가 계속 동작한다.
- GitHub-facing fields가 analyzer snapshot에 들어가지 않는다는 테스트가 유지된다.

- `git diff --check`가 경고 없이 통과한다.

## 리스크

- **패키지 이동 범위 과대화**: v1 profile snapshot까지 함께 이동하면 blast radius가 커진다. 이번 task는 v2 analyzer contract와 CLI 스캐폴드에 집중하고 v1 compatibility는 re-export로만 보존한다.
- **새 원격 레포 생성 시점 혼선**: 원격 레포 생성과 npm publish는 GitHub 권한/릴리즈 정책이 필요하다. 이번 task는 export-ready workspace package를 만들고 실제 원격 생성은 별도 승인 또는 후속 task로 둔다.
- **analyzer와 web 책임 혼합**: GitHub-facing fields가 analyzer로 섞이면 tokenmon 같은 wrapper 재사용성이 떨어진다. validator와 문서에서 해당 필드를 계속 거부한다.

## 승인 요청 사항

- 이번 task에서 먼저 `packages/codex-usage-analyzer/` workspace package로 분리하고, 실제 GitHub 원격 레포 생성은 후속 승인 대상으로 두는 방향을 승인해달라.
- `UsageSnapshot v2` validator/type/fixture의 canonical home을 analyzer package로 옮기고, profile 기존 경로는 compatibility re-export로 유지하는 방향을 승인해달라.
- 실제 로컬 usage parser 완성은 제외하고, SDK/CLI 스캐폴드와 fixture 기반 contract validation을 우선하는 범위를 승인해달라.

승인되면 `task_m100_20_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지를 구체화한다.
