# Task #32 수행계획서

GitHub Issue: [#32](https://github.com/postmelee/codex-usage-profile/issues/32)
마일스톤: M100

## 목적

공개 웹 경로 `/u/:handle`이 실제 CLI submit 경계인 Account Usage Contract v1과 GitHub-owned identity를 사용하도록 전환한다. 로그인 사용자의 `/profile` owner preview, 공개 프로필, `/u/:handle/card.png`가 동일한 owner, latest usage, visibility를 기준으로 동작하게 하여 README 카드와 웹 공개 화면 사이의 데이터 불일치를 제거한다.

production 공개 경로에서는 legacy UsageSnapshot과 sample fixture에 의존하지 않는다. 공식 account usage 계약이 제공하지 않는 plugin/skill/activity 값을 합성하거나 0으로 표시하지 않고, 지원되는 summary와 source-dated daily buckets만 보여준다.

## 배경

Task #5와 #6에서 CLI submit과 README PNG endpoint는 `codex-usage-analyzer`의 identity-free Account Usage Contract v1을 기준으로 완성됐다. owner preview와 card renderer는 GitHub OAuth owner record의 이름, login, avatar와 latest usage record를 병합한다.

반면 현재 `App.jsx`의 public route는 `profileRoutes.js`와 legacy snapshot API를 사용한다. sample handle은 API를 조회하지 않고 fixture를 즉시 렌더링하며, `ProfilePage.jsx`는 current analyzer가 제공하지 않는 Activity insights와 Most used plugins까지 표시한다. 이 때문에 실제 submit 후 공개 페이지와 card endpoint가 같은 데이터 원천을 사용하지 않는다. #8은 stable invocation usage source가 없어 종료됐고, #32에서 공개 경로 자체를 현재 계약으로 정렬한다.

참고 계약은 다음과 같다.

- `codex-usage-analyzer` Account Usage Contract v1
- `docs/readme-card.md`의 public/private와 stable card URL 계약
- 기존 `profile-card` service의 owner/usage/visibility 검증과 avatar 보안 정책

## 범위

### 포함

- 공개 handle에 대한 owner + latest Account Usage Contract v1 조회 service 경계
- public/private, usage 없음, handle 없음에 대한 동일한 not-found 정책
- 공개 profile JSON route와 client method
- `/u/:handle`을 실제 공개 profile/card 데이터로 렌더링하는 UI
- sample handle 자동 fixture 우회 제거 또는 명시적인 개발 전용 경계로 격리
- production public route에서 legacy Activity insights와 Most used plugins 의존성 제거
- 공개 profile과 card PNG가 같은 owner, usage record, visibility를 사용하는 구조
- backend, API client, route, UI, Playwright, 보안 회귀 테스트
- README 및 관련 공식 사용자 문서의 현재 공개 경로와 legacy 호환성 설명 갱신

### 제외

- plugin/skill invocation 순위, 사용 횟수, icon metadata 수집
- `codex-usage-analyzer` Account Usage Contract v1 확장
- 로컬 Codex session 파일 또는 undocumented/private endpoint 분석
- legacy snapshot 저장 API와 validator의 전면 삭제
- landing page와 Quickstart onboarding
- production 배포, 도메인, database migration과 release 운영

## 설계 방향

- `profile-card` service에 공개 profile 조회를 추가하고 `renderPublicCard`와 공통 eligibility 규칙을 재사용한다. owner와 usage record가 모두 존재하고, 두 record의 handle/visibility가 일치하며 public일 때만 공개한다.
- HTTP에는 legacy `/api/snapshots/public/:handle`과 구분되는 Account Usage Contract v1 기반 public profile JSON endpoint를 추가한다. 응답은 server-owned GitHub identity, latest usage, public card URL에 필요한 최소 필드만 포함한다.
- API client와 public route loader는 새 endpoint를 사용한다. production `/u/:handle`에서는 sample handle 특례를 두지 않는다.
- 공개 페이지는 기존 card renderer가 생성하는 `/u/:handle/card.png`를 중심으로 구성해 owner preview 및 README card와 시각·데이터 revision을 공유한다. unavailable summary 값은 card renderer의 `—` 표현을 유지한다.
- private, missing, usage 없는 profile은 동일한 공개 not-found 응답으로 처리해 존재 여부나 identity를 노출하지 않는다.
- legacy `ProfilePage`, UsageSnapshot schema와 snapshot API는 이번 task에서 즉시 삭제하지 않는다. production app route 연결만 제거하고, 남은 compatibility surface는 명시적으로 문서화해 후속 제거 여부를 별도 판단한다.
- card PNG의 ETag, Cache-Control, locale, avatar host/content/size 제한은 변경하지 않는다. 공개 JSON에는 token, credential, owner id, private revision, local path를 노출하지 않는다.

## 잠정 단계

- **Stage 1 — 공개 Account Usage profile service와 HTTP 계약**
  - card service의 공개 profile eligibility를 추출하고 public JSON endpoint를 구현한다.
  - public/private/missing/usage 없음, handle·visibility 불일치, 응답 allowlist를 단위·HTTP 테스트로 검증한다.
- **Stage 2 — public route와 UI 전환**
  - API client와 `/u/:handle` loader를 새 endpoint에 연결한다.
  - 공개 페이지를 실제 card URL 중심으로 렌더링하고 sample fixture 자동 우회 및 unsupported activity UI 의존성을 제거한다.
- **Stage 3 — legacy 경계와 공식 문서 정리**
  - production route에서 분리된 UsageSnapshot 호환 범위를 명확히 하고 불필요한 runtime import와 안내를 정리한다.
  - README와 `docs/`에 실제 public profile, data availability, privacy 동작을 반영한다.
- **Stage 4 — 통합·시각·보안 회귀 검증**
  - login fixture 또는 runtime seed를 이용해 `submit -> publish -> /u/:handle -> card.png` 흐름을 검증한다.
  - desktop/mobile screenshot, card revision 일치, private/missing 비노출, 기존 owner preview와 README cache 회귀를 확인한다.

## 리스크

- **legacy route 회귀**: 기존 screenshot 및 heatmap 테스트가 sample full-profile 경로에 의존한다. production 연결 제거와 fixture 전용 검증을 분리하고, 삭제는 이번 task 범위에서 제외한다.
- **공개 여부 불일치**: owner와 usage record의 visibility 또는 handle이 어긋나면 identity가 노출될 수 있다. card endpoint와 같은 eligibility helper를 사용해 fail-closed 처리한다.
- **JSON과 PNG revision 불일치**: 서로 다른 조회 경계를 만들면 공개 페이지와 README card가 다른 데이터를 볼 수 있다. 동일 owner/usage record resolver를 공유하고 통합 테스트로 고정한다.
- **정보 노출**: 공개 JSON이 owner id, 내부 timestamp, private revision 또는 credential을 포함할 수 있다. 명시적 serializer allowlist와 보안 테스트를 둔다.
- **sample 개발 경험 저하**: 자동 sample route 제거로 frontend-only preview가 달라질 수 있다. 필요하다면 query 또는 별도 dev fixture adapter로 격리하되 production pathname에는 적용하지 않는다.
- **시각 중복**: 공개 페이지 안에 card image만 표시하면 owner profile과 정보가 중복될 수 있다. operational public profile 성격에 맞게 card를 중심으로 하고 별도 마케팅 composition은 추가하지 않는다.

## 승인 요청 사항

- 공개 JSON endpoint와 card renderer가 같은 service eligibility를 공유하는 설계
- `/u/:handle`을 Account Usage Contract v1 card 중심 공개 페이지로 전환하는 방향
- production sample handle 특례를 제거하고 legacy UsageSnapshot 코드는 호환성 경계로만 남기는 범위
- plugin/skill/activity enrichment, landing/Quickstart, production 배포를 제외하는 범위
- 공식 사용자 문서는 기존 `README.md`, `docs/readme-card.md`, `docs/usage-snapshot-v2.md`에서 최소 수정하는 위치 판단

승인되면 `task_m100_32_impl.md`에서 단계별 산출물, 실제 변경 파일, 검증 명령, 커밋 메시지를 구체화한다.
