# 수행계획서 — Task #49: Sites full-stack MVP 적합성 검증 및 production 아키텍처 재결정

GitHub Issue: [#49](https://github.com/postmelee/codex-usage-profile/issues/49)
마일스톤: M100

## 목적

현재 ChatGPT 유료 플랜에 포함된 Sites를 제품 전체의 canonical MVP host로 사용할 수 있는지 bounded Gate 0 검증으로 판정한다. 단순한 정적 landing 배포가 아니라 기존 GitHub OAuth, browser session, CLI device login과 submit, public/private profile, card render, publish/unpublish와 stable image route의 동등성을 기준으로 삼는다.

검증이 통과하면 Sites + D1 + R2를 증분 인프라 비용 0원의 MVP architecture로 채택할 근거와 후속 migration 범위를 확정한다. 핵심 계약 중 하나라도 충족하지 못하면 현재 Cloud Run + Neon + R2 architecture와 이미 구현된 artifact를 fallback으로 유지하고, 실패 조건과 재검토 기준을 남긴다.

## 배경

- #37은 Cloud Run + Neon + R2를 canonical architecture로 확정하고 Sites를 sample-only marketing mirror로 제한했다.
- #41과 #42는 각각 provider-neutral store/media contract를 기준으로 Postgres adapter와 S3-compatible R2 adapter를 구현했다.
- #43은 Stage 1·2에서 Cloud Run 운영 계약과 local deployment artifact를 준비했지만, provider resource를 생성하는 Stage 3 Gate A에는 진입하지 않았다.
- 현재 `.openai/hosting.json`은 D1/R2 binding을 모두 `null`로 유지하고, `build:sites`는 API·account·session·provider storage가 없는 marketing artifact만 만든다.
- 초기 사용자가 적은 비상업 개인 프로젝트에서는 production-grade 다중 provider 운영보다 추가 배포 비용 0원과 단순한 운영 경계가 우선한다.
- Sites는 public beta이며 D1, R2, runtime secret과 인증 가능한 site shape를 제공하지만, 현재 제품의 app-owned GitHub OAuth, PostgreSQL callback transaction, native `@napi-rs/canvas` renderer와 외부 CLI 요청이 실제 hosted runtime에서 동작하는지는 문서만으로 확정할 수 없다.

이 task는 전체 migration을 먼저 수행하지 않는다. 기존 계약과 fallback을 보존한 상태에서 local capability POC를 완료하고, 별도 승인 Gate 뒤 제한된 remote Site에서 핵심 흐름을 검증한 다음 architecture 채택 여부를 결정한다.

## 설계 방향

- 기존 project, npm lockfile, React/Vite UI, backend service, store/media contract와 CLI protocol을 보존한다. Sites 전용 starter로 제품을 새로 작성하지 않는다.
- 현재 sample-only `build:sites`와 Cloud Run build를 즉시 제거하지 않는다. 검증 중에는 별도 full-stack Sites entry/build를 두고 fallback과 비교 가능하게 유지하며, 최종 판정에서 canonical surface 정리를 후속 migration 범위로 넘긴다.
- Sites runtime은 Cloudflare Worker-compatible ESM으로 구성한다. Node HTTP server, local filesystem과 native binary를 hosted artifact에 포함하지 않는다.
- D1 access는 `db/schema.ts`와 작은 adapter 뒤로 격리하고 prepared statement와 `batch()`를 사용한다. 현재의 임의 `transaction(runner)`가 D1에서 실제 transaction인 것처럼 보이게 구현하지 않는다.
- OAuth callback, CLI 승인/교환, usage submit, visibility 변경의 원자성은 provider별 named atomic operation 또는 동등한 명시적 경계로 분리한다. Postgres와 memory adapter도 같은 behavior contract를 통과하게 해 기존 기능을 회귀시키지 않는다.
- R2는 Sites가 제공하는 logical binding을 사용한다. S3 access key를 hosted runtime에 추가하지 않고, application ETag는 기존 PNG digest를 유지하며 storage ETag는 conditional storage operation에만 사용한다.
- GitHub OAuth identity를 유지한다. Sign in with ChatGPT는 GitHub login/avatar/provider user id 의미를 바꾸므로 이번 task의 대체 인증으로 사용하지 않는다.
- 외부 identity provider의 Sites 지원 경로는 구현 전에 확인한다. platform-supported path가 확인되지 않으면 app-owned OAuth를 억지로 우회 구현하지 않고 hard blocker로 판정한다.
- PNG renderer는 JS/Wasm 후보를 격리 비교한다. exact native binary output 일치보다 기존 정보, typography, locale, 크기, 결정성과 README 사용성을 수용 기준으로 삼되, 변경된 결과는 작업지시자 시각 승인 전 다음 단계로 진행하지 않는다.
- external Site/D1/R2 생성과 공개 access 변경은 Stage 5의 별도 승인 Gate를 통과해야 한다. 처음에는 owner-only access와 비production test data를 사용하고, public/CLI smoke 직전에 exact URL·OAuth callback·노출 범위를 다시 승인받는다.
- Site 생성은 한 번만 수행하고 `.openai/hosting.json`에 플랫폼이 반환한 opaque `project_id`를 그대로 재사용한다. 임의 ID를 만들거나 다른 프로젝트 ID로 대체하지 않는다.
- Task #43은 본 task 판정 전까지 provider apply를 보류한다. #43/#46을 close하거나 수정하는 대신 Stage 6에서 후속 처리 권고만 제시한다.

## 잠정 단계

- **Stage 1 — Sites full-stack compatibility 경계와 local harness**
  - 기존 marketing-only artifact와 분리된 Worker-compatible full-stack entry/build, host/binding/config contract와 artifact verifier를 구성한다.
  - app-owned GitHub OAuth의 platform-supported path, public API/CLI 접근 형태와 hard blocker 판정 기준을 공식 문서와 local seam으로 고정한다.
  - Cloud Run build와 기존 product route가 영향받지 않는지 검증한다.
- **Stage 2 — D1 structured store와 원자 연산 POC**
  - D1 schema/migration과 adapter를 구현하고 5개 원자 연산·rate limiter를 named atomic boundary로 검증한다.
  - duplicate callback/exchange, concurrent submit/visibility와 failure rollback을 local D1-compatible test에서 검증한다.
- **Stage 3 — native R2 media adapter POC**
  - R2 binding adapter로 revision write/read, stable materialization, conditional request, publish/unpublish와 failure recovery를 구현한다.
  - 기존 media-store contract와 public/private `404`, application ETag, concurrent publication 의미를 검증한다.
- **Stage 4 — Worker PNG renderer와 local full-stack 통합**
  - JS/Wasm renderer를 선택하고 기존 card의 locale, font, avatar, heatmap/stats, 결정적 PNG와 성능을 검증한다.
  - frontend, auth/device/API, D1/R2 adapter와 renderer를 local Sites runtime에 연결하고 전체 route smoke를 수행한다.
  - desktop/mobile UI 또는 card 출력 차이를 이미지로 보고하고 작업지시자 시각 승인을 받는다.
- **Stage 5 — 승인된 remote Sites/D1/R2와 hosted 핵심 흐름 검증**
  - Gate A에서 ChatGPT account/workspace, 현재 Sites limit, 비용 조건, project/binding/secret 이름, test OAuth app, deploy commit과 owner-only access를 제시하고 승인받는다.
  - Gate B에서 exact production URL, public access 전환, GitHub callback, disposable test identity/data와 원복 범위를 제시하고 승인받는다.
  - 승인 후 Site를 한 번 생성하고 saved version→restricted deployment→public smoke 순서로 진행하며 GitHub OAuth와 packed CLI end-to-end를 검증한다.
- **Stage 6 — architecture 판정, 공식 문서와 후속 handoff**
  - 비용, 기능 동등성, 보안, 운영성과 beta/lock-in 위험을 기준으로 Sites 채택 또는 기각을 판정한다.
  - 판정에 맞게 `docs/production-hosting.md`를 갱신하고 Cloud Run fallback, data export와 재검토 조건을 기록한다.
  - #43/#46의 중단·재개·대체 권고와 전체 migration 후속 task 범위를 최종 보고서에 제시하되, 이슈 상태는 별도 승인 없이 변경하지 않는다.

- 기존 GitHub owner identity, browser session, CLI protocol, public/private visibility와 card share URL 의미가 유지된다.

## 리스크

- **Sites public beta와 불투명한 plan limit**: 현재 계정 UI에서 limit과 공개 유지 조건을 기록하고, 한도 초과·정책 변경을 Cloud Run fallback trigger로 둔다.
- **외부 GitHub OAuth 지원 불확실성**: platform-supported path 확인과 remote callback smoke를 hard gate로 둔다. GitHub identity를 SIWC로 임의 교체하지 않는다.
- **D1 transaction 의미 차이**: generic callback transaction을 모방하지 않고 5개 원자 연산을 conditional SQL/batch와 named boundary로 재설계해 concurrency test로 고정한다.
- **PNG renderer 품질·성능 차이**: JS/Wasm 후보를 대표 `en`/`ko` fixture로 비교하고, 시각 승인과 hosted latency/bundle 검증을 통과하지 못하면 Sites를 기각한다.
- **native R2 binding과 S3 copy 의미 차이**: 작은 PNG의 get/put materialization, conditional operation과 concurrent publication을 failure injection으로 확인한다.
- **public route의 secret·private data 노출**: owner-only deployment에서 먼저 검증하고 public 전환은 별도 Gate B 승인을 요구한다.
- **data residency와 vendor lock-in**: export 가능한 D1/R2 data shape와 Cloud Run fallback을 유지하고, residency가 필요한 사용 사례는 Sites 채택 범위에서 제외한다.
- **#43과의 branch/divergence 충돌**: #49는 최신 `origin/devel` 기반 분리 worktree에서 진행하고 #43 branch를 수정·rebase하지 않는다. 채택 판정 뒤 필요한 commit 이동은 별도 승인으로 처리한다.
- **remote POC 부산물**: Site/D1/R2/test OAuth의 유지·비공개·삭제 여부를 Stage 5 Gate에 포함하고, material 삭제는 별도 승인을 받는다.

## 승인 요청 사항

- #49를 전체 migration 전의 bounded Gate 0 적합성 task로 한정하는 범위
- GitHub OAuth identity와 기존 product/CLI/store/media contract를 기능 동등성의 기준으로 유지하는 방향
- D1에서는 generic transaction callback 대신 5개 named atomic operation을 도입하는 방향
- native R2 binding과 Worker-compatible JS/Wasm renderer를 검증하되 Cloud Run/Postgres/S3 artifact를 삭제하지 않는 방향
- `docs/production-hosting.md`를 Stage 6 최종 판정에서만 수정하는 문서 위치 판단
- 6단계 진행과 Stage 5의 external Gate A/B, Stage 4의 card/UI 시각 승인
- #43/#46 상태는 이번 승인으로 변경하지 않고 최종 보고에서 별도 권고만 제시하는 범위

승인되면 `task_m100_49_impl.md`에서 단계별 산출물, 검증 명령, 커밋 메시지와 remote Gate 입력을 구체화한다.
